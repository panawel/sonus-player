# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Sonus — an Electron + Vite + React desktop MP3/audio player with a dark glassmorphic UI. macOS-focused (vibrancy, traffic-light title bar, file associations, dock/background-playback behavior).

## Commands

- `npm run dev` — starts Vite (`localhost:5173`) and launches Electron concurrently (via `concurrently` + `wait-on`). This is the normal development loop; the Electron window loads the Vite dev server, not `dist/`.
  - **Kill any previous dev server first** (`pkill -f "mp3Player/node_modules"` — scope the pattern to this project, a bare `pkill -f Electron` also kills VS Code and any other Electron app). If Vite prints `Port 5173 is in use, trying another one…` it binds **5174**, while Electron still loads **5173** — so `wait-on` succeeds, the window opens against the *old* server, and you silently test stale code with no error anywhere.
- `npm run build` — `vite build` (frontend → `dist/`) then `electron-builder`, producing a **universal** (Intel + Apple Silicon) `.dmg` and `.zip` in `release/`. ~224MB per artifact, ~498MB installed: both architecture slices of the Electron framework ship in one bundle. ~40s, but the *first* universal build downloads the x64 Electron dist (~100MB) and needs network. See `BUILD_INSTRUCTIONS.md` for the full packaging walkthrough (verification, cross-arch testing, file associations, moving to `/Applications`).
- `scripts/verify-bundle.sh [app] [--expect-universal|--expect-arch <arch>]` — structural checks on a packaged `.app` (defaults to `release/mac-universal/Sonus.app`). **The app path must come first when you pass a flag**: `verify-bundle.sh --expect-universal` reads the flag as the path and dies with `No app bundle at: --expect-universal`; write `verify-bundle.sh release/mac-universal/Sonus.app --expect-universal`. Exits 0/1. Asserts every Mach-O binary carries both slices, `LSMinimumSystemVersion`, all six file associations, both Finder Service bundles, a single merged `app.asar`, and that the smoke fixture is present. **A partial `lipo` merge is the failure this exists for** — the app launches fine on the machine that built it and then dies on Intel in whichever helper process was missed.
- `npm run lint` — ESLint over the whole repo (flat config in `eslint.config.js`). **The clean baseline is `5 problems (0 errors, 5 warnings)`** — three `exhaustive-deps` in `App.jsx` and one in `HomeDetailView.jsx` whose dep arrays are deliberately incomplete (each marked "intentionally omits" in a comment right above it), plus TanStack Virtual's incompatible-library notice in `TrackList.jsx`. Don't try to "fix" those five; a **sixth** warning is the signal. (One further exhaustive-deps warning — a volume/mute sync effect — genuinely disappeared when the full-width player pill removed volume control entirely and deleted the now-dead effect along with it; that's a real drop in the baseline, not a fix you need to re-apply.)
- `npm run test` — `vitest run`, all tests once. Tests sit beside their sources: `src/*.test.{js,jsx}` run under jsdom + React Testing Library, `electron/*.test.mjs` are pure Node against temp dirs — which is *why* `artwork.mjs`, `indexStore.mjs`, `launchFiles.mjs`, `finderServices.mjs`, `folderScan.mjs`, `pointerTracker.mjs`, `pointerMotion.mjs`, `appMenu.mjs` and `windowModes.mjs` are Electron-free modules.
  - **Coverage is deliberately lopsided, and a green run means less than it looks.** The pure modules, the sort/selection hooks and `TrackRow` are covered well. The three biggest renderer files are not covered at all: `HomeView.jsx` (1512 lines), `TagEditorWindow.jsx` (577) and `TrackList.jsx` have **no unit tests**, and `App.test.jsx` only asserts that 2598 lines of `App.jsx` mount without throwing. `SearchPanel.jsx`, `MiniPlayer.jsx` and the Chill-mode components (`ChillScene`, `ChillTurntable`, `ChillBeach`, `ChillScenePicker`) have no unit tests either; what *is* covered is their pure maths and hooks — `trackMatchesQuery`, `pointerTracker.mjs`, `pointerMotion.mjs`, `chillGeometry.js` / `chillScene.js` / `chillBeach.js` / `chillRoom.js` / `chillLyrics.js` / `chillScenes.js` (framing, the quad→matrix3d solver, the swing, the typing clock, breathing, the poster and laptop calibration, the scene registry) and `useChillChrome` — plus `ChillPhoneScreen` and `ChillLivingPhoto`'s no-WebGL fallback in jsdom. Everything meaningful about those is exercised **only** by the smoke suite below. `npm run test` passing says nothing about the UI.
- **Developing against the smoke suite: run only the section you touched.** `npx electron . --smoke --only=menus` (or `SONUS_SMOKE_ONLY=menus,adddialog`; sections: `tracklist, header, mini, menus, adddialog, listrows, tagwrite, folder, writers, reindex, fileopen, save-playing, reopen, tageditor, bench, frames, mix`) runs just those, ~10s instead of ~3min. Every check inside a chosen section is identical to the full suite; the others are not run. The result carries `partial: true` and a notice is printed: **a filtered pass is a development aid, never the gate**; run the full suite once before a build or release. A mistyped section name is reported as a failure (a filter matching nothing would otherwise read as success). Smoke windows also opt out of Chromium's background/occlusion throttling (`main.js`, smoke only) so a covered or idle window no longer produces random failures. Workflow that keeps it quick without skipping anything: unit tests + the relevant `--only` section while iterating, one full run at the end, in the background, never a rerun for the same edit.
- Single test file: `npx vitest run src/TrackRow.test.jsx`

  - Several of those are only observable in a built app — the blur one in particular is invisible under `npm run dev`. Running the unit tests alone will not catch them.
  - Prints one `SMOKE_RESULT:{...}` JSON line and exits 0/1. Assertions live in `electron/smokeTest.mjs`.
  - **The packaged app accepts `--smoke` too**: `release/mac-universal/Sonus.app/Contents/MacOS/Sonus --smoke`. The fixture MP3 and `smokeTest.mjs` ship inside `app.asar`, so the whole suite runs against the real bundle — asar packaging, `extraResources`, protocol registration and all — on *any* Mac you can copy it to. That is the acceptance test for a target machine; it needs no dev toolchain there and returns machine-readable JSON instead of a screenshot.
  - **Cross-architecture test on Apple Silicon**: `arch -x86_64 <packaged binary> --smoke` runs the real Intel slice under Rosetta. Validates the binary and every code path; it does **not** validate the target OS's APIs or its GPU, because Rosetta translates CPU only — the GPU work is still done by the host. On an arm64-only build this fails with `Bad CPU type in executable`, which is exactly what an Intel Mac sees.
  - Every result carries `arch`, `platform`, `osRelease`, `translated`, `slowFactor` and `electron`. A universal binary can execute as either architecture, so a bare pass/fail cannot tell you which slice was exercised — and a result pasted back from another machine is otherwise unattributable.
  - `metrics` carries measured-but-not-asserted numbers: `bench20k` (inject/sort ms) and `frameTimeMs` (requestAnimationFrame p50/p95/max/janky, sampled in Library as a baseline, in Now Playing with the blur furnace live, in Chill mode's turntable scene (`chill`) and in the WebGL-animated hammock scene (`chillBeach`) and study room (`chillRoom`), plus `npCostRatio` between baseline and Now Playing). The Chill numbers are the ones to compare on the 2017 iMac: the hammock redraws every frame, by choice, even while paused. **Deliberately not assertions** — the correct "too slow" threshold differs between an M-series Mac and a 2017 Intel iMac, and a hard limit would turn slow-but-working hardware into a red build that everyone learns to ignore. The probe *does* assert that it actually stressed the furnace (`flares === 3 && playing`), so a measurement of an empty panel cannot pass as healthy.
  - **Synchronisation is condition-based where it gates an assertion.** The suite used to sync with fixed `await sleep(400)` calls, which encoded the speed of the Apple Silicon machine they were written on; running the x86_64 slice under Rosetta made four *different* assertions fail across four runs. Shifting, non-reproducible failures are the signature of a harness race, not a defect. Those points now poll for the real condition, so machine speed stops mattering. Four rules when adding more: a layout measured right after `mainWindow.setContentSize` lags the resize by a frame (a `ResizeObserver` → state → transform chain), and a *stale* layout can satisfy a condition by accident (a bigger stage still "covers" a smaller box) — so wait for **two identical consecutive samples** before judging geometry; the fixture is only **20 seconds** long, so any block that runs longer than that after playback starts must set `audio.loop = true` (and restore it) or the track ends underneath it, `play()` finds nothing to resume, and every later test that expects audible playback (the mini player's) fails as a cascade; assert that an animation actually *advances* (angle/`currentTime`), not just that its `playState` is `running`; and the condition must be **false before** the transition (waiting on `.track-row` to be non-zero is wrong — the Library's rows are already mounted, so the loop exits immediately and samples too early), and on timeout the last value must still be returned so the `check()` still runs and still fails. `SLOW` scales the remaining "settle" sleeps, auto-detecting Rosetta; override with `SONUS_SMOKE_SLOW=<n>` on genuinely slow native hardware.
  - Two `?test=1`-gated hooks exist, and smoke mode is the only thing that passes that flag: `window.__sonusTest` in the main renderer, and `window.__sonusTagEditorTest` in the Tag Editor window (which lets the suite drive the Search Online popup without calling iTunes/MusicBrainz on every run — **the suite never makes network calls**).
  - For one-off DOM inspection outside the smoke suite (e.g. verifying a narrow-width layout), a standalone script run via `electron <script>.mjs` can create a `BrowserWindow` at any size and drive it with `executeJavaScript` — same technique `smokeTest.mjs` uses, no dev toolchain needed beyond the running `vite` dev server. **Creating a second `BrowserWindow` in the same process after the first sometimes fails to load** (`ERR_FAILED`, reproducible on this machine) — run one check per `electron` invocation rather than reusing a process across multiple test windows. For a window that loads the running dev server (`http://localhost:5173/?test=1`) give it `preload: electron/preload.cjs`, `webSecurity: false` and `enableLargerThanScreen: true` (to test sizes above the display), seed `window.__sonusTest.setLibrary([...])` with a `test-fixture.mp3` copy, and double-click a `.track-row` to start real playback. Resizing the *same* window with `setContentSize` between captures works fine; `webContents.capturePage()` captures opaque in-page content (a photo, say) correctly even though it can't capture vibrancy. The main process's IPC handlers aren't registered in such a window, so `library:load` / `fs:readArtwork` errors on stderr are expected noise.
  - **Driving the real app end to end (real `main.js`, real cursor)** — what the standalone-`BrowserWindow` technique above can't reach (anything the main process owns: pointer tracking, window chrome, IPC handlers). Start `npx vite`, then `npx electron . --remote-debugging-port=9333 --user-data-dir=/tmp/sonus-e2e` (a **throwaway profile**, so your real library and saved window state are untouched; there is no single-instance lock, so it runs beside a live `npm run dev`). To launch at a chosen size, pre-seed `/tmp/sonus-e2e/window-state.json` (`{"x":300,"y":200,"width":440,"height":300,"isMaximized":false,"isFullScreen":false,"displayBounds":{…}}` — only the x/y/width/height need to land on a display). Drive the page over CDP (`http://127.0.0.1:9333/json`); **run the driver with `ELECTRON_RUN_AS_NODE=1 npx electron script.cjs`**, because the system Node (v20) has no global `WebSocket` and `ws` isn't installed. Move the real cursor with `osascript -l JavaScript -e 'ObjC.import("CoreGraphics"); $.CGWarpMouseCursorPosition($.CGPointMake(x, y))'` (screen coordinates, no permissions needed). Things that look like they should work but don't: `window.resizeTo()` from the page doesn't resize an Electron window, `Browser.setWindowBounds` isn't available on the page target, and `screencapture` from inside a Claude Code session is denied ("could not create image from rect" — no Screen Recording permission), so native window chrome (traffic lights) can't be seen from here; ask the user to look. Kill it with `pkill -f "user-data-dir=/tmp/sonus-e2e"` and delete the profile.
  - **To run the suite against a *development* React build** — `NODE_ENV=development npx vite build --mode development && npx electron . --smoke`. The normal suite runs production React, which never double-invokes StrictMode updaters, so a whole class of dev-only bugs (see the "side effect inside a `setState(updater)`" row below) passes it while breaking under `npm run dev`. This is the only way to exercise that path with real IPC. `--mode development` **alone is not enough** — Vite still emits production React (bundle stays ~402KB); the `NODE_ENV` env var is what flips it (bundle ~639KB — check that number, it's the only visible confirmation). Run a plain `npx vite build` afterwards so `dist/` is production again.
- Cold-launch smoke variant: `npx electron . --smoke --open-file=/tmp/a.mp3 --open-file=/tmp/b.mp3` — seeds the same batch a real Finder double-click would, then runs a dedicated launch-ordering assertion set and exits. macOS only delivers `open-file` to a registered app, so this path is otherwise invisible to `npm run dev`.

In that case the fix is manual: crop tightly around the field to find its pixel bounds, sample its fill color from a flat area away from any glyphs, `ImageDraw.rectangle` over just the interior (inset a few px so the field's own rounded border survives untouched), then draw replacement text sized to actually fit the box (measure with `textbbox`, shrink the string or the font until it's narrower than the interior — don't guess).

## Cutting a release

`BUILD_INSTRUCTIONS.md` covers *building*; this is *publishing*. The repo is public at **https://github.com/panawel/sonus-player** and releases carry the `.dmg` + `.zip` as GitHub Release assets — they cannot live in the tree, since GitHub hard-rejects files over 100MB and each artifact is ~224MB.

1. **`git status` must be clean before building.** The artifacts have to provably correspond to the tag, not to a slightly-earlier local build.
2. `npm run build` → `./scripts/verify-bundle.sh` → smoke **both** slices (`arch -arm64` and `arch -x86_64`).
3. `shasum -a 256` both artifacts. The hashes go into the release notes verbatim: for an unsigned app that is the *only* integrity signal on offer, so a wrong one is worse than publishing none.
4. Tag, push, create the Release, upload both assets.
5. **Verify by downloading the published asset and re-hashing it** — not by re-hashing the local file, which proves nothing about what GitHub actually stored.

Repeat the Gatekeeper instructions *inline* in the release notes. People arrive at the Releases page directly from a link and never see the README, and an unsigned app that appears broken on first launch is the single biggest drop-off point.

**Environment gotchas on this machine** (both cost real time to rediscover):
- **`gh` is not installed and there is no Homebrew.** Releases go through the GitHub REST API with the token already in the macOS keychain — `printf 'protocol=https\nhost=github.com\n\n' | git credential fill` yields a token with `repo, workflow, read:user, user:email` scopes. Never echo it.
- **The system `python3` has no CA bundle**: `urllib` dies with `CERTIFICATE_VERIFY_FAILED` on any HTTPS call. Use `curl` for the API and `python3` only for assembling/parsing JSON locally.
- **Annotated tags don't resolve to commits.** `git rev-parse v1.0.0` returns the tag *object*; comparing it to `HEAD` reports a phantom mismatch. Use `git rev-parse 'v1.0.0^{}'`.
- **Git identity here is repo-local `panawel`**, deliberately different from the global `Idan Pnuel`. Don't "correct" it — the global config would write a real name into public commit history, permanently.
- **`arch -x86_64 <binary> --smoke` failing with `Bad CPU type in executable` doesn't necessarily mean the build isn't universal** — it's also exactly what happens when Rosetta itself isn't installed on the host Mac, which a macOS upgrade can silently reset (hit for real right after an upgrade to macOS 27). Don't assume the build is broken and start re-lipo'ing things; check first with a trivial system binary the build had no hand in: `arch -x86_64 /usr/bin/true` fails identically either way, so the real discriminator is `lipo -info <binary>` (confirms both slices are genuinely present) plus `ps aux | grep oahd` / `pkgutil --pkgs | grep -i rosetta` (confirms whether Rosetta is actually installed). If it's missing, `softwareupdate --install-rosetta --agree-to-license` is the fix — a standard, reversible Apple component install, not a system/security setting change.
- **The x86_64 smoke under Rosetta flakes roughly one run in three**, on a shifting assertion ("library command bar", "instant load", the frame-time probe, the Mix block's `waitFor` checks) — the harness-race signature described under `npm run test` above, not a defect; it doesn't always fail just one assertion either — a heavily-loaded run can take out a cluster of unrelated ones at once (real case: `mix: Details page shows the MIX kicker` through the breadcrumb check, four in one run). Protocol: rerun **once**, and capture the *full* failure text that time (don't `cut` it) so a genuine second failure is diagnosable. Two failures in a row on the *same* assertion(s) is real. **A second run failing on a *different* assertion than the first is not yet a clean bill of health either** — that's still the harness-race signature, just a different sample of it — keep rerunning until one pass has zero failures; only that counts as confirmation. Never publish on a single green rerun without having seen what the first failure said. It takes 3–4 minutes translated, so run it in the background.
- **Intermittent smoke failures and multi-second frame stalls on this Mac, cause unconfirmed.** Seen across several runs: a single Now Playing frame taking 12s (once 484s — an ~8 minute run instead of ~50s), and runs where the mini-player section never appeared within its wait and everything after it failed. Every one passed on a plain rerun, repeatedly (five clean ~49s runs in a row at one point), and nothing in the code explained them. The smoke window is *visible* on screen, so the leading suspicion is the window being covered or the display idle (Chromium/macOS throttling an occluded window) — not proven, and `main.js` has no `backgroundThrottling`/`disable-backgrounding-occluded-windows` guard. **Stronger evidence since:** a run stuck for 11+ minutes while `ioreg -c IOHIDSystem | awk '/HIDIdleTime/'` showed the user idle for ~30 minutes (display almost certainly asleep); killed and rerun under `caffeinate -di npx electron . --smoke` (keeps the display awake for just that command), it passed in ~50s twice in a row. Still not proven the cause, but when the user is away, **run smoke as `caffeinate -di npx electron . --smoke`** — it costs nothing. If it recurs anyway: check `ps aux | grep -i electron` first (the item below), look at the metrics' `frameTimeMs.max` (a huge value = a stall, not a defect), and rerun before debugging. Also remember that `pkill -f "mp3Player/node_modules"` — the documented step before a smoke run — stops the user's own `npm run dev` window too; restart it afterwards.
- **The Chill idle-fade smoke check (`bar, tabs, search, add and exit all fade out together…`) failed intermittently, then three runs in a row — it was a REAL bug, not a flake.** `useChillChrome` remembered "the pointer is resting on the chrome" from the last `mousemove`'s target; that went stale whenever the pointer left without an event to say so (the smoke window resizing away from a parked cursor over the bar — the cursor's *position* decided whether a run failed, which is why it came and went; a user tabbing away after resting on the bar), and held the chrome up forever. Found only by logging what woke it (a trusted `mousemove` on the seek bar, then nothing). The fix asks the browser (`:hover`) when the timer fires. Lessons: don't remember pointer-over state, ask at decision time; a synthetic DOM `mousemove` can't test hover — use `webContents.sendInputEvent`; and don't explain an intermittent failure away ("the mouse", "a stall") without evidence — I blamed the mouse and then a stall, and both guesses ended up in this file before the log refuted them. (Real renderer stalls do exist — see the next entry; a 36s `frameTimeMs.nowPlaying.max` is how to recognise one.)
- **Running more than one Electron process at once (a `--smoke` run alongside another `--smoke` run, or alongside a live `npm run dev` window) makes `save-while-playing` fail spuriously**, cascading into `20k: scroll window actually moved` and a `frame-time probe` reading zero captured frames — all three at once, on *either* architecture, not the shifting-single-assertion Rosetta pattern above. Real audio playback and `requestAnimationFrame` both appear to get starved when something else is fighting for the same GPU/compositor. Confirmed by running the *same* build solo immediately after: clean pass, every time. Before trusting a `--smoke` failure (especially `save-while-playing`), check `ps aux | grep -i electron` and kill any other instance, then rerun alone.

- **Tooling gaps on this machine.** The system `python3` has Pillow but **no numpy/scipy/OpenCV** — for numeric fitting (the Chill mode homography was fitted with a small Levenberg-Marquardt in plain Node) use Node. And `python3 -I` (isolated mode, which the "untrusted data" guidance suggests for scripts that read downloaded files) **hides the user site-packages, so `import PIL` fails under it**; run plain `python3` from a directory with no stray `.py` files instead. `sed -i` needs `''` on macOS (`sed -i ''`); there is no `timeout`.
- **The Claude desktop app's browser pane can't run a local page's scripts from `file://`** — it renders a static `data:` snapshot with `script-src 'none'`, even for files inside the project. To show something live (spinning, interactive), serve the folder (`python3 -m http.server <port> --bind 127.0.0.1`), navigate to `http://127.0.0.1:<port>/…`, and stop the server afterwards. `screenshoots/` is gitignored, which makes it the right place for local-only mockups — but remember they may contain the user's own album art.

## Architecture

**Three layers, strict separation:**
- `electron/main.js` — the main process. Owns `BrowserWindow` creation/lifecycle, all `ipcMain` handlers (file dialogs, metadata parsing, MP3/FLAC/WAV tag writes), and OS integration (`open-file` for double-click-to-open, Finder Services, `electron-window-state` for remembered window geometry). **There are no native context menus** — every menu in the app is rendered in the renderer.
- `electron/preload.cjs` — the only bridge between them. Uses `contextBridge.exposeInMainWorld('electronAPI', {...})` with `contextIsolation: true` / `nodeIntegration: false`. Every renderer→main capability must be added here explicitly; the renderer has no other access to Node/Electron APIs.
- `src/` — the renderer, a standard Vite + React 19 app. `App.jsx` is effectively the whole main-window application: nearly all state (library, current track, playback, view routing between `'home'` / `'library'` / `'now_playing'`) lives in this one component via hooks. The other meaningful pieces: the unified tracklist engine (`TrackList.jsx`, `TrackRow.jsx`, `TrackListHeader.jsx`, `useTrackSelection.js`, `useTrackSort.js`, `trackUtils.js` — see [Tracklist engine](docs/ARCHITECTURE.md#tracklist-engine-tracklistjsx-trackrowjsx-tracklistheaderjsx-hooks)), `HomeView.jsx`, `HomeDetailView.jsx`, and `TagEditorWindow.jsx` (the Tag Editor, mounted instead of `App` in its own `BrowserWindow` — see [Tag Editor](docs/ARCHITECTURE.md#tag-editor-a-separate-window-not-a-view)). `src/main.jsx` is the entry point that decides which of the two to mount, based on a `?editor=1` URL query flag.
- `electron/artwork.mjs` (pure artwork normalization/repair), `electron/indexStore.mjs` (JSON metadata index + play stats — deliberately isolated so a future SQLite swap is contained), and `electron/folderScan.mjs` (recursive directory expansion for drag-and-drop and the Add Music dialog) are Electron-free modules unit-tested directly by vitest.

Dev vs packaged loading is decided by `app.isPackaged` in `main.js`: dev loads `http://localhost:5173`, packaged loads `../dist/index.html`.

Below `NARROW_LAYOUT_BREAKPOINT` (560px, `App.jsx`) — window `minWidth` is 380 — the whole shell restructures for phone-portrait widths: the title-bar tabs (Home | Library, plus a round + Add button) drop to icon-only (the active tab keeps its name), the player bar becomes its own floating pill, and Now Playing becomes a single-column Song/Lyrics tab view. Both widths' player bars are floating pills now, not docked panels — narrow's own (`PlayerPillNarrow.jsx`, two buttons: Play/Pause and Skip Forward, no seek strip, no menu) replaced the old docked mini-player bar entirely, including its second use inside narrow Now Playing's own Lyrics tab. The title-bar navigation is shared across both widths rather than narrow-exclusive, and **Search is a round title-bar button (or ⌘F) that opens a floating panel** (`SearchPanel.jsx`: whole-library Artists/Albums/Songs, scoped to the page on a Details page, and the Library/Details list behind it filters live as you type; it opens over Now Playing too, and the text never survives a page change — clicking outside closes it and the click is swallowed (nothing behind reacts), while on Library/Details the filter stays on the list and the search button shows it; see [Primary navigation](docs/ARCHITECTURE.md#primary-navigation-nav-pill)), so "narrow" and "full-width" are no longer two fully independent code paths everywhere. The tracklist engine is likewise shared and untouched. A third, height-driven state sits on top of both: at or below `MINI_LAYOUT_HEIGHT_BREAKPOINT` (420px tall — the window's `minHeight` is 180) the whole shell is replaced by `MiniPlayer.jsx`, a player-only card with Now Playing's moving lights and glow (shared `AmbientFlares.jsx`), from any page; the app underneath stays mounted but hidden, so it returns exactly as it was (taller window, the card's expand button, or Escape). Full-width Now Playing also has an opt-in **Chill mode** (`ChillScene.jsx`, `chillScene.js`): a photo fills the whole window (a fixed full-bleed layer, title strip included) and the artwork is part of it — the spinning record of the turntable scene, the live phone screen of the animated hammock scene, the prints on the wall of the animated study-room scene (rain, lightning, and she types — the song's own lyrics when it has them, stopping at verse breaks — with the music) — chosen from a picker and framed automatically for any window shape, with its chrome — bar, title-strip buttons, traffic lights — fading away together when idle — see [Chill mode](docs/ARCHITECTURE.md#chill-mode-the-turntable); the three scene photos (`turntable.jpg`, `beach.jpg`, `room.jpg`, ~1.2-1.3MB each) are the deliberately >1MB assets in the tree, and everything in `chillScene.js`, `chillBeach.js`, `chillRoom.js` and the masks is calibrated to *those* photos (generated by `scripts/make-chill-beach-mask.py` and `scripts/make-chill-room-mask.py`); the scenes share one animated-photo engine, each bringing its own shader and masks (`scene.fx`). See [Mini player](docs/ARCHITECTURE.md#mini-player-very-short-windows), [Player pills](docs/ARCHITECTURE.md#player-pills-full-width-and-narrow) and [Narrow layout](docs/ARCHITECTURE.md#narrow-layout-phone-portrait-widths).

Library's tracklist has extra sortable columns (Album/Year/Genre) beyond Title/lyrics/Duration, which appear and disappear one at a time as the window narrows — a separate mechanism from the narrow-layout breakpoint above. Home's detail pages (artist/album/year/quality/…) get the same columns through the same `extended` row mode, each suppressing whichever column is redundant for that page (`detailExtraColumns` in `trackUtils.js`). The width thresholds live in `trackUtils.js`, shared by `App.jsx` and `HomeDetailView.jsx` so they can never drift apart; none may drop below 780px (a hardcoded 700px smoke-test check depends on it). See [Tracklist engine → Library's extra columns](docs/ARCHITECTURE.md#tracklist-engine-tracklistjsx-trackrowjsx-tracklistheaderjsx-hooks).

### `backdrop-filter`: never hand-write the `-webkit-` prefix

**This broke every glass surface in the packaged app and went unnoticed, so treat it as a hard rule.** In `index.css`, write only the unprefixed `backdrop-filter`. Vite emits both spellings itself.

Writing both by hand is what breaks it: Vite's CSS minifier collapses a `backdrop-filter` + `-webkit-backdrop-filter` pair down to the **`-webkit-` one alone**, and Electron 41's Chromium has *removed* that property (`CSS.supports('-webkit-backdrop-filter', 'blur(10px)')` → `false`). The declaration is then dropped entirely and the element renders with no blur.

The failure mode is why it survived so long: `npm run dev` serves unminified CSS, where the unprefixed declaration is still present, so it looks perfect. Only the built/packaged app loses its glass. `.glass-panel`, `.track-dropdown`, and `.confirm-modal-panel` were all affected. (Inline React styles — the player panel, the NP overlay — were never affected, since those aren't minified.)

The smoke suite asserts `.glass-panel` has a real computed `blur()` against the **built** CSS. That assertion is the regression guard; don't delete it.

### The macOS support floor, and why Electron is pinned

The app ships **universal** (Intel + Apple Silicon) because the oldest machine it must run on is an **iMac 27" 5K 2017 (`iMac18,3`) — Radeon Pro 575 4GB, 24GB RAM, macOS Ventura 13.7.8**.

Two numbers govern whether that machine can run a given build:

| | Value | Source |
| --- | --- | --- |
| Electron 41.7.1's macOS floor | **12.0** (Monterey) | `LSMinimumSystemVersion` in the built `Info.plist` |
| The iMac's maximum macOS | **13.x** (Ventura) | Sonoma 14 requires an iMac 2019 or newer |

There is exactly one major version of headroom, and **it cannot be widened.** A 2017 iMac can never install macOS 14, so the day Electron's floor reaches 14 that machine is permanently excluded — no OS update, no build flag, no config change recovers it. The only options at that point are staying on the last compatible Electron or dropping the machine.

That is why `package.json` pins **`"electron": "41.7.1"` exactly, with no caret.** A routine `npm update` under `^41.7.1` could otherwise cross that line silently: the build succeeds, every test passes on Apple Silicon, and the failure only appears as "it won't open any more" on a machine that isn't in front of you.

**After any deliberate Electron bump**, check the floor before shipping — `scripts/verify-bundle.sh` asserts it and prints a warning naming this constraint if it moved:

```bash
/usr/libexec/PlistBuddy -c "Print :LSMinimumSystemVersion" release/mac-universal/Sonus.app/Contents/Info.plist
```

Anything `≤ 13.x` is fine. `14.0` or higher is the cliff.

Note that nothing else about the app is OS-version-sensitive: Chromium and Node are bundled, so every web and Node API travels with the build rather than the host. Vibrancy, `hiddenInset`, Automator Services and `open-file` all behave the same on Ventura as on macOS 26. The floor is the whole compatibility story.

### Known accepted issues (don't "fix" opportunistically)

- `webSecurity: false` in the `BrowserWindow` config is required for `file://` audio/art loading to work against the `http://localhost:5173` dev origin. Don't flip this without implementing a custom protocol handler as a replacement.
- `npm audit` reports `shell-quote` (transitive via `concurrently`) and `undici` (transitive via `electron-builder`'s `@electron/rebuild`/`node-gyp`, and via `jsdom`) advisories — both dev-only tooling, never shipped in the built app. Known, accepted risk; don't force-downgrade `concurrently` or otherwise "fix" these opportunistically.
- ~~Album art stored as full-resolution base64 in every track object~~ — **resolved** by the metadata-index/thumbnail architecture (tracks carry only a `sonus-thumb://` URL; full-res is on-demand for NP/Tag Editor). Don't reintroduce base64 into library track objects.
- Orphaned thumbnail files (tracks removed from the library, or art format changes leaving an old-extension file) are not garbage-collected — they're a few KB each in `userData/thumbs/`. Accepted; a cleanup sweep is a possible future follow-up, not a bug.
- Inter ships as `@fontsource/inter` (a devDependency — Vite inlines the CSS and emits the woff2 as hashed assets at build time, so nothing is needed at runtime). All **seven** subsets are bundled for the five weights, not just latin: the previous Google Fonts endpoint served them all via `unicode-range`, and bundling latin alone would silently drop Cyrillic and Greek track titles to the system font. Cost is ~520KB of woff2. `@fontsource` also references a legacy `.woff` per face, so ~680KB of never-loaded fallbacks ship too — Chromium always picks woff2. Accepted: ~0.14% of a ~500MB bundle, and stripping it would mean hand-maintaining 35 `@font-face` blocks or a fragile post-build rewrite.
- The packaged `app.asar` ships the ~320KB generated fixture MP3 and the `*.test.mjs` files (~14MB of its 25MB). **Deliberate, not an oversight** — it is exactly what lets the packaged app run its own `--smoke` suite on a target machine with no dev toolchain installed, which is how the Intel iMac gets machine-checked rather than eyeballed. A `files` exclude would save 14MB out of a 494MB bundle and cost on-device acceptance testing. Don't strip it without replacing that capability.
- The universal build is **unsigned and un-notarized** (no Apple Developer account). On Ventura the right-click → Open bypass still works, so it costs one extra click the first time on a given Mac. Note this bypass was removed in macOS 15 Sequoia, so a modern Mac needs System Settings → Privacy & Security → "Open Anyway" instead. `codesign --verify` fails strictly on the ad-hoc signature (`code has no resources but signature indicates they must be present`) — that is normal for electron-builder's unsigned output and matches the known-good baseline, which is why `verify-bundle.sh` reports it as info rather than asserting it.
- The `react-hooks/refs`, `react-hooks/set-state-in-effect`, and `react-hooks/immutability` ESLint rules are disabled in `eslint.config.js` — they're React-Compiler diagnostics, this project has no React Compiler, and the codebase's documented render-time mirror-ref idiom (`viewRef.current = view` etc.) is deliberate. Don't "fix" the idiom to re-enable them.
- ~~The packaged app's Dock/Finder icon sits on a light-grey plate~~ — **resolved**, and the earlier "accepted, needs an Xcode asset catalog" diagnosis was wrong. On macOS 26/27 the system decides from the icon's **alpha outline alone** whether to draw it as a modern icon or shrink it onto a grey plate: with Sonus's colours and another app's outline it is not plated; with Sonus's outline and another app's shadow it is. Size (824/1024 vs larger), a shadow, a rim, the Info.plist, the linked SDK and the `.icns` chunk layout all made no difference. A plain rounded square (circular corner arcs, radius ~190, the usual "squircle" recipe) is rejected even at the right size; a **superellipse |x|^5 + |y|^5 = 1**, 824px centred in the 1024 canvas, is accepted. `scripts/make-app-icon.py` builds `build/icon.png` + `build/icon.icns` from the opaque 824x824 art in `build/icon-art.png` — edit the art there, never the outputs, and keep the mask curve. How this was found, and how to re-check it without seeing the Dock: render the icon through macOS's own icon service (`NSWorkspace.iconForFile` on an ABSOLUTE path — a relative one silently returns a generic document icon — drawn into a bitmap via `osascript -l JavaScript`) and look at the PNG; a bundle with just an `Info.plist`, a `Resources/icon.icns` and a dummy executable is enough to test an icon variant in seconds, and the installed apps in `/Applications` are free comparison cases. Dock/Finder cache the old icon: after installing a new build, `killall Dock` (and `killall Finder`).

### Genuinely dead code (unlike everything above, this *is* safe to delete)

Almost all of this file argues that something which looks removable is load-bearing. The inverse is worth writing down too, so the next reader doesn't have to re-derive it by grep. All of the following are verified unreferenced:

- **CSS in `index.css`** — `.track-header-sort-chip` (left over from the deleted Sort dropdown), `.track-list-header-title` and `.track-list-header-meta` (the deleted Library identity line, whose *absence* the smoke suite asserts), `.np-text-block`, and `--np-slider-color` (read via `var()` but never set anywhere, so it always renders its hardcoded fallback gradient).
- **`src/MarqueeText.jsx`** — committed but imported by nothing. The player panel uses the inline `.marquee-scroll` class instead, so the shared `@keyframes marquee-scroll` can be changed without touching this file.
- A **stale comment block** immediately above `.track-list-header` still describes the deleted sticky/`--scrolled` header design; the correct comment follows right after it.

Deleting these is safe but optional — they cost nothing at runtime, since unused CSS rules and an unimported module are dropped or never loaded by the bundler.

## Working in this repo

- **README.md's Privacy section claims an exhaustive list of every outbound network call the app makes**: Search Online in the Tag Editor (iTunes Search API, MusicBrainz, Cover Art Archive, lrclib), Start Mix (MusicBrainz, ListenBrainz Labs, Deezer), and Search in YouTube (opens the browser). All three are user-initiated; nothing calls out on launch or in the background. If you add or change a network call anywhere in the app, update that table too — otherwise the README's "no telemetry, nothing sent unless you ask" claim silently becomes false.
- The current UI/UX (glassmorphism, colors, hover/drag effects, playback behavior) is considered intentionally finished — treat any visible or behavioral change as a regression unless the task explicitly calls for it. Glassmorphism depends on *all* of these together: the Electron window flags (`vibrancy: 'under-window'`, `visualEffectState: 'active'`, `transparent: true`, `backgroundColor: '#00000000'`), `nativeTheme.themeSource = 'dark'` in `main.js`, and the CSS (`body { background: transparent }`, `.glass-panel` `backdrop-filter`) — changing any one piece without the others breaks the look.
- **`test-fixture.mp3`** (repo root, ~320KB) is the audio file the smoke suite parses, tags, copies and re-opens — don't move, rename, or delete it. Make copies elsewhere (e.g. `/tmp`) for any test that needs to mutate it. It is generated, not a real song, because this repo is public: `node scripts/make-test-fixture.mjs` rebuilds it from MPEG-1 Layer III frame headers plus `scripts/fixture-cover.jpg`, using only `node-id3` (already a dependency — no ffmpeg needed). **Its 20-second length is load-bearing**: the suite seeks to 5s and then 7s and asserts the playhead landed there, so a shorter fixture makes those seeks clamp and fail for reasons unrelated to the behaviour under test.
- For *manual* listening tests (playback, marquee scrolling, lyrics, artwork colour) the fixture is 20 seconds of silence and therefore useless — keep a real track somewhere outside the repo for that.
- A plain Playwright/CDP screenshot of this app will render mostly blank/white — it can't capture macOS's vibrancy/transparency compositing. This is a known tooling limitation, not a visual regression; don't diff against headless screenshots as a correctness check. To verify visual changes: run `npm run dev`, then use `screencapture -x /tmp/sonus.png` (native macOS screenshot, which correctly captures vibrancy compositing). For pixel-level verification, use Python PIL (`from PIL import Image; img = Image.open('/tmp/sonus.png').convert('RGB'); img.getpixel((x, y))`). Retina displays produce 2× physical pixels, so logical coordinates must be doubled.
- This repo is published at **https://github.com/panawel/sonus-player** (MIT). Releases are built locally and attached to a GitHub Release — `release/` is gitignored, since the artifacts are ~224MB each and GitHub rejects files over 100MB. `.claude/settings.local.json` is gitignored too: it holds absolute paths from the developer's own machine. Before any commit that adds files, check that nothing personal or over ~1MB is staged.
