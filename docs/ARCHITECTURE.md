## Home view (`src/HomeView.jsx`, `src/HomeDetailView.jsx`)

The Home view is the first of the two title-bar tab destinations (see "Primary navigation" below). It shows: genre filter chips, decade filter chips, a library stats micro-line, a Featured Artist hero banner, Quick Picks grid, New Releases, Artists, and Albums horizontal card rows (with a Top Artists ranked sub-section beneath the Artists row). All data comes exclusively from the loaded library — no network calls.

**Section order:** Quick Picks → New Releases → Artists (+ Top Artists sub-section) → Albums → Songs by Year → Library Stats (Sound Quality + Completeness) → Languages.

**Always-mounted with `display: none` (critical performance constraint)**

`HomeView` is rendered unconditionally in `App.jsx` inside a wrapper div whose `display` toggles between `'block'` and `'none'` based on `view === 'home' && !homeDetailItem`. It is **never unmounted** while the app is running. This is load-bearing: base64 artwork images are decoded synchronously by the browser when their `<img>` elements enter the DOM; unmounting and remounting `HomeView` on every navigation would re-decode all visible artwork images on every visit. With always-mounted, that cost is paid exactly once (first visit). Do not change this to conditional rendering (`{view === 'home' && <HomeView />}`) — the freeze comes back immediately.

`HomeDetailView` (album/artist drill-down) is still conditionally mounted: it's a simpler component with no artwork grid, so its mount cost is negligible. Its track list is **virtualized** via `useVirtualizer` with its own inner scroll container (`overflowY: 'auto'`) separate from the shared `.scrollable` — the outer div has `overflow: 'hidden'` and `height: '100%'`. Scroll position is preserved via `savedScrollTop` / `onScrollChange` props + `initialOffset` on the virtualizer + a `useLayoutEffect` on mount.

**App.jsx state owned by the Home view:**
- `homeDetailItem` — `{ type: 'album'|'artist', key }` or `null`; drives which detail view is shown. Resets to `null` whenever `view` leaves `'home'`, **except** for `'now_playing'` — treated as a temporary overlay, so `homeDetailItem` is preserved through it so the back button returns to the correct detail view. (The Tag Editor is no longer a `view` value at all — see "Tag Editor" below — so it never entered into this reset logic in the first place.) The reset effect is: `if (view !== 'home' && view !== 'now_playing') { setHomeDetailItem(null); setHomeDetailOrigin(null); }`.
- `homeDetailOrigin` — stores which view the user was on before entering a HomeDetailView. Set by the player panel artist/album clicks (`setHomeDetailOrigin(view)` before navigating to Home). Set to `null` by HomeView card clicks (navigating from within Home). Used by `onBack` in HomeDetailView to return to the correct screen; passed as `backLabel` prop. Without this, the back button always returned to Home main regardless of where you came from.
- `playAllTracks(tracks, shuffle)` — callback passed to both `HomeView` and `HomeDetailView`. Sets `forcedNextQueueRef.current` to the remaining tracks after playing the first one, so the queue fills without touching library state.
- `isPlaying` — passed as a prop so `QuickPickRow` can render animated equalizer bars (`.eq-bar` CSS, `@keyframes eq-bounce`) over the current track's artwork thumbnail.

**Decade + genre filters:**
Both filters can be active simultaneously — `filteredLibrary` chains them. Decade chips appear in a second row below genre chips (both inside one always-rendered wrapper div; the decades chips were previously nested inside the `{genres.length > 0}` block — this was a bug, now fixed). The hero `useMemo` bypasses its filter-aware logic and uses the full `allArtists` pool when neither filter is active.

**Top Artists sub-section:**
`topArtists` (top 5 by track count from the current filtered artists, via `useMemo`) renders as `TopArtistsPanel` → `TopArtistRow` components directly inside the Artists section, after the horizontal card row. No glass wrapper — it's a sub-section, not a standalone panel. Requires ≥2 artists to show. Each row has an animated fill bar (width driven by `pct = tracks.length / max * 100`) that expands on mount via `setFilled(true)` in a `useEffect` staggered by `index * 75ms`.

**Library stats micro-line:**
`allAlbumsCount` and `totalDuration` are both `useMemo` values derived from the unfiltered `library` (same dep array as `allArtists`). The stats line (`N songs · N artists · N albums · Xh Ym`) always reflects the full library, not `filteredLibrary`. `formatDuration(sec)` is a module-level helper that formats seconds as `143h 12m` (or just `12m` if under an hour).

**Seeded PRNG (`mulberry32` + `seededShuffle`)**

Module-level helpers in `HomeView.jsx`. `mulberry32(seed)` returns a deterministic float in [0,1); `seededShuffle(arr, seed)` returns a new shuffled copy without mutating the input. Each shuffled section has its own `useState(() => Math.random())` seed — `quickPickSeed`, `albumSeed`, `artistSeed`, `releasesSeed`, `heroSeed`. Changing any seed triggers only that section's `useMemo` to recompute.

**Auto-refresh timers (HomeView):**
- **Hero**: `setInterval` every 8 seconds. On each tick, fades out (opacity 0, 300ms CSS transition), swaps `heroSeed`, fades back in. Pauses when the mouse is over the banner (`heroHoveredRef`).
- **Sections** (Quick Picks, Latest Releases, Artists, Albums): single `setInterval` every 60 seconds, rotating through the four sections in order. On each tick checks `isActiveRef.current` — skips silently if the user is not on the Home main screen (in Library, Now Playing, or a detail view; the Tag Editor is a separate `BrowserWindow` so it can never make this `false` by itself). Also checks `sectionsHoveredRef.current` — skips if mouse is over any of the four section wrappers. Same fade pattern as the hero. The `isActive` prop (`view === 'home' && !homeDetailItem`) is synced to `isActiveRef` via `useEffect([isActive])`, never put in the interval's dep array (mount-only `[]` avoids timer restarts on navigation).
- **`HomeView` is wrapped in `React.memo`** — prevents re-renders during `currentTime` ticks (which update App.jsx 4× per second during playback). All props passed to HomeView are stable: `playTrack`/`playAllTracks`/`onOpenDetail` are `useCallback`; `library`, `currentTrack`, `isPlaying`, `isActive` only change on meaningful events.

**Section caps and grid:**
- Quick Picks: 12 tracks, 4-column CSS grid (`repeat(4, 1fr)`, drops to 2 at ≤900px and to 1 at ≤460px)
- Library Stats: Sound Quality (`flex: 3`) and Completeness (`flex: 2`) sit side by side and **stack vertically at ≤560px** via `.home-stats-row` / `.home-stats-divider` in `index.css`. Below ~500px the donut legend's hard minimum widths (label ≥70px, count ≥22px, percent ≥30px, plus the fixed 180px donut) overflow sideways into the Completeness column — nothing in that chain clips — reading as jumbled overlapping text. 560 deliberately matches `NARROW_LAYOUT_BREAKPOINT`: one fewer number to keep in sync, and comfortably past where it actually starts.
- Albums / Artists / New Releases: `MAX_SECTION_CARDS = 20` each
- New Releases: sorts all albums by their most recent track year (descending), takes the top-30 as a recency pool, shuffles within that pool using `releasesSeed`, displays up to 20. This always fills the section regardless of library age — the section is meaningfully different from Albums (which draws from all albums randomly rather than the newest 30).

**`groupByAlbum` / `groupByArtist`** — module-level helpers in `HomeView.jsx`.

`groupByAlbum` groups tracks into `{ name, artist, year, artwork, tracks }` objects. Case-insensitive: Map key is `track.album.toLowerCase()`. Display name uses most-common casing variant across the group's tracks.

`groupByArtist` uses **token-based splitting** (see `splitArtists` below) — each track is added to *every* artist token group it belongs to. A track with `artist: "Inna & Bob Taylor"` contributes to both the "Inna" group and the "Bob Taylor" group. This means artist cards, Top Artists counts, and `allArtists` track counts all correctly reflect total appearances across solo tracks and collaborations. Case-insensitive grouping and most-common-casing display name resolution are preserved.

**`splitArtists(str)` — `src/audioUtils.js`**

Exported utility that splits an artist field into individual artist tokens by common separators: ` & `, ` and `, ` feat. ` / ` feat `, ` ft. ` / ` ft `, ` x ` (space-bounded — "Alex" is not split), `,`. Returns trimmed, non-empty strings. **Repeated-token rule:** if the split yields the same token twice (case-insensitive), the whole string is returned as a single artist — a real collab never lists the same artist twice, so repetition means the separator is part of the name (e.g. "Years & Years"; splitting it into duplicate tokens caused duplicate React keys → corrupted player-panel subtitle text, plus double-counted tracks in `groupByArtist`). Imported by `HomeView.jsx`, `HomeDetailView.jsx`, and `App.jsx`. Language-agnostic: works for Hebrew and other languages because music metadata internationally uses these English separators even for non-English content.

**`detectScript(title)` — `src/audioUtils.js`**

Exported utility that returns the dominant Unicode script of a track title: `'Hebrew'`, `'Arabic'`, `'Cyrillic'`, `'CJK'`, or `'English'` (catch-all for Latin and any title with no letter characters). Iterates every character, skips non-letters (`\p{L}`), tallies by codepoint range (Hebrew `0590–05FF`, Arabic `0600–06FF`, Cyrillic `0400–04FF`, CJK `4E00–9FFF` / `3040–30FF` / `AC00–D7AF`, everything else → English), returns the script with the highest count. Tie-breaks toward whichever came first in the sort. Used by `HomeView.jsx` (`scriptData` useMemo) and `HomeDetailView.jsx` (`type: 'language'` track filter).

**Languages section (HomeView):**
`scriptData` useMemo groups `filteredLibrary` (genre+decade filtered) by `detectScript(t.title)`, sorted by count descending (highest % first). Only shown when ≥2 distinct scripts are present. Rendered as a `LanguageDonut` component — same `donutSlice` / `polarToCart` SVG helpers as `DonutChart` (Sound Quality). `LANG_COLORS` map assigns fixed colors per script (`Hebrew: '#a855f7'`, `English: '#4facfe'`, `Arabic: '#10b981'`, `Cyrillic: '#f59e0b'`, `CJK: '#ef4444'`). Clicking a segment or legend row navigates to `onOpenDetail({ type: 'language', key: script })` — it does not filter in place.

**HomeDetailView artist filter** uses token matching: `splitArtists(t.artist).some(a => a.toLowerCase() === item.key.toLowerCase())`. The `item.key` is always a single artist token (never a compound string like "Inna & Bob Taylor") — the player panel click handler extracts `splitArtists(currentTrack.artist)[0]` as the key so it always navigates to the primary artist's page.

**Hero banner:**
Picks via `seededShuffle(eligibleArtists, heroSeed)[0]` where eligible = artists with ≥2 tracks (falls back to all artists). When a genre filter is active, prefers an artist present in the filtered set; falls back to the most-tracked filtered artist. No manual Refresh button — the hero auto-rotates every 8 seconds (see Auto-refresh timers above). The banner has `onHoverChange` prop that sets `heroHoveredRef.current` to pause rotation while the user's mouse is over it.

**Horizontal card row two-div split (load-bearing — do not collapse back to one div):**

Each card row is split into two elements:
- **`.home-card-row-outer`** — the scroll container (`overflow-x: auto`, `scroll-snap-type: x mandatory`, `padding: 20px 12px 48px`, dynamic `mask-image`). The `ref` for scroll-button logic and `onScroll` for fade state live here.
- **`.home-card-row`** — the inner flex row (`display: flex`, `gap: 16px`, no overflow). Cards live here.

This split is required because CSS spec forces `overflow-y: auto` whenever `overflow-x: auto` is set (they cannot be mixed with `visible`). Without the split, `transform: scale(1.05)` on hovered cards is clipped at the container boundary on all four sides — the hover scale looks like it hits a wall. The outer's `padding: 20px 12px 48px` provides the actual clipping boundary room: 20px/48px contain the card's `box-shadow: 0 10px 36px` (extends ~18px above, ~46px below), and 12px each side contains the ~3.5px horizontal scale of the first/last card.

**`getFlushTarget`** reads `el.firstElementChild.children` (cards inside the inner div), not `el.children` (which is just the one inner div). Using `el.children` directly would give wrong `getBoundingClientRect` positions.

**Dynamic fade mask (`scrollFades` state, `getFadeMask`, `updateFade`):**
Three fade states per row (`albums`, `artists`, `releases`) stored in one `useState` object. `updateFade(key, el)` computes `atStart = el.scrollLeft <= PAD` and `atEnd = el.scrollLeft + el.clientWidth >= el.scrollWidth - PAD` (where `PAD = 12` matches the horizontal padding). `getFadeMask` returns a gradient offset inward by `PAD` so the fade zone starts at the card edge, not the container edge — preventing the left fade from clipping the first card when scrolled slightly. States: `'right'` (at start), `'left'` (at end), `'both'` (middle), `'none'` (all content fits). Initialized to `'right'` (correct default since all rows start unscrolled).

**HomeDetailView:**
Receives `{ type, key }` and filters `library` to matching tracks. Shows a hero (large square artwork with an ambient glow behind it, a title/subtitle block, and Shuffle + Play buttons — see "Detail hero redesign" below for the current premium treatment, a later pass over what was originally a plain fixed-160px side-by-side row), subtitle line (artist · year · N tracks · duration), and a virtualized scrollable track list. `playAllTracks` is the same callback from `App.jsx` — the Play button's label reads "Play" now, not "Play All", but it's still literally `playAllTracks` under the hood; nothing about the underlying queueing mechanism changed, only the button's own text and styling. No IPC calls — pure renderer computation.

Supported `type` values: `'album'`, `'artist'`, `'year'`, `'bitrate'`, `'missing-metadata'`, `'language'`, and `'mix'` — the last is the only one that isn't a synchronous filter over `library`; see "Mix" below.

`type: 'language'` — filters with `detectScript(t.title) === item.key`, sorted by artist then title. Hero is a **2×2 mosaic grid** of up to 4 unique track artworks (deduplicated by thumb URL, first-come order); empty cells show a faint `Music` icon. Type label reads "Language"; title reads the script name (e.g. "Hebrew").

Accepts a `backLabel` prop (default `'Home'`) that drives the back breadcrumb label. When opened from the player panel artist/album links, `backLabel` reflects the origin view ("Library", "Now Playing", etc.) and `onBack` returns to that view instead of Home main.

The detail track list is the same unified `<TrackList>` engine the Library uses (see "Tracklist engine"), configured with no drag, per-open sort (`useTrackSort` with `resetKey` = the item identity), its own `useTrackSelection`, and `showAlbum={item.type !== 'album'}` (the Album/Year column is hidden inside a single album's page). `HomeDetailView` owns the inner scroll container (`innerScrollRef`), passes it as `scrollElRef`, and renders `<TrackListHeader>` **itself, above** that container (`TrackList` never renders the header — see "The column header lives OUTSIDE the scroll container"), plus `initialOffset={savedScrollTop}` for scroll restoration. It registers its selection into App's `activeSelectionRef` via an every-render effect so Cmd+A routes to it while open.

### Detail hero redesign

A later pass, inspired by a reference screenshot the user shared of an Apple Music-style album detail screen — deliberately adapted, not copied: several of the reference's elements (a "+" add button, an editorial description blurb, Dolby Atmos/Lossless format badges) have no real Sonus feature behind them and were dropped rather than fabricated, and the reference's own right-side vertical nav rail was left alone entirely since nav placement is app-wide, out of scope for a Details-screen-only change.

**Went through three real iterations, not one.** (1) A bounded, padded artwork card (rounded square, a soft ambient glow behind it) sitting *above* a separate text block. (2) The user pushed back after seeing it live: in the reference, the photo is the hero's own full-bleed background with text overlaid via a gradient — so the card became edge-to-edge, with a dark gradient scrim fading it toward black for text legibility. (3) The user pushed back *again*, this time from an actual screenshot: the "gradient" rendered as a hard dark band with a visible seam, not a blend — because the surface behind this page is light artwork-tinted glass, not black, so fading *toward black* creates a new edge instead of removing the old one. Two more real problems showed up in that same screenshot: the full-width hero column was a tall narrow pillar (360px capped, ~970px tall — a 0.4 aspect ratio slicing up a square cover), and there was a hard 40px gutter between the hero and the tracklist instead of the reference's seamless one-surface look. All three are fixed in the version described below; the dark-gradient-scrim version described in an earlier draft of this section no longer exists.

**Two structurally different layouts, chosen by `isNarrowLayout` (`useIsNarrow(NARROW_LAYOUT_BREAKPOINT)`, its own subscription here — `NARROW_LAYOUT_BREAKPOINT` moved from being App.jsx-only into `trackUtils.js` alongside the other shared breakpoints specifically so this component could import the same number without a second hardcoded `560`):**
- **Narrow** — a fixed-height band at the top (`height: clamp(280px, 45vh, 460px)`), the background image filling it, masked to transparent toward the bottom (see below) so it dissolves into the panel rather than cutting off. Title/subtitle/Shuffle+Play sit centered in that faded lower zone. The tracklist continues below in normal flow, unaffected.
- **Full-width** — the hero content column (`HERO_WIDTH_WIDE = clamp(260px, 35%, 520px)` — narrower than the first iteration's `32%/360px cap`, the tall-pillar problem's actual fix) sits over an image layer that's *wider than the column itself* (`+ HERO_OVERLAP_WIDE`, 16px) and masked to fade out over its own right `HERO_FADE_WIDE` (200px) — so the image visibly runs *under* the start of the tracklist column and dissolves there, instead of stopping at the hero column's own edge with a gap after it. The tracklist column has no left gutter of its own beyond a small `paddingLeft: 24` — the fade itself is what visually separates the two, not empty space. **`HERO_OVERLAP_WIDE`/`HERO_FADE_WIDE` are deliberately tuned against `HERO_TRACKLIST_PAD_WIDE`'s own 32px, not picked independently** — see the dedicated paragraph below; the original numbers (120/280) left the image still genuinely visible, not just structurally present, at the exact point the tracklist's own text renders.

**The hero reaches `.glass-panel`'s own top/left(/right) edges flush because `App.jsx`'s `.scrollable` has no padding to escape while a Home detail item is open — not via a negative margin on this component's own side.** A negative margin was the original approach, and it's a real, previously-undetected bug: **discovered and fixed**, worth understanding since it's a genuine category of failure, not a one-off mistake.

**The bug:** `.scrollable` (`App.jsx`) is `overflow-y: 'auto'` — a genuine *scroll port*, not just static `overflow: hidden`. Per the CSS overflow spec, setting `overflow-y` to anything but `visible` forces `overflow-x` to also become non-visible (confirmed: its computed `overflow-x` is `'auto'` even though only `overflow-y` was ever authored). Worse, for an actual scrolling container specifically, content pulled above/before the container's own scroll origin via negative margin isn't just clipped — it's permanently unreachable, because `scrollTop`/`scrollLeft` can never go negative. The hero's negative-margin bleed (`margin: '-16px -16px 0'` narrow, `'-32px 0 0 -32px'` full-width, canceling `.scrollable`'s own padding) fell exactly into this trap: it *looked* correctly positioned by every check this whole redesign had used so far — `getBoundingClientRect()` reports an element's own layout box, which is unaffected by an ancestor's overflow/scroll clipping, so a bled element can report "flush with the panel" while its actual *painted* pixels are clipped away. Caught only by `document.elementFromPoint()` (which returned `.scrollable` itself at the hero's own supposed corner, instead of the hero) and real pixel sampling with a solid-color test image (a 16-17px band that was actually `.scrollable`'s own padding color showing through, not artwork) — the same category of blind spot as the rounded-corner and native-traffic-light bugs below, a **third** distinct cause, this time in the app's own CSS rather than OS chrome.

**The fix:** stop fighting the scroll port — remove what the hero needs to escape, instead of trying to escape it via negative margin. `App.jsx`'s `.scrollable` padding becomes `0` on **every** side specifically when `view === 'home' && homeDetailItem` (bottom joined top/left/right in a later fix below — at the time of this fix it was still `0 0 <bottom-clearance>`, since bottom was never negative-margined and wasn't part of *this* bug). With nothing to escape, the hero renders at its own natural `(0, 0)` origin and is already flush — no negative margin, no compensating height math. `HomeDetailView` adds its own padding back around *only* the tracklist (`HERO_TRACKLIST_PAD_NARROW`/`_WIDE`, 16/32 — matching what `.scrollable`'s own padding used to be, so the tracklist's own position is visually unchanged from before this fix; only the hero is new edge-to-edge territory):
- **Narrow**: the hero band is a plain, non-negative-margined `flexShrink: 0` box; the tracklist wrapper below it gets `padding: '0 16px'`.
- **Full-width**: the image layer is `position: absolute; top: 0; left: 0; bottom: 0; width: calc(HERO_WIDTH_WIDE + HERO_OVERLAP_WIDE)` (no more `-HERO_BLEED_WIDE` offset or matching width increase); the hero content column is a plain flex child, `width: HERO_WIDTH_WIDE; height: '100%'` (no margin, no `calc(100% + bleed)` compensation — that whole trick existed only to counteract the negative margin's side effect, which no longer exists); the tracklist column keeps its `paddingLeft: 24` and now also needs an explicit `paddingRight: HERO_TRACKLIST_PAD_WIDE` (32), since `.scrollable`'s own right padding — which used to supply it — is also gone.

Reverified the same way the bug was found: `elementFromPoint()` at each edge now hits the hero's own layers (not `.scrollable`), and pixel sampling confirms solid, opaque color reaching every non-fading edge with no gap — narrow's top/left/right, full-width's top/left, both. (A first re-check at the wrong y-coordinate briefly looked like the fix hadn't worked for narrow's left/right — it had; the sample point had landed just below the hero, in the tracklist's own new 16px padding, not a real bug. Worth remembering: always double check a coordinate is actually inside the region being tested before trusting a "still broken" pixel read.)

**A fourth bug, found later: `.scrollable`'s bottom padding was reserving pill clearance a second time, on top of `TrackList`'s own `bottomPadding`, silently shrinking the tracklist's own scrollable area.** The fix above deliberately left `.scrollable`'s bottom padding alone (`0 0 <bottom-clearance>`) since it wasn't part of the negative-margin bug — but it turned out to be a second, related bug on its own, reported by the user as the tracklist looking "cut off" and not extending "behind the Player and the way down, just like in the Library list." Root cause: `HomeDetailView`'s own top-level wrapper is `height: '100%'`, and a percentage height resolves against the *content box* of its parent (`.scrollable`) — i.e. after `.scrollable`'s own padding is subtracted. With `.scrollable`'s bottom padding still carrying `<bottom-clearance>` (~89-121px depending on width), `HomeDetailView`'s entire available height was silently reduced by that amount — on top of the *same* clearance `HomeDetailView` already reserves internally via `TrackList`'s own `bottomPadding` (see "Scroll clearance for the floating pill" below), a genuine double reservation. Confirmed live via geometry, not bounding rects alone: with a synthetic 40-track library, `HomeDetailView`'s own inner scroll container (`innerScrollRef`) ended at `y=678` in an 800px-tall window — ~120px short of the true bottom — even though scrolling *that* container to its own max worked correctly in isolation. Library never has this problem because it never applies pill clearance via `.scrollable`'s CSS padding at all (see the same section below) — `TrackList`'s own `bottomPadding` is Library's *only* source of clearance, and its single, un-nested scroll container (`.scrollable` itself) therefore extends flush to the window's true bottom, letting rows visibly slide underneath the floating pill. `HomeDetailView`'s nested scroll container (necessary because the hero, in full-width layout, sits beside the tracklist rather than above it in one linear flow — it can't just reuse `.scrollable` as its own scroll port the way Library does) was stopping short of that same bottom edge instead, because of the duplicate reservation. **The fix:** `.scrollable`'s padding for the home-detail case is now `'0'` outright — bottom joins top/left/right. `TrackList`'s own `bottomPadding` (already correctly wired to the same `bottomClearance` prop) is left as the sole source of clearance, exactly matching Library's pattern. Reverified the same way: with the fix, the inner scroll container's own bottom now lands at the window's true edge (`y=799` of 800, both widths), and scrolling it to its own max puts the last row's own bottom edge `<bottom-clearance>`-worth of pixels above that edge — matching Library's behavior instead of stopping early.

**Hero background** — a real photo (`<img>`, `position:absolute; inset:0; object-fit:cover`) for every type with real artwork; the language type's mosaic becomes a full-bleed 2×2 image grid instead of a small bounded one; and — no artwork at all (Year/Quality/Missing-metadata/Mix-before-ready, or a language mosaic with zero found thumbs) — a plain dark gradient (`linear-gradient(160deg, var(--glass-active), rgba(0,0,0,0.6))`) with the type's existing fallback icon (`Calendar`/`Headphones`/`AlertCircle`/`Sparkles`/`Music`) centered in it (`size: 72`, dimmed via `opacity: 0.35`) — confirmed with the user: the hero's own shape/size should stay consistent whether or not there's a real photo.

**A real bug: the image was still genuinely *visible*, not just structurally present, at the exact point the tracklist's own text rendered — caught only once the user saw it live and flagged it as the tracklist "overlapping" the artwork.** The math looked reasonable on paper (that's exactly why it shipped): `HERO_FADE_WIDE` (originally 280) is measured from the image layer's *own* right edge (`HERO_WIDTH_WIDE + HERO_OVERLAP_WIDE`, originally `+120`) — but the tracklist's actual text starts much earlier than that, at `HERO_WIDTH_WIDE + HERO_TRACKLIST_PAD_WIDE` (only `+32`, minus a few px of the column's own `paddingLeft: 24`). The fix re-anchors both constants to `HERO_TRACKLIST_PAD_WIDE` itself instead of treating them as independent: `HERO_OVERLAP_WIDE` (now 16) stops the image comfortably *before* the tracklist's own 32px padding (leaving an 8px buffer with neither image nor text), and `HERO_FADE_WIDE` (now 200) is sized so the fade actually *reaches* fully transparent by that point, not just gets most of the way there. The DOM structure is otherwise unchanged — still one continuous image layer running under the start of the tracklist column, still no gap in the layout — only the pixel where it visually finishes moved earlier. **Verified with real pixels, not the arithmetic alone** (the arithmetic was what produced the bug in the first place): a solid-color test thumbnail, sampled across the seam — confirmed fully transparent (matching the background exactly, no partial color) a clear 8px before the tracklist's own text-start x-coordinate, at every point checked.

**The fade is a CSS `mask-image` to transparent, not a gradient painted over the image — this is the actual fix for the "hard dark band" bug.** A wrapper around the background layer gets `WebkitMaskImage`/`maskImage` (the same inline pair `PlayerPill`'s marquee text fade already uses — inline styles aren't minified, so this doesn't risk the `-webkit-` prefix collapse `CLAUDE.md` warns about for `backdrop-filter`). Masking to transparent lets whatever's actually behind the hero show through — the same glass surface the tracklist sits on — so image and tracklist read as one continuous surface with no seam, regardless of what that surface's actual color is. A gradient *painted over* the image (an earlier version) can only ever fade toward whatever color you pick, which only blends correctly if that color happens to match the real backdrop — it didn't. **Verified with real pixels, not just geometry** — an earlier draft of this section only ever checked element positions/sizes (this sandbox can't render the app's real vibrancy colors), which is exactly how the dark-band bug shipped without being caught. Now: a synthetic solid-red test thumbnail, captured via `webContents.capturePage()`, sampled with PIL at increasing distance into the fade — confirmed the red channel drops smoothly to nothing with no dark plateau in between, on every edge.

**Only the edge(s) that serve a real purpose fade. Every other edge is fully opaque, flush with the hero's own bounds — no decorative vignette.** This went through a brief detour: a version of this did fade all four edges (a `mask-composite: 'intersect'` stack of four gradients, a lighter vignette on the three non-primary edges layered under the original deep primary-edge fade) at the user's own request. Seeing it live, the user reconsidered — the reference itself doesn't fade those edges either, and the transparency read as unwanted "free space" (revealing the background through the image) rather than more artwork. Reverted to a single-gradient `heroMask` in narrow (`linear-gradient(to bottom, black 45%, transparent 100%)`) — only the edge actually blending into other content fades; everything else fills its frame completely.

**Full-width needs two fades, not one — a real omission the vignette-removal briefly introduced, caught once the user compared it against the reference again.** Narrow's single fade (toward the bottom) happens to serve *two* purposes at once: it blends into the tracklist below, *and* it sits right where narrow's own eyebrow/title/subtitle/Shuffle+Play text is anchored, so that text gets a darkened backdrop for legibility "for free." Full-width's one fade faces a *different* direction (right, toward the tracklist) than where its own text is anchored (bottom) — so reverting to "only the tracklist-facing edge fades" for full-width left its text sitting directly on the raw, un-faded photo with nothing behind it but a `text-shadow`. `heroMask` in full-width is therefore two gradient layers combined with `mask-composite: 'intersect'` (the same technique the four-edge vignette used, here for a genuine functional reason instead of decoration): the existing right-edge fade (`HERO_FADE_WIDE`, unchanged) plus a new bottom fade, `HERO_TEXT_FADE_WIDE` (300px) — a **fixed pixel depth**, not a percentage of the hero's own height the way narrow's fade is, since full-width's hero can be considerably taller than narrow's and a percentage-based fade there would cover far more than the actual text block needs. Verified with real pixels: solid red (a test thumbnail) stays fully opaque through the upper ~2/3 of the hero, then fades smoothly to near-transparent over the bottom `HERO_TEXT_FADE_WIDE` — comfortably covering the whole text block, including its Play button — while the separate right-edge fade (checked at a Y position within the still-opaque zone) is unaffected by the new bottom layer.

**The full-width text block clears the floating player pill — a real overlap, found while checking the mini player's in-between window heights, and present at every height.** The hero's eyebrow/title/subtitle/Shuffle+Play block was anchored 32px up from the bottom, but the full-width pill (centered, up to 644px wide, its top edge 75px above the window bottom) reaches left under this 35%-wide column whenever the window is narrower than about **1250px**, so at ~1000px it sat on top of the Play button by 42px (measured via `getBoundingClientRect()` across 600 to 1728px wide; at 1250px and up there is no overlap since the pill starts to the right of the column). The full-width text block's bottom padding is now `bottomClearance` — the same 89px (`PLAYER_PILL_CLEARANCE`) `TrackList`'s own `bottomPadding` reserves so its last rows clear the pill — which leaves Play 14-15px above the pill's top edge at every width and height tested (600×800 to 1728×900, down to 440px tall, with a two-line title). It applies at **all** widths rather than only below 1250px so the button's position never jumps as the window is dragged across that line; on wide windows that is simply higher than strictly needed. `HERO_TEXT_FADE_WIDE` went 240 to 300 to keep the bottom fade covering the 57px-taller block. Narrow's hero is at the top of the page, nowhere near its pill, so it keeps its own 20px. Guarded by a smoke-suite check at 1000px wide (Play does not intersect the pill, 8px minimum gap).

**Overlay content, layered above the masked image:** the back button (floating top-left) and the eyebrow/title/subtitle/button row (centered, anchored low) — `zIndex: 2`, `position: absolute` within the same `position: relative` hero box the image sits in.
- **Text uses `--chrome-text`/`--chrome-text-dim`** (white) instead of the page's usual `--text-secondary`/`--text-primary` — the same pair Now Playing already uses for text on a photo/blurred backdrop (see "Chrome text colors" below) — plus a soft `text-shadow` (`0 1px 2px rgba(0,0,0,0.5), 0 2px 16px rgba(0,0,0,0.45)`) for the stretches of the fade where the surface behind the text is bright.

Label kept (names the actual return destination — "Home", "Library", "Now Playing" — a deliberate earlier choice, confirmed again here rather than switching to an icon-only button like the reference's own).

**Two real, distinct bugs at this same corner — and a hard limit on what this sandbox can ever verify about the second one.**

**The hero upgrades to full-resolution artwork on demand — a real quality bug, caught from the same on-screen screenshot as the corner-clip one above.** Library track objects only ever carry a small ~300px thumbnail (`thumb`); full-res artwork is deliberately kept out of renderer memory otherwise and fetched via `fs:readArtwork` IPC only when something actually needs it (see "Metadata index, thumbnails" below) — until this fix, Now Playing and the Tag Editor were the only two consumers. ## Mix ("Start Mix" recommendations)

A "Start Mix" entry in the track context menu (single-track only, `src/App.jsx`) opens `homeDetailItem = { type: 'mix', key: track.filePath, label: track.title || track.artist }` — same `openHomeDetail`/`setHomeDetailItem` path every other detail type uses, so navigation, the back-chevron, scroll-position caching, and the "Playing from" breadcrumb (see [`queueSource`](#playing-from-breadcrumb-queuesource) below) all work for it automatically with zero Mix-specific code at the App.jsx level beyond the menu item itself and one label lookup (`detailItemLabel`, since `key` is a filePath here, not human-readable like every other type's `key`).

**All three data sources are free and keyless** — verified live against real data before committing to this design, not assumed: MusicBrainz (already used by Tag Editor's Search Online) resolves a track/artist name to MusicBrainz IDs; ListenBrainz Labs (`labs.api.listenbrainz.org`, a sibling MetaBrainz project, same keyless philosophy) returns similar recordings/artists for those IDs; Deezer's public API (`api.deezer.com`) is a second, independent similar-artists source. No API key, no account, for the app or for anyone running it — see `useMix.js`'s header comment for the exact endpoints and the required (fixed, non-configurable) `algorithm` query parameter each ListenBrainz Labs endpoint demands.

**Two-tier matching** (`src/mixMatch.js`, pure and unit-tested, mirrors how `tagSearch.js` already works for Search Online):
1. **Song-level** (tier 1) — MusicBrainz recording search → ListenBrainz `similar-recordings` for that exact recording MBID. High precision when it has data, but coverage is real-world-listening-dependent: a current mainstream hit returns rich results, an obscure or older track often returns nothing. Never treated as the only source because of this.
2. **Artist-level** (tier 2, the reliable fallback/widener) — the recording search's own `artist-credit` already embeds the artist's MBID (one MusicBrainz call typically resolves both IDs at once), so ListenBrainz `similar-artists` and Deezer's `/artist/{id}/related` run in parallel off it. Their artist-name results are merged and de-duplicated (`mergeArtistNames`, case-insensitive, keeps first-seen casing) before being matched against the library, and capped per-artist (`matchArtistsToLibrary`'s `perArtistCap`, default 4) so one deep-catalog similar artist can't dominate the whole mix.

`buildMix` combines both tiers, ranks tier 1 by the API's own relevance score, appends tier 2 after, de-duplicates, drops the seed track itself, and caps the total (default 40).

**`useMix.js`** owns the actual fetch/cache/state-machine, returning `{ status, tracks, retry }` where `status` is `'idle' | 'loading' | 'ready' | 'empty' | 'error'`. `HomeDetailView.jsx` calls it unconditionally (`const mix = useMix(item, library)`) alongside its existing synchronous per-type filtering — the hook itself no-ops (`status: 'idle'`) for every non-`'mix'` item type, so this is safe regardless of which detail page is open.

**`'idle'` is a real, reachable status, not just a theoretical initial value — treat it exactly like `'loading'` everywhere.** Even on a guaranteed cache hit, the cache lookup only happens inside `useMix`'s effect, which fires *after* the first render — so there is always one render where `status` is still its `useState` initial value. `HomeDetailView`'s hero (title/kicker) doesn't depend on the fetch at all (`item.label`/`'Mix'` are available immediately), so it looks identical whether the mix is actually ready or hasn't started resolving yet. Two places had to explicitly fold `'idle'` into the loading branch to avoid a one-frame flash of "Based on X · 0 tracks" (a real bug, caught and fixed during this feature's own smoke-test development, not a hypothetical): the subtitle text and the loading/empty/error placeholder that replaces the tracklist.

**Caching is in-memory only** (`useMix.js`'s module-level `mixCache` Map, keyed by `artist::title` lowercased) — cleared on relaunch, never persisted. Matches the deliberate "nothing about a Mix is ever saved" design: it's not a new kind of object, just another computed lens over the library, exactly like an Artist or Album page, regenerated fresh whenever reopened rather than remembered.

**Smoke-test coverage never touches the real APIs** — `window.__sonusTest.seedMixResult(seedTrack, tracks)` (mirrors `__sonusTagEditorTest.openSearchResults` for Search Online) writes directly into `mixCache`, so the suite drives every UI state (ready, empty, the Play All → breadcrumb round trip) off a synthetic result.

**A genuinely non-obvious smoke-test gotcha, worth remembering for any future test that injects fake library tracks:** `App.jsx` has a "on window focus, batch-check every library path via `checkPaths` and silently remove whatever's missing" effect (see the fails-silently table in `CLAUDE.md`). A real window-focus event is entirely plausible mid-suite, and it doesn't care which track is currently playing — it validates the *whole* library. The Mix smoke test originally seeded fake, non-existent filePaths for its library fixture; only the one actually pushed through `<audio>` (via Play All) visibly failed at first, but *all three* fake entries were vulnerable to this same cleanup and intermittently vanished depending on exactly when focus fired relative to the test's own timing — a failure that reproduced reliably in the full suite but not in any smaller standalone repro, because a lone `electron script.mjs` invocation doesn't generate the same focus-event traffic a 25-plus-test run does. Fixed by making every library entry point at a real file (a copy of `test-fixture.mp3` for the two that are only matched-and-listed, never actually played).

## Scroll position preservation across views (`App.jsx`)

All views share a single `.scrollable` scroll container. Positions are preserved across navigation via `scrollPositionsRef` (a `useRef({})` map of `view → scrollTop`).

**Three load-bearing constraints:**

1. **Save on `onScroll`, never in cleanup.** The `.scrollable` div's `onScroll` handler writes `scrollPositionsRef.current[view] = e.currentTarget.scrollTop`. A `useLayoutEffect` cleanup that reads `scrollTop` is wrong: setting `display: none` on a child collapses the element's `scrollHeight`, clamping `scrollTop` to 0 before cleanup runs, so the saved position is always 0.

2. **Two separate `useLayoutEffect` restores.** One fires on `[view]` change (handles all view switches). A second fires on `[homeDetailItem]` change (handles the back button from a detail view) — because `view` stays `'home'` the entire time the detail view is open, the `[view]` effect never fires on back-navigation. The `onScroll` handler guards against overwriting the home position while the detail view is open: `if (!(view === 'home' && homeDetailItem)) { scrollPositionsRef.current[view] = ... }`.

3. **`showLibraryRef` pattern for `scrollToTrack`.** `scrollToTrack` is a `useCallback` that calls `rowVirtualizer.scrollToIndex` inside a `setTimeout`. It must not add `view` to its dependency array (causes re-creation on every navigation). Instead, `showLibraryRef.current = showLibrary` is set each render; the `setTimeout` callback reads the ref. Without the guard, `scrollToTrack` (called on track advance/autoplay) would fire `rowVirtualizer.scrollToIndex` even when the Home view was visible, resetting its scroll position.

## Tracklist engine (`TrackList.jsx` + `TrackRow.jsx` + `TrackListHeader.jsx` + hooks)

One unified engine renders both the Library and every HomeDetailView track list — they are two configurations of the same `<TrackList>` component. Pieces:

- **`trackUtils.js`** — single source for `formatTime` (row semantics: `--:--` for missing), `ROW_HEIGHTS`/`ART_SIZES` (compact 44/30, comfortable 56/40), `SORT_FIELDS` (title/artist/album/duration/year/genre — `bitrate` was added alongside year/genre and later removed again, see "Library's extra columns" below), `COLUMN_CYCLES` + `nextInCycle` + `activeFieldForColumn` (see "Column-cycle sorting"), `compareBy` (locale-aware, numeric-aware, missing values always last in *both* directions, stable), `sortTracks` (`'manual'` returns the input array untouched), and `LIBRARY_EXTRA_COLUMNS` + `displayValueForColumn` (Library-only extra columns, below).
- **`useTrackSort.js`** — `{ sort, cycleColumn, setManual, sorted, isManual }`. `cycleColumn(columnId)` advances that column's cycle. `storageKey` persists to localStorage (Library: `'sonus.librarySort'`); `resetKey` snaps back to manual when it changes (Details per-open reset). `readStored` validates against the current `SORT_FIELDS`, so a persisted field that no column can reach falls back to manual instead of stranding the user.
- **`useTrackSelection.js`** — Set-based selection over the *displayed* array: macOS click semantics (plain/cmd/shift), keyboard cursor (`moveFocus`/`focusIndex`), `selectAll`/`clear`/`prune`. Deliberately does **not** auto-prune when `tracks` changes — hiding rows behind a search must not drop their selection; `removeTracks` calls `prune` explicitly.
- **`TrackRow.jsx`** — config-driven row: leading cell (grip in drag mode / 1-based index otherwise), artwork with overlay (EQ bars while the current track plays un-hovered, Play/Pause icon on hover; clicking toggles without selecting), **combined adaptive cells** (Title/Artist stack — the sorted field becomes the bold primary line, so sorting by artist promotes artist; the Album/Year stack, used only when `showAlbum` is true, never flips — it's a separate code path from Library's own Year column, below), `Mic2` lyrics indicator, and then either a duration⇄⋮ cell where both are always mounted and crossfaded (zero layout shift) — every caller except Library — or Library's own `extended` layout (below). Also exports `DraggableTrackRow`, the *only* place `useSortable` is called — rows outside a DndContext never touch dnd hooks.
- **`TrackListHeader.jsx`** — the hairline column line (`.track-list-header`). Rendered by the layout owner **above its scroll container, never inside it** — see "The column header lives OUTSIDE the scroll container" below, which is the single most important constraint in this area. **There is no Sort chip or dropdown** — sorting is driven entirely by clicking a column label, which walks that column's cycle (see "Column-cycle sorting"). A leading spacer stands in for the row's index + artwork cells so every label sits over the column it sorts.
- **`TrackList.jsx`** — rows only; it deliberately does **not** render the header (see below). Owns the `useVirtualizer` (fixed `estimateSize` per density, `overscan: 10`, **no `measureElement`** — rows are fixed-height), keyboard handling on a focusable container (↑/↓ nav, Shift ranges, Home/End, Enter plays, Delete/Backspace removes via `onRemoveTracks`, Escape clears; ←/→ deliberately fall through to the global seek), and mounts `DndContext`/`SortableContext` **only when `canDrag`**.

**`showAlbum` prop** (default `true`, threaded through `TrackList`/`TrackListHeader`/the `scrollMargin` measurement effect) hides the combined Album/Year *stacked* cell entirely when `false`. The Library passes `showAlbum={false}` — that stacked cell was deliberately removed from the Library screen in favor of the separate flat Album/Year/Genre columns below. `HomeDetailView` passes `showAlbum={item.type !== 'album'}` (see "Home view" above) — hiding it only when already inside a single album's own page where an Album column would be redundant. This prop and `extraColumns` (below) are independent and never both active on the same screen.

**Library's extra columns (Album/Year/Genre — `App.jsx` + `TrackRow.jsx` + `TrackListHeader.jsx` + `trackUtils.js`).** Only the top-level Library instance of `<TrackList>`/`<TrackListHeader>` passes an `extraColumns` prop (`HomeDetailView`'s own instances never do, so they're unaffected by any of this). `extraColumns={null}` (the default everywhere else) keeps `TrackRow`'s classic layout — lyrics indicator, then a single duration⇄⋮ crossfade cell — completely untouched; passing an array (even an empty one, at narrow widths) switches `TrackRow` and `TrackListHeader` to `extended` mode:
- Row order becomes: …Title, lyrics indicator, **Duration as its own always-mounted flat column**, the extra columns, then a **standalone ⋮ button pinned at the very end**, visible on hover only — Duration and ⋮ no longer share one crossfading slot the way they do everywhere else, because Duration had to move earlier in reading order (next to lyrics) while ⋮ stays a trailing "row action," not a column.
- `LIBRARY_EXTRA_COLUMNS` (`trackUtils.js`) is the single source of truth for id/label/width-or-flex/alignment, in order: `album` (flex), `year` (fixed width, right-aligned, tabular-nums), `genre` (flex). That order is *both* the left-to-right render order and the right-to-left hide order — `App.jsx` slices the array from the front as the window narrows, so the last entry is always the first to disappear. A `bitrate` column briefly existed as the second entry (fixed-width, right-aligned like Year) and was removed at the user's request after it shipped; nothing about the mechanism assumes a fixed column count, so removing one was a pure data-and-breakpoint change (below), not a structural one.
- Each extra column is rendered by the existing generic `HeaderZone` (header) and a small `FlatCell` (row, single-line, secondary-weight, unlike Title's bold two-line `StackedCell`) — both driven purely by `col.id`/`col.width`/`col.flex`/`col.align`, so adding or removing a column is a one-line change to `LIBRARY_EXTRA_COLUMNS`. `displayValueForColumn(track, columnId)` supplies each cell's text and is deliberately separate from `getSortValue`: display keeps original casing and shows only the *first* genre of a multi-genre tag (e.g. "Rock" from "Rock, Pop"), while the sort comparison value is lowercased for case-insensitive ordering.
- The first extra column (Album) gets an extra `marginLeft: 20` beyond the row's normal 12px flex gap, in both `TrackRow` and `TrackListHeader` — without it, Album's left-aligned text reads as crowded against Duration's right-aligned number immediately to its left.
- **Breakpoints** (`App.jsx`): `LIBRARY_YEAR_COL_BREAKPOINT` (900) and `LIBRARY_GENRE_COL_BREAKPOINT` (1000) are dedicated constants; the lowest tier (zero extra columns) deliberately reuses the existing `isUltraCompactPanel` (780) rather than a constant of its own. `visibleLibraryColumnCount` is a plain cascade (0/1/2/3) rather than three independent checks, since each wider threshold implies the narrower ones are already satisfied. **780 is a hard floor, not a stylistic choice**: `electron/smokeTest.mjs` has a hardcoded check (predates this feature, written when `minWidth` was 700) that resizes the window to exactly 700px and asserts Library's header/rows show no horizontal overflow — keeping the lowest breakpoint above 700 guarantees that check still sees zero extra columns, exactly like before this feature existed.
- **Smoke-test alignment is selected by label text / row class, not position** (`electron/smokeTest.mjs`) — `labels().find(l => l.textContent.trim() === 'Time')` and `firstRow.querySelector('.track-row-duration')`, rather than `labels[labels.length-1]` / `row.children[length-1]`. That matters because in `extended` mode the *last* header label and the *last* row child are no longer Duration/Time — they're whichever extra column is currently visible (header) and the standalone ⋮ button (row). Only `children[2]` (Title, always third from the left in every mode) stays a safe positional selector.

**Load-bearing constraints (several inherited from the old implementation):**

1. **`scrollElRef` must point at the actual scrolling ancestor** (Library: `.scrollable` in `App.jsx`; Details: `HomeDetailView`'s `innerScrollRef`). A `flex:1` div nested in a non-flex parent has unbounded height and never truly overflows — attaching the virtualizer there silently mounts every row.
2. **`scrollMargin`**: TrackList measures the offset from the scroll container's content top to the first row (`useLayoutEffect` on density/showAlbum/first-rows-appearing) and feeds it to the virtualizer; rows translate by `virtualRow.start - scrollMargin`. This keeps windowing and `scrollToIndex` exact with the title + sticky header above the rows.
3. **Drag gate**: `canDrag = isManual && no-search && 1 < count ≤ 5000`. dnd-kit's per-row `useSortable` context broadcasts are why unvirtualized/ungated large lists were slow — `React.memo` blocks prop-driven re-renders but not context-driven ones, so capping how many rows are *mounted* is the only real fix. Don't reintroduce an ungated path. In sorted mode the leading cell shows the position index instead of a grip. (Originally measured on a 1272-song library: mounted rows 1272 → ~18, click-select latency ~135ms → ~8ms.)
4. `scrollToTrack` (next/prev/autoplay-advance) goes through `rowVirtualizerRef.current.scrollToIndex(...)` — TrackList assigns its virtualizer into the `virtualizerRef` prop; off-screen rows don't exist in the DOM.
5. **Playback follows the displayed order**: `App.jsx` derives `sortedLibrary` from `useTrackSort` and `playNext`/`playPrev`/`removeTracks`-advance/`togglePlay`-start all walk it, so "next" always matches what the user sees. Manual order (the raw `library` array) is what `library:save` persists; sorting is a view over it and survives sessions via localStorage.
6. **Cmd+A routing**: the App-menu IPC (`menu-select-all`) can't be seen by DOM keydown, so App keeps `activeSelectionRef` — assigned to `librarySelection` when `view === 'library'`, claimed by an open HomeDetailView via its registration effect, nulled otherwise. The rows-block is keyed on `${sort.field}:${sort.dir}` for a soft fade on sort changes (`.track-rows-appear`).
7. **Interaction model**: single click selects; double-click and Enter play; the global Space handler in `App.jsx` toggles play/pause (skips INPUT/TEXTAREA/BUTTON focus); Delete/Backspace removal lives inside TrackList's keydown (the old global handler is gone) — the list container self-focuses on mousedown so keyboard works after any click. The context menu opens on button-2 `mousedown` (earliest possible signal) **and** on `contextmenu` (covers macOS Ctrl+click, which never produces a button-2 mousedown), guarded by `lastMenuOpenRef` so the contextmenu that follows a handled mousedown within ~400ms is a no-op.
8. **Row callbacks must stay referentially stable** (`latestRef` idiom in `TrackList.jsx`: callbacks are `useCallback(..., [])` and read live values through a per-render-updated ref). Before this, every App render re-rendered all ~25 mounted memo'd rows and menu-open→paint measured ~70ms; after, ~22ms. Same reason `DraggableTrackRow` is a memoized component rather than a render-prop shell — a render-prop's fresh `sortable` object busted row memoization in drag mode. Don't pass freshly-created objects/closures as row props.

### Row states, the playing bars, the footer and the handle

The blue accent (`--accent-color`) is gone from track lists and the player's toggles; it survives only where it is a deliberate primary action (the add-songs dialog's Play, genre chips, the Tag Editor's artwork pick).

- **States are a white ladder** (`.track-list .track-row…` in `index.css`, scoped so the search panel, which reuses the `.track-row` class for hover only, is untouched): hover is a faint wash (0.07), the playing row a stronger one (0.12, no stripe), the selected row the strongest (0.18) plus a white hairline ring; playing+selected is 0.2 with the ring. Rows are 10px-radius; padding is still 12px (the column header's labels are aligned to it).
- **The playing row is marked by bars in the leading column** (`NowPlayingBars` in `TrackRow.jsx`, `.row-eq`): they dance while playing and stand still while paused, and replace the row's number. They replaced the bars that used to dim the artwork, so the artwork now shows a play/pause overlay on hover only. Home's Quick Picks and the search panel keep their own markers (white now).
- **Player toggles** (shuffle/repeat, everywhere they appear: the pill, narrow Now Playing and the mini player share the same transport markup): active is `--chrome-text` (white) **with a 4px white dot under the icon** (`.player-toggle--on::after`: a pseudo-element, so the icon never moves; it fades and grows in over 0.18s); inactive is `--chrome-text-off` (50% white) with no dot. The dot exists because brightness alone (white vs 50% white) was easy to miss over a bright artwork tint, so "on" is now a marker as well as a colour. (A soft chip behind the icon was built first and replaced by the dot at the user's request.) Both carry `aria-pressed` and an `aria-label` (`Repeat: off|all|one`); repeat shows the dot for all and one (its icon already switches to the `1` version). Smoke asserts the dot (via `getComputedStyle(b, '::after')`), no chip, `aria-pressed` and the cycle.
- **Footer** (`summarizeTracks` / `formatTotalDuration` in `trackUtils.js`): "3 songs · 9 min" under every track list (Library and Details). It lives in the first 40px (`FOOTER_HEIGHT`) of the virtualizer's `paddingEnd`, *above* the floating player's clearance: as a plain element after the list it landed below the clearance, behind the pill at the end of a long list. Absolute-positioned inside the rows block at `getTotalSize() - bottomPadding - FOOTER_HEIGHT`.

- Guarded by the `listrows` smoke section: white ring and fill on a selected row, bars on the playing row (and still when paused), no stripe, a scan of every element in the list and its header for the old blue in any state, the footer's position, and the handle appearing on a genuine hover.

## Column-cycle sorting (no Sort dropdown)

Clicking a column header advances that column's cycle. The cycles are **data** (`COLUMN_CYCLES` in `trackUtils.js`), not branching logic:

| Column | Cycle |
| --- | --- |
| Title | title↑ → title↓ → **artist↑ → artist↓** → manual → ⟲ |
| Album (Details' stacked cell, or Library's flat column — same `album` field/cycle either way) | album↑ → album↓ → manual → ⟲ |
| Time | duration↑ → duration↓ → manual → ⟲ |
| Year (Library only) | year↑ → year↓ → manual → ⟲ |
| Genre (Library only) | genre↑ → genre↓ → manual → ⟲ |

Title folds in Artist because both share one combined cell — `TrackRow`'s `StackedCell` already promotes whichever is sorted to its bold primary line. The label renames itself **only for a borrowed field** (`activeFieldForColumn` + the `active !== columnId` check in `HeaderZone`), so the Title column reads "Artist" while sorted by artist but Time stays "Time" rather than becoming "Duration". Manual shows the column's own name with no arrow.

**Every cycle must end at manual.** `canDrag` keys off `isManual`, so without that step one click on any header would disable drag-to-reorder permanently, with no affordance anywhere to restore it (the dropdown that used to offer "Manual order" is gone). `nextInCycle` relies on a not-found `findIndex` returning `-1` so `(-1+1) % len` lands on index 0 — that is what makes clicking a *different* column start its cycle from the top, and what rescues a persisted-but-unreachable field.

`dateAdded`, `playCount` and `lastPlayed` remain **removed** from `SORT_FIELDS` along with the dropdown that used to be their only entry point — a field with no column header would be unreachable. `year` was later reintroduced once Library gained its own Year column ("Library's extra columns" above); a `bitrate` field went through the identical add-then-remove cycle. This is the general rule for this file: `SORT_FIELDS`/`COLUMN_CYCLES`/`getSortValue` only ever carry entries a rendered column can actually reach — add a column, add its entries; remove a column, remove them too. `CONTEXTUAL_FIELDS`, `formatContextValue`, `formatRelative` and `TrackRow`'s old contextual trailing column are still gone. Note the consequence: **play stats are still recorded** (`stats:recordPlay`, `play-stats.json`) but are no longer displayed anywhere. That data is intact for a future UI.

## The column header lives OUTSIDE the scroll container

**This is the central structural decision, and reverting it reintroduces a bug that has already been fixed twice.**

`TrackList` does **not** render the header. Each layout owner places `<TrackListHeader>` as a **sibling above its own scroll container** — `App.jsx` above `.scrollable`, `HomeDetailView` above its `innerScrollRef`.

Why it matters: a sticky header *inside* a scroller has rows passing behind it, so it must paint an opaque fill to stay legible. That fill is what made the bar visibly darken on scroll, and no amount of colour tuning removes it — the fill is load-bearing as long as anything can get behind the labels. Moving the header out means **nothing is ever behind it**, so it needs no background, no blur, and no scrolled state at all. It is text over a 1px rule and looks identical at every scroll position.

Consequences worth knowing:

- There is no `--scrolled` class, no scroll listener, and no elevation state anywhere. All of that was deleted, not restyled.
- `.track-list-header` is `position: relative`, not `sticky`. It carries no `z-index` (nothing overlaps it any more, including dragged rows).
- `scrollMargin` in `TrackList` is now ~0, but is still **measured rather than assumed** — a caller may put content above the rows inside its scroller.
- The Library screen carries **no title, song count or total duration at all** — no `<h2>Library</h2>`, and nothing in the title-bar strip either. The nav pill already marks the active view, and the same counts remain on Home's stats line. Panel top → first row went from **135px to ~48px**. The smoke suite asserts none of it comes back.

**The scrollbar-gutter compensation.** Because the header sits outside the scroller, it does not lose width to the scrollbar the way the rows do — which put `TIME` 6px right of the duration column on *both* screens. Both scrollers therefore set `scrollbar-gutter: stable` (so the gutter is reserved even when the list is too short to scroll, keeping the offset constant), and both headers add a matching **6px right padding** (`App.jsx` uses `padding: '16px 38px 6px 32px'`; `HomeDetailView` uses `paddingRight: 6`). The smoke suite asserts label-over-column alignment to the pixel on both screens — that is the guard, since the arithmetic is otherwise easy to break.

**Testing "nothing is behind it" requires a hit-test, not a rect comparison.** `getBoundingClientRect` still reports geometry for rows scrolled out of view and clipped by the scroller, so a rect-overlap check flags invisible rows and proves nothing. The smoke suite uses `document.elementFromPoint` across the header and asserts no `.track-row` is ever the painted element.

**Density's only entry point is the `.track-header-density` toggle**, in the 20px header slot that lines up with the row's lyrics indicator. It used to live in the Sort dropdown; when that was removed it would have been orphaned, and it is persisted (`sonus.trackDensity`) and shared with detail views. That slot is the only free space that does not push `Time` out of alignment with the duration column.

**Empty states:** `TrackList` takes an `emptyState` node that replaces its default "No tracks found." block. A search matching nothing renders through `TrackList` so the header (and its sort controls) stays on screen; only a genuinely empty `library` hides the header entirely for a full-bleed prompt, since there is then nothing to sort.

## Player pills (full-width and narrow)

The full-width transport bar used to be a full-width docked strip, permanently occupying real layout space at the bottom of the content card. It's now `PlayerPill.jsx` — a compact, thin, dark-glass floating capsule, `position: fixed; bottom: 18; left: 50%; transform: translateX(-50%)`, rendered as a sibling of the main content card (`.glass-panel`) rather than its last flex child. Narrow layout went through the exact same migration later, at a genuinely separate later request — `PlayerPillNarrow.jsx` replaced the old docked `renderMiniPlayerBar` (a bar that lived inside normal layout flow, in two separate call sites) with its own floating pill, described in its own subsection below. The two components share the bubble-animation state machine (`usePillPhase.js`, a small extracted hook) and the underlying `.player-pill`/`.player-pill-wrapper` CSS, but are otherwise separate files — narrow's row content (two buttons, no seek strip, no menu, touch-sized) differs enough from full-width's that a single parameterized component wasn't worth the branching.

**Geometry: a concentric squircle with a seek row (current design).** `PlayerPill.jsx` is a soft rounded rectangle (`PILL_RADIUS = 18`, `min(644px, 100vw - 48px)` wide), two rows tall: a 46px **main row** — artwork at the leading edge, title/artist (marquee), then shuffle, previous, play/pause, next, repeat, and the ⋮ menu — and a 26px **seek row**: elapsed time, the seek line, remaining time (`-m:ss`), the same arrangement as the mini player. `PLAYER_PILL_TOTAL_HEIGHT` (72) + `PLAYER_PILL_BOTTOM_MARGIN` (18) feed `PLAYER_PILL_CLEARANCE` in `App.jsx`, which is what every list's scroll padding, the toast offset and the hero's Play-button gap derive from — never hand-pick those. The measured pill is ~74px tall (the 1px border sits outside the constants). The seek line sits *inside* a second row, with the times at each end, because a bar running along the pill's bottom edge looked wrong where it met the rounded corners.

**The artwork's radius is derived, not chosen.** A thumbnail inside a rounded container only looks right when its corner is *concentric* with the container's: `ARTWORK_RADIUS = PILL_RADIUS - border (1) - ROW_INSET (5) = 12`. Both are computed from the constants (`PlayerPill.jsx`, and the same formula in `PlayerPillNarrow.jsx` with its own inset), so changing the pill's radius or padding moves the artwork's corner with it. Forgetting the 1px border once left it at 13 — visible as a corner that doesn't hug the pill's. Verified by measuring `getBoundingClientRect` insets (equal on all sides), not by eye.

**Dark glass with white icons, matching the rest of the app — this flipped once, and why.** The pill originally inverted the app's usual dark-glass language on purpose: a light, `rgba(255,255,255,0.45)` background with dark icons via its own scoped `--pill-icon`/`--pill-icon-dim` pair, built to chase an Apple Music-style bright floating capsule reference the user shared early on. Once full-width Now Playing grew its own built-in transport controls (see "Now Playing artwork sizing" below) in `--chrome-text` white, the mismatch — white buttons on the Now Playing screen, black buttons on the pill one click away — started bothering the user, and they asked for the pill to flip to dark glass with white icons instead, "fully transparent" in the sense of not forcing its own color onto whatever's behind it rather than literally invisible. It now uses the exact same `--chrome-text`/`--chrome-text-dim` pair every other on-dark-backdrop surface in the app uses (the narrow pill, Now Playing's own controls) — no more scoped pill-only color variables, and no more `.player-pill`-scoped overrides for `.player-artwork::after`'s hover tint, `.player-meta-link:hover`'s color, or `.play-pause-btn--playing`'s glow color — all three now just use their ordinary shared dark-theme rules, since the pill's own surface is dark like everywhere else those rules already apply.

**0.45 black is a computed floor, not an arbitrary number — same number as before, opposite color, opposite direction of risk.** The light version's 0.45 white was a floor against *dark* backdrops threatening *dark*-icon contrast (dark bleeding through a light glass). Flipping to dark glass with white icons flips which backdrop is dangerous: now a *bright* backdrop (most realistically a light-colored album cover tile in Home's artwork grid, blurred by the pill's own `backdrop-filter`) threatens *white*-icon contrast by washing the dark glass toward white. Composited with the actual WCAG relative-luminance formula against that worst case — a blurred near-white tile, only partly darkened by the scrim itself — 0.45 black holds white-icon contrast at ~3:1; every less extreme, more realistic case (which is almost always Sonus's own dark chrome behind it) does dramatically better. Don't raise the background transparency (lower the alpha) further without redoing this calculation. The heavy blur (`blur(64px) saturate(160%)`, saturation eased down from the light version's `200%` since over-saturating a black-tinted blur read muddy) is still load-bearing for the math to hold in practice, not just decorative — it's what keeps sharp content behind (row text, artwork edges, a thumbnail's hard edge) from poking through as uneven patches of contrast instead of blending into the one averaged tone the composite math actually models.

**Artwork-color tint — background only, deliberately not icons.** `PlayerPill` takes `artworkRgb` (`App.jsx`'s existing `{r,g,b}` state, the same value already driving the app's background wash and Now Playing's ambient flares — no new color extraction) and applies it as two things, both purely decorative layers with `pointer-events: none`, never touching icon or text color:
- **A tint layer inside the capsule** — `position: absolute; inset: 0`, painted *behind* the row/seek-strip content (which gets `position: relative; z-index: 1` to sit above it), `background: rgba(r,g,b,alpha)`.
- **An ambient halo behind the capsule** — a much larger (`inset: -41px`), heavily blurred (`blur(44px)`) wash of the same color, a DOM sibling placed *before* the capsule in the outer wrapper so plain source order (no explicit z-index needed) keeps it behind. The same "blur flare" language Now Playing already uses behind its artwork, just applied behind the pill.

**Why background-only, and why a luminance clamp (now inverted from the light-pill version):** artwork-color tinting of the *icons themselves* was tried once already, for the pre-pill dark panel, and explicitly reverted — "it made the icons hard to see against some album art, and always-white was preferred" (see "Artwork-derived color" below). To not repeat that failure while still getting a "themed to this track" feel, the tint here only ever touches the background, and `tintAlphaForLuminance` (`PlayerPill.jsx`) scales the tint layer's *own* alpha as the artwork's perceived luminance (`0.299r + 0.587g + 0.114b`) changes — but which direction gets clamped flipped along with the theme. The light-pill version scaled the tint *down* as artwork got *darker*, since a dark tint on a white glass was what threatened the (then-dark) icons. The dark-pill version scales it down as artwork gets **brighter** instead — down to literally 0 for a near-white cover — since now it's a *light* tint on the dark glass that would threaten the (now-white) icons. A bright or near-white album cover simply doesn't tint the glass, rather than tinting it into a shade the white icons can't be read against; a dark or saturated-but-dark cover tints it fully. The halo (a soft wash *outside* the capsule, never behind the icons) isn't subject to this clamp, since nothing needs to read text against it. Both layers transition (`background 1s ease`) on track change, matching `.app-container`'s own `bgColor` transition, so retinting doesn't snap.

**Bubble appear/disappear.** The pill can't just conditionally render (`{shouldShow && <PlayerPill/>}`) and expect to animate its own exit — an unmounted node can't run a CSS transition. Instead the component stays mounted through both transitions, driven by an internal phase state machine (`'hidden' | 'entering' | 'visible' | 'exiting'`) on the outer wrapper's className, independent of whatever top-level condition `App.jsx` used to decide whether to render the component at all. **This logic is shared** — `usePillPhase(shouldShow, currentTrack)` (`usePillPhase.js`), extracted once `PlayerPillNarrow` needed the exact same state machine, returns `{ phase, displayTrack }`; `PlayerPill` and `PlayerPillNarrow` each compute their own `shouldShow` differently (see below) and pass it in, but the mechanics are identical. The condition that drives it for full-width is `shouldShow = !!currentTrack && !isNowPlayingOpen` (`PlayerPill.jsx`) — the pill has no reason to exist while Now Playing is open, since that screen has its own built-in transport controls now (see "Now Playing artwork sizing" below); folding that into `shouldShow`, rather than having `App.jsx` simply not render `<PlayerPill>` while NP is open, is what lets the bubble-out animation actually play when NP opens instead of the pill vanishing instantly:
- `shouldShow` goes from `false` to `true` → `'entering'` (plays `player-pill-bubble-in`, a scale+opacity animation using a "back-out" cubic-bezier for the overshoot/bounce — no 3-keyframe animation needed, the easing curve alone produces it) → settles to `'visible'` after `ENTER_MS` (450ms, must match the animation's own duration). This covers both a genuine appear-from-nothing *and* closing Now Playing while a track is still playing — both are "was hidden, should now show," and both get the same bubble-in.
- `currentTrack` changes to a *different* truthy value while `hadShownRef.current` is already `true` (an ordinary track-to-track change during normal listening — skip, autoplay, picking another song) → **no animation at all**, just `displayTrack` swapping to the new track. `currentTrack` gets a new object reference on every such change, so gating on the object itself (rather than on `hadShownRef`, a plain `useRef` flag, not state) was a real bug this had at first: the entrance animation replayed on *every* track change during ordinary listening, not just when the pill first appeared from nothing — directly contradicting the intended "existence only" scope. Checking `hadShownRef.current` is what actually scopes it correctly.
- `shouldShow` goes from `true` to `false` (either the track stopped, or Now Playing opened) → `'exiting'` (plays `player-pill-bubble-out`, the reverse) → settles to `'hidden'` after `EXIT_MS` (300ms), at which point the component finally returns `null`.
- `displayTrack` (state, not `currentTrack` directly) holds the last real track object so title/artist/artwork don't go blank while the exit animation is still playing out.
- `pointer-events: none` while `'exiting'`, so a fading-out pill can't be clicked as if it were still live.
- `hadShownRef` starting at whatever `shouldShow` computes to on mount means a genuinely empty library on first launch never plays a pointless exit animation for something that was never shown.

**A second real bug, in the CSS rather than the state machine: the entrance/exit keyframes must include `translateX(-50%)` at every step, not just `scale(...)`.** The outer wrapper's inline style uses `transform: translateX(-50%)` purely for centering (`left: 50%` alone only places its *left edge* at center). A CSS `animation`'s `transform` value **replaces** the inline style outright rather than merging with it — so keyframes that specify only `scale(...)` silently drop the centering translate the instant the animation starts. The visible symptom was exactly "jumps to the right, then back to place": mid-animation the pill sat off-center (translate gone, only scale applied), then the moment the animation's class was removed (`setPhase('visible')`) and the element fell back to the inline style, the centering translate reasserted itself and it snapped back. Both keyframes now carry `translateX(-50%) scale(...)` together at every step, so the same translate value is present start-to-finish and handing off to the static inline style at the end is a no-op, visually. Verified live by checking `(rect.left + rect.width/2) - window.innerWidth/2` stays `0` throughout the animation, not just at rest.

Verified live via the *real* `removeTracks` path (select the playing row, Backspace) rather than `window.__sonusTest.setLibrary([])` — the latter doesn't clear `currentTrack` at all (`setLibrary` and `currentTrack` are independent state; only `removeTracks` nulls `currentTrack` when the removed track was playing and nothing remains to advance to), so it's not a valid way to trigger the exit path in a smoke test either.

**Whole-pill hover/press and the top inner highlight — both pure CSS, no new state.** `.player-pill:hover`/`:active` deepen/flatten the `box-shadow` only — **no `transform`, deliberately**. A first version also lifted and scaled the whole capsule on hover; the user didn't like the movement, so it's shadow-only now, matching the same convention `.skip-btn`/`.play-pause-btn` already use for their own hover/press, just without any translate/scale. `.player-pill`'s `box-shadow` also carries a 1px `inset` highlight along the top edge, on top of the drop shadow — a real glass surface catches ambient light there, and it's the specific detail that reads as "glass" rather than "a translucent box." Much fainter now than the light-pill version (`rgba(255,255,255,0.12)`, was `0.8`) — a strong white rim reads as a glass edge on a light pill, but as a chrome bevel on a dark one.

**Structure:** a `position: fixed` positioning wrapper (no `overflow` — needed so the hover/seek time tooltip, an absolutely-positioned sibling of the capsule with `bottom: calc(100% + 12px)`, isn't clipped) contains the actual capsule (`border-radius: 9999px; overflow: hidden`, for corner-clipping), which is a flex column of two rows:
1. **Main row** (46px — see the size-history note below for how it got here) — Shuffle, Skip Back, Play/Pause, Skip Forward, Repeat, then artwork (41px) + title/artist (marquee-scrolled, same mechanism as before, just smaller than the pre-pill panel — 15px/13px instead of 20px/15px — and artist-only in the subtitle, no album/year, to fit the pill's much narrower width), then the `⋮` menu button. Deliberately one flat row, not the old three-cluster (left/center/right) layout with measured centering math — a fixed-max-width capsule (`width: min(644px, calc(100vw - 48px))`) doesn't need to redistribute space across the window's remaining width the way the full-width bar did, so `centerBlockStyle`, `leftClusterRef`/`rightClusterRef`, `useMeasuredWidth.js`, and the `isCompactPanel`/`isUltraCompactPanel`-driven icon-shrink tiers are all gone (`useMeasuredWidth.js` was deleted outright — it had no other callers left). `isUltraCompactPanel` itself is still very much alive; it's shared with Library's extra-columns cascade.
2. **Seek row** (superseded the old 9px strip along the capsule's bottom edge — see "Geometry" above) — elapsed time, the seek line, remaining time, class `.pill-seek-bar` (a fully separate class from `.top-progress-bar`/`.wow-slider`, so it can't inherit their rules) but with **Now Playing's and the mini player's look**: the `--np-slider-color` cyan-to-blue fill (`#00f2fe` → `#4facfe`) and the glowing white dot (`box-shadow: 0 0 10px rgba(255,255,255,0.8)`), not the flat `--accent-color` it used to have. Same interaction model as the old top-of-panel bar (hover-thicken, drag-to-seek, click-anywhere-on-the-row-to-jump, a floating time tooltip). **No volume control anywhere in the pill** (removed at the user's request); `volume`/`isMuted`/`prevVolumeRef` state and the effect that synced them to the `<audio>` element were deleted along with it, since nothing could ever change them anymore — full-width mode currently has no in-app way to adjust volume at all (system volume only).

**Size history, three rounds, two opposite directions — don't be surprised the current numbers match neither the original nor the "thin" version.** Launched at a 52px row / 12px strip / 24px margin; flattened to 40px / 8px / 12px at the user's explicit "lower, flatter, as thin as possible" request — trimming *chrome* specifically (`.player-pill .player-control-button`'s padding, 12px→8px, pill-scoped so narrow's and full-width Now Playing's own transport rows sharing the base `.player-control-button` class were untouched), not content, since icon/artwork/text sizes were explicitly required to stay the same that round; then scaled back up to the current 46px / 9px / 18px at a later, separate "a little bit bigger... same proportions, same design" request. That third round is a genuine uniform ~1.15× scale-up of every size-related constant together — row height, icon sizes (`PLAY_PAUSE_SIZE`/`ARTWORK_SIZE` 36px→41px, `CONTROL_ICON_SIZE` 20px→23px, etc.), fonts, paddings, the seek-track inset, the ambient halo, the hover tooltip, the hold-ring (now `HOLD_RING_OFFSET`, a computed `(ringSize - buttonSize) / 2` rather than the earlier hardcoded `-4`, so it stays correctly centered at any size) — not a reversion to the original pre-flattening numbers (46 vs. the original 52, 41px icons vs. the original 36px, genuinely new territory both times). The bottom margin (12→18) moved as its own separate "a little bit higher" adjustment in that same third round, not part of the size scale factor — position and size are independent knobs here. `PLAYER_PILL_TOTAL_HEIGHT` (the exported sum of the row + seek strip, `55` now) and `PLAYER_PILL_BOTTOM_MARGIN` (`18`) both feed `PLAYER_PILL_CLEARANCE` in `App.jsx` automatically — scroll clearance and toast positioning track the pill's current size with no separate edit needed there (see "Scroll clearance" below).

**The seek track is inset `SEEK_STRIP_INSET` from each edge, not edge-to-edge — the inset itself is a bug fix, reported by the user from a screenshot, and the exact value has moved once since (16px→18px) along with the size-up above.** The strip sits flush against the very bottom of the capsule, inside the tightest part of the capsule's own `border-radius: 9999` rounding (a full stadium shape, so the left/right ends curve at roughly half the pill's total height as their radius) — a full-width track put the thumb right on top of that curve, so at 0%/100% the capsule's own `overflow: hidden` visibly sliced off part of the thumb. Both the original 16px and the current 18px were verified live via `webContents.capturePage()` pixel sampling at both extremes (not just measured/eyeballed, and not just extrapolated from the old math when the pill's — and so the corner radius's — size changed) to actually clear the curve with room to spare. Two things had to move together with the inset, or they'd silently desync:
- The click/hover handlers on the wrapping div compute their seek percentage against **the `<input>`'s own `getBoundingClientRect()`**, not the div's — the div itself is still the full (un-inset) width via its own `padding`, so using the div's rect would compute percentages against a wider span than the track actually occupies, putting a click just inside the padding at the wrong time position.
- The hover/scrub tooltip's `left` is a `calc()` expression (`${inset}px + (100% - ${inset*2}px) * progressPct/100`), not a plain `${progressPct}%` — the tooltip is a sibling of the capsule, positioned relative to the *wrapper's* full width, so a plain percentage would drift away from the actual (now-inset) thumb position as playback progresses, most visibly wrong near either end.

The native thumb's own CSS `--progress` fill percentage (`::-webkit-slider-runnable-track`'s gradient) needed no equivalent change — that's already relative to the `<input>` element's own (now narrower) box, which is inset via plain `padding` on its parent, so the browser handles it automatically.

**Long-press-to-jump (`handlePlayPauseClick`/`handlePlayPausePressStart`/`handlePlayPausePressEnd`, `App.jsx`) is unchanged mechanically, just relocated:** holding Play/Pause for 700ms while on the Library view scrolls the tracklist to the currently playing track (`rowVirtualizerRef.current?.scrollToIndex(...)`) instead of toggling playback, with a cyan hold-ring as the only visual feedback. `handlePlayPausePressStart` no-ops outside Library (`if (view !== 'library') return`); `handlePlayPauseClick` mirrors that guard for the release side, falling back to a plain `togglePlay()`. Three timing zones: under `QUICK_CLICK_MS` (250ms) is a genuine click; the ring only renders after that threshold (a separate `ringDelayTimerRef`, so a normal click never flashes it for a frame); 250–700ms is an aborted long-press that does nothing at all; past 700ms, `longPressTriggeredRef` swallows the subsequent `onClick` so it doesn't also toggle playback. All three button instances that expose this — `PlayerPill`, `PlayerPillNarrow`, and `renderTransportControls` (narrow Now Playing's Song tab) — call the exact same three handlers; only each instance's own `ringSize`/`ringRadius`/`ringCircumference` differ, locally computed off that instance's own button size (`playSize + 8` in `renderTransportControls`; `PlayerPill` uses `+ 9` for its own `HOLD_RING_SIZE`; `PlayerPillNarrow` uses `+ 8` — three independently-tuned constants, not one shared formula, since each component's own button size moved independently of the others.

**Clickable artist link:** rendered with class `.player-meta-link`, same mechanism as everywhere else it's used — clicking navigates to the artist's HomeDetailView via the first `splitArtists` token, after `setHomeDetailOrigin(view)` so the back button returns correctly. Album/year links were dropped from the pill's subtitle (artist only) to fit its width — they're still one tap away via the artwork/title click straight into Now Playing, which shows the full artist · album · year line.

**Play button glow / bare-icon styling** is unchanged from the pre-pill design (see "Play/Pause is a bare icon" further below) — `.play-pause-btn`/`.skip-btn`/`.player-control-button` are shared classes, reused as-is, including the glow color: now that the pill is dark glass like everywhere else, it uses the same plain white `icon-glow-pulse` every other Play/Pause button uses, with no pill-specific override (the earlier light-pill version needed its own accent-blue `icon-glow-pulse-pill` variant so the glow would show up against a *light* background; that variant no longer exists).

**Scroll clearance for the floating pill — a real, non-obvious gotcha:** Library/Home/HomeDetailView all need extra space at the bottom of their scrollable content so the last rows don't end up hidden underneath the pill. **Plain CSS `padding-bottom` on the scrolling container does not work for this if that container's overflow comes from a `TrackList` virtualizer** — confirmed live: forcing `.scrollable`'s `padding-bottom` to `900px` produced a **zero-pixel** change in `scrollHeight` when Library was showing (virtualized), while the exact same test on Home (plain content, no virtualizer) changed `scrollHeight` by the full expected delta. The root cause: Library's `<TrackList>` sits inside a `height: '100%'`-bound wrapper div, and when a *virtualizer's* rows overflow that kind of wrapper, Chromium's `scrollHeight` calculation for the ancestor scrolling container doesn't add that container's own bottom padding on top of the overflow — only content that's part of "real" in-flow layout does. The fix is `<TrackList>`'s own `bottomPadding` prop, which feeds `paddingEnd` directly into its `useVirtualizer(...)` call (`TrackList.jsx`) — this bakes the clearance into the virtualizer's own `getTotalSize()`, which is what actually determines `scrollHeight` here, sidestepping the wrapper issue entirely. Library's `<TrackList>` (`App.jsx`) and HomeDetailView's own `<TrackList>` (which manages its own separate scroll container, independent of `.scrollable`) both take `bottomPadding={isNarrowLayout ? NARROW_PILL_CLEARANCE : PLAYER_PILL_CLEARANCE}` — both widths need real clearance now that both pills float, where narrow used to pass a plain `0` back when its bar was still docked and part of normal layout flow. Home's own card-based content (no `TrackList`, no virtualizer) is the one place plain CSS `padding-bottom` on `.scrollable` does work correctly, and is what's actually used there (also now width-conditional on the appropriate pill's own clearance constant) — don't "fix" it to also use a `TrackList`-style prop; it was never broken in the first place, and Home's cards have no such prop to feed. **`.scrollable`'s own padding is `0` on every side while a Home detail item is open specifically because HomeDetailView already has its own clearance mechanism** (`TrackList`'s `bottomPadding` above) — giving `.scrollable` bottom padding *too* in that case is a real, previously-shipped bug, not a hypothetical: see "Detail hero redesign"'s fourth bug above for what a duplicate reservation there actually did (silently shrunk `HomeDetailView`'s own available height, stopping its internal scroll container short of the window's true bottom instead of extending flush to it like Library's does).

**Now Playing overlay reaches the true bottom edge in both widths.** The NP overlay's own bounding box (`App.jsx`, `bottom: 0`) used to stop `124`px short of the content card's bottom edge in full-width mode specifically, to visually sit above the then-docked panel without overlapping it. Since the pill is now a `position: fixed` overlay with its own z-index (`6`, above the NP overlay's `5`) that floats independently of any content beneath it, there's no reason for NP's own box to stop short anymore — it matches narrow's already-`0` value now. If this box's `bottom` value and either pill's z-index ever drift out of sync (e.g. a pill's z-index drops below NP's), that pill would end up rendering underneath Now Playing instead of on top of it — which specifically matters for `PlayerPillNarrow`, since (unlike the full-width pill) it's meant to render *above* part of the NP overlay itself while the Lyrics tab is open (see "Narrow pill" below).

**Toast notifications** float above whichever pill is showing via `PLAYER_PILL_CLEARANCE`/`NARROW_PILL_CLEARANCE` (`App.jsx`) — the same constants used for scroll clearance above, not separately hand-picked numbers, so they can't drift out of sync with each other.

### Narrow pill (`PlayerPillNarrow.jsx`)

Narrow's own floating pill, added later at a genuinely separate user request ("make the same pill for the narrow view... with only two player buttons") — it replaced the old docked `renderMiniPlayerBar`, a bar that lived inside normal layout flow rather than floating, and was reused verbatim at two call sites (Library/Home, and narrow Now Playing's own Lyrics tab). `PlayerPillNarrow` is rendered **once**, unconditionally on `isNarrowLayout`, as a `position: fixed` sibling near the full-width pill in `App.jsx` — it isn't rendered separately inside each screen the way the old bar was, since a single floating instance can cover every case its own `shouldShow` allows.

**Deliberately not a size prop on `PlayerPill`.** The two components differ enough in actual row content — two buttons instead of five, no seek strip, no `⋮` menu, touch-sized rather than desktop-scaled (44px artwork/Play button vs. full-width's 41px, closer to the old docked bar's own sizing than to full-width's newer bigger scale) — that branching a single component on a `narrow` prop would mean most of its JSX being conditional anyway. What they *do* share: `usePillPhase.js` (the bubble-animation hook, see "Bubble appear/disappear" above) and the underlying `.player-pill`/`.player-pill-wrapper` CSS (dark glass background, border, box-shadow, hover/press, bubble keyframes) — genuinely shared, reused as-is, not duplicated.

**`shouldShow` folds in `isLyricsOpen`, not just `isNowPlayingOpen`** — `!!currentTrack && (!isNowPlayingOpen || isLyricsOpen)`. This is what lets one instance replace both of the old bar's call sites: visible in Library/Home (`isNowPlayingOpen` false); hidden on narrow Now Playing's Song tab (which has its own full-size embedded `renderTransportControls`, so a second, smaller transport row floating over it would be redundant); visible again on the Lyrics tab (`isLyricsOpen` true), where there's otherwise no way to control playback while reading. Its z-index (`6`) already sits above the NP overlay's (`5`), so it correctly floats over the Lyrics tab's own content with no extra stacking work needed — see the z-index note in the "Now Playing overlay reaches the true bottom edge" paragraph above.

**Tapping the pill branches on `isNowPlayingOpen`**, expressed as a single `onTap` prop computed in `App.jsx`: `() => { if (isNowPlayingOpen) setIsLyricsOpen(false); else expandNowPlaying(); }`. This is a deliberate synthesis of what the old bar's *two* separate `onBarClick` callbacks did at its two call sites (Library/Home: open Now Playing; Lyrics tab: switch back to the Song tab) into one branch on one shared instance — tapping the pill never needs to "close Now Playing entirely" from the Lyrics tab, since `isNowPlayingOpen` can only be true there in the first place when `isLyricsOpen` is also true (that's the only way `shouldShow` keeps the pill visible while NP is open at all).

**Two buttons only — Play/Pause and Skip Forward** — shuffle, skip-back, and repeat are dropped entirely (the old docked bar kept skip-back; this is a further reduction), all still reachable inside narrow Now Playing's own Song tab. No seek strip (seeking stays inside the Song tab's own always-visible bar) and no `⋮` menu (track-action access stays inside Now Playing's own top bar) — both deliberate scope cuts confirmed with the user before building, not oversights. Play/Pause reuses the same `handlePlayPauseClick`/`handlePlayPausePressStart`/`handlePlayPausePressEnd` trio as every other transport button in the app, so long-press-to-jump-to-track (see above) works identically here on the narrow Library screen.

**No marquee scrolling on title/artist** — plain `textOverflow: 'ellipsis'` truncation, matching the old docked bar exactly. The full-width pill's marquee effect depends on `App.jsx`-level ref-measurement machinery (`playerTitleWrapRef` etc.) that was never wired up for a second, narrow-specific text block; this was a deliberate scope decision (not asked about, since it wasn't implied by the request that prompted this component — "the same pill... with only two player buttons" was about buttons, not text animation) to keep the change scoped to what was actually asked. Worth revisiting if the user wants marquee here too.

## Narrow layout (phone-portrait widths)

Below `NARROW_LAYOUT_BREAKPOINT` (`560`, `App.jsx`) — a strict subset of `ULTRA_COMPACT_PANEL_BREAKPOINT` (`780`, still used by Library's extra-columns cascade) — the app shell branches into an entirely different, single-column layout instead of further shrinking the desktop one. `minWidth` in `electron/main.js` is `380`, so this range is fully reachable. `isNarrowLayout = useIsNarrow(NARROW_LAYOUT_BREAKPOINT)` gates every branch below; nothing here is a CSS media query, since these are structural DOM differences, not just sizing (Home's own `.home-quick-picks-grid` responsiveness is still a plain `@media` swap — this distinction matches how `isUltraCompactPanel` is already JS-gated for the same reason).

**The nav pill lives in the draggable title-bar strip itself** (the same 42px strip that holds the traffic lights, `top: 5`-ish), a true sibling of `.glass-panel` (not nested inside it — see why below), not in a row of its own inside the panel — an earlier version gave the sidebar's hamburger toggle a dedicated ~42–58px row directly below the strip, which cost real vertical space for one icon. Search used to be this pill's leftmost segment; it is now a separate round button beside the + (see "Primary navigation" below).

Home used to get an equivalent centered "Home" label in this same strip, in the spot the old standalone search field occupied on Library. It was removed at the user's request — its condition only checked `view === 'home'`, not whether a Home *detail* page (artist/album/year/etc.) was open on top of it, so it kept showing alongside that page's own "‹ [origin]" back breadcrumb, reading as a redundant double header. Home's top strip is simply empty now; nothing replaced it.

**Why the pill is a true sibling of `.glass-panel` and not nested inside it, with a big z-index:** `.glass-panel`'s own `backdrop-filter` gives it a separate stacking context, so a z-index on something nested inside it only ever competes with the panel's *other* children — it can never out-rank a true sibling, no matter how large the number. This bit a since-removed narrow overlay drawer that used to live at this same level (nesting its trigger inside `.glass-panel` once left it genuinely covered and unclickable behind the drawer's own higher z-index — confirmed live via `document.elementFromPoint()` hit-testing, not just visually dimmed); the constraint still applies to anything added at this level going forward. See the matching "fails silently" row in `CLAUDE.md`.

Removing the old hamburger's dedicated row eliminated the ~42–58px that used to sit between the strip and the first track row — Library's `TrackListHeader` now renders directly at the top of `.glass-panel`, right after the strip.

**Player panel → floating pill.** `PlayerPillNarrow` (see "Narrow pill" above, under "Player pills") replaced the old docked `renderMiniPlayerBar` entirely — it's rendered once as a `position: fixed` sibling near `<PlayerPill>` in `App.jsx`, not inline inside Library/Home's own layout, and its own `shouldShow` (folding in `isLyricsOpen`) is what makes one instance cover both of the old bar's call sites (Library/Home, and narrow Now Playing's Lyrics tab) without App.jsx needing to render it from two different places. It's hidden while narrow Now Playing's **Song** tab specifically is open — that tab has its own full-size embedded transport controls (`renderTransportControls`, below), so a second floating transport row over it would be redundant — which is also why the NP overlay's `bottom` offset is `0` here (now also `0` at full width, for a different reason — see "Player pills" above).

**Now Playing → single-column tab view.** Branches to an entirely different JSX tree (not a forced 50/50 → 100/0 width transition) inside the same always-mounted NP overlay: a top row (back chevron, a Song/Lyrics tab label reusing the same `isLyricsOpen` boolean the desktop side-panel toggle already uses, and the `⋮` menu), then either the Song tab (artwork, title/artist, the seek bar, and a transport row) or the Lyrics tab (the same lyrics block, full width, extra `NARROW_PILL_CLEARANCE` bottom padding on its own scroll container so the last lines of a long lyric don't sit underneath `PlayerPillNarrow` — which floats over this tab from outside, as a sibling of the whole NP overlay, not rendered inline here; see "Narrow pill" above). The transport row (shuffle/prev/play/next/repeat) is built by `renderTransportControls({ playSize, playIconSize, playMargin, controlSize, secondarySize })`, a separate local helper in `App.jsx` — it reuses the exact same handlers/state as the pills (`playPrev`, `playNext`, `toggleRepeat`, `handlePlayPauseClick`/`handlePlayPausePressStart`/`handlePlayPausePressEnd`) but not their JSX or sizes, since this row has the full screen width to itself.

No new features were added anywhere in this layout — favorite/add-to-playlist/equalizer/sleep-timer/queue-view/skip-±10s all have no Sonus equivalent and are simply absent; Playlists/Folders/Artists tab navigation for the Library was likewise left out (it stays a single flat list, just restyled). An earlier version of narrow Now Playing kept a Volume control (the one reference "utility icon" with a real Sonus feature behind it) — it was later removed at the user's request, so narrow Now Playing has no volume control; full-width's player pill later dropped its own volume control too (see "Player pill" above), so as of that change neither width has one anywhere in the app.

## Mini player (very short windows)

When the window is at or below `MINI_LAYOUT_HEIGHT_BREAKPOINT` (`trackUtils.js`, **420px** tall), the whole shell is replaced by `MiniPlayer.jsx`: artwork, title/artist (marquee when long, `dir="auto"` so Hebrew titles read correctly), animated bars while playing, a seek line with elapsed / remaining (`-m:ss`) time, and the same five transport controls as the full-width pill. It is **only the player** — no page of the app adapts to short heights; to see anything else the user makes the window taller again. It triggers automatically from any page (Library, Home, a detail page, Now Playing), in either width, and leaves the same way: a taller window, the expand button, or Escape. 421px is not mini; 420px is (asserted exactly by the smoke suite).

**Window limits.** `electron/main.js`'s `minHeight` went from 600 to **180** (the shortest the card fits at `minWidth` 380; verified at 380×180). `minWidth` is unchanged. This is the one thing that makes the in-between band — 421-599px tall, previously unreachable — reachable for the normal layouts; they were checked there (no overflow, no mini), and the only thing that needed help was the narrow detail hero, whose height is `clamp(max(230px, min(280px, calc(100vh - 320px))), 45vh, 460px)` — identical to the old `clamp(280px, 45vh, 460px)` at 600px and above, easing down to 230px below that so the track list isn't squeezed out. (A separate, older problem found while checking this band — the floating pill covering the detail hero's Play button at ~1000px wide — is fixed; see "Detail hero redesign".)

**Mechanism.** `useIsShort(px)` (`useIsShort.js`, the height twin of `useIsNarrow`) drives `isMiniLayout` in `App.jsx`; `MiniPlayer` renders as a `position: fixed; inset: 0` overlay (`zIndex: 900`, above Now Playing's 5 and the pills' 6; the drop-confirm modal at 1000 and toasts at 2000 still sit above it). The app underneath stays **mounted** so leaving mini returns to the same page, scroll position and library:
- The nav pill and `.glass-panel` get `inert` plus `opacity: 0`. **Not `visibility: hidden`** — descendants such as `.scrollable` set their own explicit `visibility`, which punches through a hidden ancestor — and **not `display: none`**, which collapses the scroll containers and loses Library/detail scroll positions.
- Both pills are *unmounted* (not just hidden) while mini shows; they re-enter with their normal bubble animation.
- The transport row is `App.jsx`'s own `renderTransportControls` (passed in as `renderTransport`), not a copy, so shuffle/repeat/skip behavior has one definition.
- The play button's long-press "jump to the playing track" is disabled in mini (it would scroll a Library nobody can see and flash the hold ring).
- Toasts move to the top edge (nothing to clear at the bottom; the controls fill it). An open track context menu is closed on entry.
- With no current track the card shows only "Nothing playing" — no controls, so nothing can start playback from an empty state.

**Getting out of mini mode.** Dragging the window taller works, and so does the expand button (top-right, `.mini-restore-btn`, a `Maximize2` icon) or Escape. Both send `window:restore-from-mini` with the **last non-mini window size**, which the renderer records on every `resize` while above the breakpoint (`normalWindowSizeRef` in `App.jsx` — recorded there, not in `main.js`, because the breakpoint lives in renderer code and `main.js` deliberately imports none; each resize event is judged on its own size, so a half-shrunk size can never be recorded). `main.js` grows the window to that size (animated), keeps its position, and only nudges it as far as needed to stay on its display. The height is **never less than `MIN_RESTORED_HEIGHT` (760px)**, clamped to the display's work area: a remembered size in the 421-599px band (legal now, cramped) used to restore into a window with things cut off, and 760 is comfortably above the old 600px minimum every page was designed for (re-checked at 760 on Library, Home, a detail page and Now Playing at 420, 1000 and 1728px wide: every key control inside the viewport, no overflow). A remembered size already taller than 760 is kept as is. If there's no recorded size (the app launched already in mini mode) it falls back to 1000px wide by 760 tall. Escape is ignored while the drop-confirm modal is open, so it dismisses the modal first instead of also resizing. The button is shown and hidden **together with the macOS traffic lights** (next paragraph) — fully hidden otherwise, with `pointer-events: none` so it can't be clicked blind; Escape and the window edges work whether or not the chrome is showing. (An earlier version kept it faintly visible at rest as a safety net, until the pointer tracking below made the hover reliable.)

**The mini player's look: Now Playing's lights and glow.** The card carries the full-screen player's atmosphere rather than a flat scrim:
- **Moving lights.** `AmbientFlares.jsx` (extracted from `App.jsx`, where Now Playing now uses the same component) — three `artworkRgb`-coloured circles in a blur furnace on 8/13/18 second loops (`np-flare-1..3`), running only while playing and fading out (1.5s) when paused. Its one knob is `blur`: Now Playing keeps its `100px`, the mini player passes `clamp(36px, 14vh, 64px)`, since 100px is far too diffuse for a card this small. Extraction was checked property-by-property against the pre-extraction DOM: identical except the one deliberate addition below. **Also new, for both screens:** the circles' colour eases over 1s when the cover changes (`transition: background 1s ease`, as the pill's halo already did) instead of snapping.
- **Artwork** gets Now Playing's treatment: 1px light border, a glow in the cover's own colour (`boxShadow` from `artworkRgb`), and the `np-artwork` fade-in plus slow breathing pulse (paused when playback is), keyed by track so the fade-in replays.
- **Seek line** is `.wow-slider`'s own look — the cyan-to-blue fill and a glowing white dot — rather than the pill's flat accent blue, with a 24px invisible hit box (the input keeps the app's base height and cancels it with negative margins; an earlier version shrank it to the 4px it draws and only the line was clickable) and the same hover thickening the other bars have.
- **Glass edge:** a 1px inset top highlight only; the window's native rounded corners would clip any border on the other three sides.

**Spacing at the minimum height.** The card's top padding (26px, for the traffic lights' own strip) and the artwork size are CSS custom properties (`--mini-pad-top`, `--mini-art`, `--mini-seek-gap`, read inline in `MiniPlayer.jsx`) so `index.css` can change them below 215px tall (`@media (max-height: 215px)`): 38px top padding, a 54px artwork, a 6px seek gap. At the 180px minimum the lights end ~22px from the top and the artwork used to start at 27px — ~5px under them, against 22px of margin on its left; it now starts at 40px (~18px). The content needs ~124px and 180−38−14 = 128 is available, so it just fits (the smoke suite asserts the artwork's top and that nothing crosses the bottom edge at 380x180 and 380x205, and that 440x260 keeps its layout). The traffic lights themselves are native and can't be seen from the test environment: the 22px figure is read off a user's screenshot.

**The ⋮ track menu in the mini player.** After the five transport controls, `[data-mini-menu-btn]` opens the SAME `trackMenu` the pill, Now Playing and Chill mode open (`context: 'now-playing'`: Start Mix, Edit Tags…, Reveal in Finder, Search in YouTube), rendered once at the root of `App.jsx` (z 1000, above the card's 900). Things specific to a window this small: **(1) the menu is clamped inside the window** — it is ~130px tall and the window can be 180px, so a layout effect (`trackMenuRef`) nudges it back inside a 6px margin whichever side it opened on (at 380x180 it ends up overlapping the button row, which is the only place it fits); **(2) `.track-dropdown` is `-webkit-app-region: no-drag`** — the card is a window-drag area and Electron hands drag areas to the OS, so a menu over it without this would show but never take a click (a scripted `.click()` would still pass; the smoke suite asserts the computed region); this also fixes the same latent trap for the menu over the title strip in other views; **(3) Escape closes the menu before it would expand the window** (`restoreOnEscape` is false while `trackMenu` is open); **(4) leaving mini mode closes an open menu** (the effect's cleanup) — entering already did; **(5) Start Mix expands the window first** (the expand button's own `restoreFromMini`), because the card covers everything and the mix page would otherwise open unseen. Edit Tags / Reveal in Finder / YouTube need nothing special. The row stays six buttons wide inside the 336px content area at the 380px minimum width (no negative margin on the new button: it overlapped Repeat's padding and would have stolen part of its click area). The traffic lights and the expand button are *not* held up by an open menu: the pointer is inside the window while you use it, so they are already shown. Smoke covers 380x180, 440x300 and 700x420: button clear and topmost, four items, menu inside the window, items on top, no-drag, Escape order, toggle, outside click, closing on leaving mini, and Start Mix expanding the window (with the mix cache seeded, so no network call). The items' own actions are not clicked (they open real windows).

**Window chrome.** The window *is* the card. Its corners are macOS's native window corners and the glass is the window's native vibrancy; CSS can't round or clip either, so `MiniPlayer` deliberately has no `border-radius`, border or backdrop-filter of its own, just a `rgba(0,0,0,0.2)` scrim like Now Playing's. **Traffic lights and the expand button — one hover signal, tracked by the main process.** Both are hidden in mini mode and appear together while the pointer is over the window; the traffic lights are always restored on exit. The pointer is tracked in `main.js` by `electron/pointerTracker.mjs` — it compares the OS cursor position (`screen.getCursorScreenPoint()`) with the window's bounds every 100ms, reports *entering* on the next tick and *leaving* only after the pointer has stayed out for 500ms (so grazing the edge doesn't flicker) — and each change drives `setWindowButtonVisibility` and a `window:pointer-inside` message that the page turns into the button's visibility (`miniChromeVisible` in `App.jsx`). **Why not mouse events in the page:** the card is a `-webkit-app-region: drag` area (it can be dragged from anywhere), and Electron gives drag areas to the OS, so the page never sees the pointer over them — an earlier version listened for `mousemove`/`mouseout` and only worked over the no-drag controls (buttons, seek line), which is exactly what was reported. Polling from the main process has no such blind spot and also works while the window isn't focused. The renderer only says when mini mode starts and stops (`window:mini-chrome-tracking`). `pointerTracker.mjs` is Electron-free (cursor, bounds, clock and timers injected) and unit-tested with fake timers; verified end to end against the real app by warping the real cursor (outside → hidden; over the draggable background → shown within ~100-200ms; leaving → hidden after ~650ms; button restore from a mini launch → 1000x760). Not verifiable from here: the native traffic lights themselves (screen capture isn't available to the test environment) and any effect of macOS app-nap if the window is completely covered by other windows (timers may slow down, but nothing is visible then). The card's 26px top padding gives them their own strip above the artwork. Whether hover still reveals them while the window is *unfocused* has not been verified on a real screen.

**Verification, and its limits.** Layout, hit-testing, hide/restore, playback and seek were checked live with a real-config `BrowserWindow` resized through 440×300, 380×180, 1000×200 and 600×420, plus the smoke suite's "Mini player" block (breakpoint edge, controls actually clickable via `elementFromPoint`, play/pause toggles the real `<audio>`, page and library survive the round trip). As everywhere in this app, `capturePage()` cannot render the vibrancy, so how the glass looks, and the traffic lights' hover behavior, can only be judged on a real screen.

## Primary navigation (nav pill)

The title-bar strip holds **Home | Library** — a centered glass tab switch (`.nav-pill` / `.nav-pill-btn` in `index.css`, `position: fixed; top: 5; left: 50%; zIndex: 51`) — and a separate round **+ Add music** button (`.nav-add-btn`, `top: 5; right: 16`). The traffic lights own the left edge, so there's no collision at any width (at 380px the centered tabs sit between them and the + button). **Search** is a third, round button just left of the + (see "Search" below). Both title-bar controls stay on every page at every width, including narrow Now Playing's full-screen takeover; the tabs and the search and + buttons are `inert` + `opacity: 0` (not removed) while the mini player shows.

Order is **Home, then Library** (Home first, the usual convention). Tabs and the + button are deliberately separate controls: the tabs are two *places*, the + is an *action* — grouping them as four identical buttons (the previous design) hid that, and at narrow widths the labels vanished so "+" and the Library icon took guessing. **Narrow windows:** the tabs are icon-only *except the active one, which also shows its name* (`.icon-only` on the inactive tab), so you always see where you are in words. `Add` calls the same `handleAddFiles` the old sidebar's "Add Files" button did; drag-and-drop remains the only other entry point.

**Active state** — the current view (Home or Library) gets a highlighted background (`.nav-pill-btn.active { background: var(--glass-active) }`) with text staying the same bright neutral as hover, **not** `--accent-color`. An earlier version colored the active label accent-blue; it was dropped as a jarring flash of color in an otherwise monochrome control — a deliberate, user-confirmed departure from the app's usual "accent = on/selected" toggle language. The persistent, stronger-than-hover background is the entire signal. The + button never carries `.active`; neither does either tab on Now Playing.

History: this replaced a four-segment pill (Search / Add / Library / Home, top-right) whose search segment expanded in place and auto-closed on a 2s hover timer (a bottom "search dock" that swapped places with the player pill came and went in between, and was dropped because the pair never looked right together), which itself replaced a collapsible icon-rail sidebar with a narrow-mode drawer (`sidebarCollapsed`, `⌘\`, `.sidebar-drawer` — none of that exists any more).

### Search (`SearchPanel.jsx`, a floating panel)

A round **search button** (`.nav-search-btn`, `top: 5; right: 56`, left of the + button) in the title bar, or **⌘F** (Edit > Find, `electron/main.js` → `menu-find` IPC, the same round-trip as Select All since a menu accelerator never reaches the page as a keydown), opens `SearchPanel.jsx`: a Spotlight-style panel (`.search-panel`, `position: fixed; top: 92px; z-index: 40`, centered, `min(580px, 100vw - 24px)` wide, radius 18, dark glass) floating over whatever page is showing. It is `inert` + `opacity: 0` with the rest of the title bar while the mini player shows, and is never rendered there.

**Rendered at the root of `App.jsx`, not inside `.glass-panel`.** The card's `backdrop-filter` makes it a stacking context (and the containing block for `position: fixed` descendants), so nothing inside it can out-rank a sibling layer — Chill mode's full-window photo (z 30) used to cover the panel completely while the search button appeared to do nothing. That is also why `top` is `92px`: the 42px title strip plus the 50px it used to sit below the card's top. The smoke suite asserts the panel is the topmost element at its own position over Chill mode, and its position in normal mode.

**The panel searches the whole library**, grouped **Artists** and **Albums** (round / square tiles, via `splitArtists`, each opens its own Details page) and **Songs** (ranked: title starts with, then contains, then matched on another field; click plays; 20 at a time with "Show more"). Nothing is shown until there is text. Choosing a song keeps the panel open so you can keep choosing; choosing an artist/album navigates, which closes the panel (see page change below).

**Live filtering behind it.** On Library and Details pages the same text *also* filters that page's own list while you type, so the panel is a way to find things and the list is the place to act on them:

| Page | What the text also does |
| --- | --- |
| Library | Filters `visibleTracks` (Title, Artist, Album, Year, Genre — `trackMatchesQuery` in `trackUtils.js`, the single shared definition). Applies **only while `view === 'library'`** (`librarySearchQuery` in `App.jsx`), so the box can never silently filter the Library behind a Details page or Home (playback order walks that list). |
| A Details page (artist/album/year/quality/language/mix/missing metadata) | Filters *that page's own tracks* (`HomeDetailView`'s `searchQuery` prop, `listTracks`), with a "No tracks match" empty state. Only the **list** is filtered: the subtitle's track count/duration, the hero artwork and whether Play/Shuffle are enabled keep reading the full set. The panel starts **scoped to the page** (Songs only, placeholder "Search <page>") and a chip (`.search-panel-chip`, "In Kid Cudi ⌄") widens it to the whole library. `HomeDetailView` reports its unfiltered tracks up through `onTracksChange` so the panel can scope to them. |
| Home | Cards, not a list, so nothing is filtered in place; the panel's grouped results are the thing. |
| Now Playing (either width) | The panel opens **over** Now Playing — you don't leave it. Playing a song keeps you there; picking an artist/album opens its Details page with the back button returning to Now Playing (`openDetailFromSearch` sets `homeDetailOrigin`). |

**Closing, and what an outside click does.** Close with **Escape** (a window-level listener, so it works even when focus moved to a row; clears the text first, then closes), the **X** (clears first when there is text; `onMouseDown` is `preventDefault`ed so the field doesn't lose focus), **changing page**, or a **primary-button click anywhere outside the panel** (a capture-phase `pointerdown` on `document` in `SearchPanel.jsx`). That click **only closes**: it is swallowed, so nothing behind the panel — a row, a card, a tab, a hero button — reacts to it; the user clicks again once the panel is gone. Because the panel unmounts at once, the swallowing is done by `swallowGesture()` with listeners on `window` (capture) for `pointerdown/up`, `mousedown/up`, `click` and `dblclick` that remove themselves ~450ms after release (long enough to eat the second click of a fast double-click; 5s fallback if no release arrives). Not treated as outside: the panel itself, the search button (its own handler refocuses an open panel), the track context menu and modals, and right/middle clicks. Title-bar drag areas never deliver pointer events to the page, so dragging the window doesn't close it.

**Does the filter survive dismissal?** On Library and Details, yes: an outside click calls `onDismiss` → `dismissSearch` in `App.jsx`, which closes the panel but leaves `searchQuery` filtering the list, so the filtered rows are usable (single and double click) once the panel is gone. The search button shows `.active` while that is the case (`searchFilterActive`), so a filtered list is never a silent surprise; reopening the panel shows the text (selected) and **Escape/X are the clear paths**. On Home and Now Playing nothing is filtered, so dismissal clears the text with the panel. Escape/X-on-empty call `onClose` (`closeSearch`), which always clears. A page change clears everything, via an effect keyed on `searchPageKey` (`view` plus the open Details item; Now Playing is its own stable key), so a filter never lingers on a page where its panel isn't. Opening while already open just refocuses the field.

Smoke hooks: `.nav-search-btn`, `.search-panel`, `.search-panel-input`, `.search-panel-chip`, `.search-panel-x`, `.search-panel-song`. Library-page rows are told apart from the panel's own song rows with `.track-row:not(.search-panel-song)` (the panel's songs reuse `.track-row`). The smoke suite covers live filtering on Details (including the hero staying intact), page scope and chip widening, close-on-page-change, outside-click close (swallowed gesture, filter kept on Library and the button's active state, inside/right-click ignored), grouped Home results, "No results", clearing the text, Escape, and opening over Now Playing.

## Track context menu (`trackMenu` state)

The dropdown is a `position: fixed, zIndex: 1000` div rendered at the root of `App.jsx`. Positioning logic:
- **Vertical:** opens downward (`top: anchorRect.bottom + 4`) when the button is in the upper half of the screen; opens upward (`bottom: window.innerHeight - anchorRect.top + 4`) when in the lower half. This prevents clipping for buttons near the bottom (e.g. the player panel ⋮).
- **Horizontal:** anchors to the right edge when the button is past the screen midpoint, otherwise to the left edge.

**Close triggers:** click anywhere on the document, scroll the `.scrollable` container, or press **Escape**. The Escape listener is added in the same `useEffect` as the click listener and cleaned up together. The player panel ⋮ button additionally **toggles** — clicking it while the menu is open closes it (via `if (trackMenu) { setTrackMenu(null); return; }` before the open logic, with `stopPropagation` preventing the document click listener from double-firing).

## IPC channel surface (`electron/preload.cjs` ↔ `electron/main.js`)

- `fs:readFiles` — opens a native file/folder picker, parses any audio files found.
- `fs:parseFiles` — parses an explicit list of paths (used for drag-and-drop from Finder — `App.jsx`'s `handleDrop` resolves each dropped item's real path via `webUtils.getPathForFile`, which works the same for a folder as a file, and hands the raw list straight to this channel with no folder-specific renderer code). Both are index-aware: a path whose mtime matches its cached index entry is served without touching `music-metadata`.
- **Folder expansion (`electron/folderScan.mjs`, `expandToFiles`)** — both channels above run every path through this first: a file passes through untouched, a directory is walked **recursively** (a real library is `Artist/Album/track.mp3`, so a single-level `readdir` would miss everything two levels deep — this used to be main.js's inline one-level loop, which is what `fs:readFiles`' own folder picker was silently limited to before this existed). Entries starting with `.` are skipped at every level (`.DS_Store`, `.git`, etc.) rather than relying on the extension filter to catch them. No extension filtering happens here — `parseFilePaths` already does that once, so `expandToFiles` returns every non-hidden file found and lets that filter be the single source of truth for what counts as audio. Pure (`fs/promises` + `path` only, no Electron import), unit-tested directly in `folderScan.test.mjs`; the recursive-directory and IPC-integration cases are also covered by the smoke suite (`electron/smokeTest.mjs`'s "Dropping a folder..." block) since that's the only way to exercise the real `window.electronAPI.parseFiles` round trip.
- `fs:readArtwork` — returns the file's full-resolution embedded artwork as a base64 data URL (or `null`), behind a small LRU keyed `path::mtime`. **Consumers: Now Playing, the Tag Editor, and the Home detail hero** (`HomeDetailView.jsx`, upgrading its own thumbnail-quality hero image once mounted at a much bigger display size — see "Detail hero redesign" above) — library track objects never carry base64 (see "Metadata index, thumbnails, play stats" below).
- `stats:recordPlay` — increments `playCount` + stamps `lastPlayed` for a path; returns the new stats. The renderer calls it when the current track crosses 50% (once per listen-through — the guard re-arms below 25%, so repeat-one loops count again but mid-track scrubbing never double-counts).
- `library:updated` (main→renderer) — background reconciliation pushes after the instant cached load: `{ updated: Track[], removed: string[] }`. The renderer merges updates by filePath and routes removals through `removeTracks`.
- `reindex:progress` (main→renderer) — `{ done, total }` while a background (re)index runs (only emitted when >20 files need parsing); surfaces as a toast.
- `fs:writeTag` — writes tags, cover art, and lyrics back to disk. The handler routes by file extension:
  - **`.mp3`** — `node-id3` path (unchanged). Renderer sends `picture` (base64 data URL or `null`) and `lyrics` (string or `null`); handler maps these to `node-id3`'s `image`/`unsynchronisedLyrics` shapes. **`picture: null` means explicit removal** — detected via `'picture' in tags && tags.picture === null`, then handled with `NodeID3.read` + `delete existingTags.image` + `NodeID3.write` because `node-id3` 0.2.x can't remove individual tags via `update`.
  - **`.flac`** — `writeFlacTags()` in `main.js`: pure-JS FLAC metadata block rewriter. Reads the file, parses the block chain, drops old `VORBIS_COMMENT` (type 4) / `PICTURE` (type 6) / `PADDING` (type 1) blocks, writes fresh ones, appends 8KB padding, then appends untouched audio data (never touched). Maps: `year → DATE`, `lyrics → LYRICS`, `albumArtist → ALBUMARTIST`; empty/null fields are omitted (not written as empty strings). **Leading ID3v2 header stripping:** some encoders (Picard, iTunes) prepend a non-standard ID3v2 tag before the `fLaC` marker. `writeFlacTags` detects this (bytes 0–2 === `ID3`), computes the ID3v2 block size from the synchsafe integer at bytes 6–9 (plus 10-byte footer if flag `0x10` is set), skips past it to find `fLaC`, and omits the ID3 header from output — Vorbis Comment is the correct FLAC metadata container. The block parser has a `if (pos + 4 > file.length) break` bounds guard before `readUIntBE(pos+1, 3)` to prevent `RangeError` on malformed files. Writes directly to `filePath` via `fs.writeFile` (not a sibling temp file) — creating a new `.swtmp` file in the same directory requires directory-level write permission that macOS may not grant for protected folders (Desktop, etc.), while overwriting an existing file only needs file-level permission.
  - **`.wav`** — `writeWavTags()` in `main.js`: uses `NodeID3.create()` to build an ID3 payload buffer (no file I/O), then splices/replaces the `id3 ` RIFF chunk in the WAV structure without touching audio chunks. Writes directly to `filePath` via `fs.writeFile` (same rationale as FLAC — no sibling temp file).
  - Other formats (OGG, M4A, AAC) — returns `false`; "Edit Tags…" context menu item is disabled for these in the renderer.
- `fs:writeTag` returns `{ success, thumb }` (the renderer tolerates a legacy `true`). On success the handler also syncs the index entry (new field values + fresh mtime, so the next launch serves them without a re-parse), regenerates or removes the thumbnail, and invalidates the artwork LRU for that path.
- `fs:revealInFolder` — calls `shell.showItemInFolder` to reveal a file in Finder.
- `fs:checkPaths` — takes `string[]` of file paths, returns `boolean[]` (true = file accessible). Used for missing-file detection (see below).
- `library:load` / `library:save` — session state (`{ trackPaths, currentTrackPath, currentTime }`) in `userData/library.json`, format unchanged. **`library:load` is also where a file-open launch is arbitrated** — see "Launch behavior" above; its return adds `autoPlay` and `failedOpenCount`. On a normal launch it returns **instantly**: every path is served from the metadata index (unknown paths get a renderable placeholder with `pending: true` and a filename-derived title), then a background pass stats all paths, re-parses only new/mtime-changed files, drops missing ones, and patches the renderer via `library:updated` / `reindex:progress`. This is also the migration path for pre-index installs: first launch serves placeholders and heals in the background.
- (There is **no** native right-click menu IPC. Earlier revisions of this file listed `show-track-context-menu` / `context-menu-command` / `remove-tracks` / `play-next-tracks` / `show-now-playing-menu`; none of those channels exist in `main.js` or `preload.cjs`. The context menu is the renderer-side `trackMenu` dropdown described above.)
- `window:restore-from-mini` (renderer→main, fire-and-forget) — `{ width, height }` (the last non-mini window size, or `null`); main grows the sending window back to it, clamped to its display (see "Mini player").
- `window:mini-chrome-tracking` (renderer→main, fire-and-forget, boolean) — starts/stops the main process's pointer tracker for the sending window while the mini player shows (see "Mini player"). Starting hides the traffic lights and reports the pointer's current state immediately; stopping restores the traffic lights. Replaced `window:set-buttons-visible`, which the renderer drove from page mouse events that never fire over the card's drag area.
- `window:pointer-inside` (main→renderer, boolean) — whether the pointer is over the window (with the 500ms hide delay); drives the mini player's expand button, in step with the traffic lights.
- `window:chill-chrome-tracking` (renderer→main, fire-and-forget, boolean) — starts/stops `electron/pointerMotion.mjs` for the sending window while Chill mode is active (see "Chill mode"). Stopping — for any reason: chill exits, Now Playing is left, narrow/mini, the window closes, the page reloads (`did-start-loading`) — restores the traffic lights, unless the mini player is tracking the same window (it owns them then).
- `window:pointer-moved` (main→renderer) — the OS cursor moved to a new position inside the window (polled at 100ms). Exists because the title strip is a drag area the page never sees the pointer over; wakes Chill mode's idle chrome.
- `window:set-buttons-visible` (renderer→main, fire-and-forget, boolean) — Chill mode's idle clock asking for the traffic lights to be hidden/shown; honoured only while chill tracking is on. All traffic-light changes go through `setWindowButtons(win, visible)` in `main.js`, which records the last requested state on the window (`win.__sonusButtonsVisible`) because macOS has no getter and the smoke suite asserts it.
- `open-external-url` (renderer→main) — opens a URL in the default browser via `shell.openExternal`.
- `open-external-file` (main→renderer) — `{ tracks, failedCount }`, fired when a file is opened via macOS "Open With" or double-click **while the app is already running**; the renderer replaces its whole library with it (see "Launch behavior" above). A cold launch never uses this channel — it resolves inside `library:load` instead.
- `clipboard:readImage` (renderer→main) — reads an image from the system clipboard via `clipboard.readImage()`; returns a base64 data URL string or `null` if the clipboard holds no image.
- `clipboard:writeImage(dataUrl)` (renderer→main) — writes a base64 data URL to the system clipboard via `nativeImage.createFromDataURL()` + `clipboard.writeImage()`.
- `menu-find` (main→renderer) — fired by Edit > Find (⌘F); opens the search field beside the player for whichever page is showing. Same IPC round-trip as Select All, for the same reason (see "Custom application menu").
- `menu-command` (main→renderer) — one string per File > Add Music / Controls item (`add-music`, `play-pause`, `next`, `previous`, `toggle-shuffle`, `cycle-repeat`, `go-to-current`, `enter-chill`; the list is `MENU_COMMANDS` in `electron/appMenu.mjs`). `App.jsx` runs the handler the on-screen control already uses; see "Custom application menu".
- `menu:set-state` (renderer→main, fire-and-forget) — `{ hasTrack, isPlaying, isShuffle, repeatMode }`, sent whenever one changes, so the Controls menu can show Play vs Pause, the shuffle tick and the repeat mode, and grey out items that need a track.
- `menu-select-all` (main→renderer) — fired by the Edit > Select All menu item; see "Custom application menu" below for why this exists as an IPC round-trip instead of a plain renderer keydown listener.
- `open-tag-editor` (renderer→main, invoke) / `tag-editor:load` (main→renderer) / `tag-editor:saved` (main→renderer) / `tag-editor:resize` (renderer→main, fire-and-forget) — the Tag Editor window's IPC surface; see "Tag Editor" below.
- `service-action` (main→renderer) — `{ action: 'add-to-queue' | 'play-next', tracks }`. An alternate delivery channel for the same file-open pipeline as `open-external-file`, used when the trigger was a Finder Services menu entry rather than a double-click/Open With. Deliberately a separate channel: Services *queue*, a double-click *replaces*. See "Finder Services integration" below.

The "add files when queue is non-empty" prompt is a **renderer-side dialog** (`AddTracksDialog.jsx`, rendered in `App.jsx`; see "Add-songs dialog" below) — there is no `dialog:askQueueAction` IPC channel.

Metadata parsing (`parseFilePaths` in `main.js`) runs through a small hand-rolled bounded-concurrency pool (`mapWithConcurrency`, limit 8) rather than sequentially — preserves original file order (pre-sized results array indexed by position) while parsing in parallel.

## Launch behavior: what library the app starts with

Three ways in, three outcomes. `electron/main.js` decides all of them — the renderer never arbitrates.

| Trigger | Result |
| --- | --- |
| Finder double-click / "Open With" | The opened files **replace the entire library** and the first (by file name) starts playing. No confirm dialog. Persists like any other library change — the previous library is overwritten in `library.json` and is not recoverable. |
| Dock / Launchpad launch | Saved session restores, current track paused at its saved position. |
| Finder Services | Saved session restores, then the files are appended/inserted. Playback is untouched. |
| Drag-and-drop, or the title bar's + Add button | Confirm modal (Play / Play Next / Add to Queue / Cancel) when the library is non-empty; straight to playing when it's empty. **This is the only surviving use of that modal.** |

**`library:load` is the single arbitration point.** It resolves the whole question and returns one already-correct answer, rather than letting the renderer restore the saved session and then having an `open-external-file` push wipe it. That older shape raced (the instant index-backed restore always won, so every double-click hit the confirm modal), flashed the old library on screen, and started a background verify over every path it was about to discard. The payload gained two fields: `autoPlay` (true only for a file-open launch — a restored session must come back paused) and `failedOpenCount`.

**Never return an empty library on a failed open.** If every opened file fails to parse, `library:load` falls through to the saved session and reports `failedOpenCount`; the renderer toasts. Returning `{tracks: []}` and letting the file-open push fill it in later is wrong — the renderer's 500ms debounced save would persist the emptiness, permanently, before the files arrived.

**Batch settling.** macOS fires one `open-file` per file with no ordering guarantee. A batch opens on the first event and settles `OPEN_FILE_SETTLE_MS` (100) after the last; both consumers wait for that settle, so neither ever sees a partial selection. Paths are then sorted by file name (`sortByFileName`, `electron/launchFiles.mjs`) so "the first track" is deterministic.

**`libraryLoadServed` is load-bearing — do not remove the guard in `flushOpenFiles`.** `did-finish-load` force-flushes any pending batch (it has to: `webContents.send` doesn't queue, so a batch that settled before the page loaded would be lost). But that flush fires *while* `library:load` is still awaiting the same batch, and stole it — verified live, the cold-launch path silently fell back to the session with `flushOpenFiles` count 1. The fix is explicit precedence, not another timing tweak: a pending batch belongs to `library:load` until it has served the renderer, at which point `loadLibraryState`'s `finally` hands the claim back and re-triggers the flush (which is how a **Services** batch — deliberately not consumed by `library:load` — still gets delivered). A 3s safety net in `did-finish-load` releases the claim if the renderer never asks for its library at all.

**`replaceLibraryWith` (`App.jsx`)** is the single renderer-side "this is your library now" path, shared by the file-open push and the modal's Play. It clears `playbackHistory` and `forcedNextQueueRef` — both hold `filePath`s, and those tracks cease to exist the moment the library is swapped (`playPrev` would otherwise jump to a track that isn't in the list). It also clears `homeDetailItem` and lands on Library, **except** in Now Playing, which stays put because it simply swaps to the new track and still reads correctly.

**Nothing slow sits in front of the window.** `app.whenReady()` kicks off the index load and creates the window without awaiting it; the Finder Services install is fire-and-forget *after* `createWindow()` (an install only affects the Finder menu from the next launch onward, so nothing on this launch depends on it). Measured: the index load is ~4.5ms at 2k tracks, ~18ms at 10k, ~37ms at 20k (12.9MB) on a warm cache; the first-run services install ~3ms. Modest, but it was all pure blocking before the window existed.

**Every path that reads the metadata store must `await ensureStoreLoaded()` first** — `parseFilePaths`, `resolveInitialLibrary`, `verifyLibraryInBackground`, `stats:recordPlay`, `syncIndexAfterTagWrite`. This is not a subtle correctness issue: an unloaded store reports every path as unknown, so `library:load` serves `pending: true` placeholders for the *entire* library and kicks off a full background reindex of files that were already indexed. The smoke suite asserts a restored session carries real metadata rather than placeholders, which catches that symptom — though note it can't catch a missing await on its own, since by then the store has always finished loading anyway. Treat the await as the invariant; the assertion is a backstop.

**Testing the cold-launch path.** macOS only delivers `open-file` to an app it has registered, so this is invisible to `npm run dev`. `electron . --open-file=<path>` (dev/unpackaged only) seeds the same batch the real Apple Event would. Combined with `--smoke` it runs a dedicated cold-launch assertion set — including that `flushOpenFiles` was never reached — and exits:

```
npx vite build && npx electron . --smoke --open-file=/tmp/a.mp3 --open-file=/tmp/b.mp3
```

The seeded cases in the main smoke run (`seedOpenFileBatch`) inject an *already settled* batch, which deliberately bypasses that ordering — they cover arbitration logic, not launch sequencing. Both are needed.

## Finder Services integration ("Add to Queue" / "Play Next")

Selecting audio files in Finder and right-clicking → Services offers **"Add to Queue in Sonus"** and **"Play Next in Sonus"**. Both restore the saved session and then queue the files — appending, or inserting after the current track — with no confirm dialog and **without changing what is playing**. (A double-click on the same files does something entirely different: it replaces the library outright. See "Launch behavior" above.) Both are installed **by the app itself**, with no manual user setup — a hard requirement, since this machine only has Command Line Tools (no full Xcode), ruling out a real native `NSServices` provider compiled into the app bundle.

**Mechanism:** a Service doesn't have to be answered by Sonus's own native code — macOS's own Automator runtime can answer it. Each bundle in `electron/resources/services/` is a hand-authored Automator "Service" (`Info.plist` declaring `NSServices` with `NSMessage: runWorkflowAsService` and `NSSendFileTypes: [public.audio]`, plus `document.wflow` — Apple's verbose plist schema for a single "Run Shell Script" action). No compilation step; they ship as static resources (`package.json`'s `build.extraResources`: `electron/resources/services` → `services` in the packaged app) and are copied into `~/Library/Services/` from `app.whenReady()`. Packaged-only (`app.isPackaged` guard — dev mode has no installed `.app` for `open -a "Sonus"` to target, and writing into the user's real `~/Library` as a side effect of `npm run dev` isn't appropriate).

**Install policy is versioned, not first-launch-only** (`installFinderServices` / `serviceInstallAction` in `electron/finderServices.mjs`, Electron-free and unit-tested against temp dirs). A `services-installed.json` marker in `userData` records which version of each bundle was installed:

| Bundle on disk | Marker | Action |
| --- | --- | --- |
| absent | no record | install (first run) |
| absent | has record | **skip** — the user deleted it; that choice isn't fought, even across version bumps |
| present | stale or no record | overwrite |
| present | current | skip |

The "present + no record" row is the migration case: v1 shipped without a marker, so an existing bundle gets replaced. **Bump `SERVICES_VERSION` whenever a shipped bundle's contents change**, or existing installs keep a stale copy forever. The directory is scanned rather than the bundles being named, so adding a third Service later needs no code change here. Installs replace wholesale (`rm` then `cp`) rather than copying over — otherwise a file dropped in a newer version would survive on disk.

**The flag file — how "queue, don't replace" crosses the process boundary:** each Service's shell action is `mkdir -p "$HOME/Library/Application Support/Sonus" && printf '<action>' > ".../service-action.flag" && open -a "Sonus" "$@"`. `open -a` can only pass file paths through the OS `open-file` Apple Event; there's no channel for "and queue these instead of replacing the library". The flag is that channel — written to the same `userData` directory Sonus already uses for `library.json`. It is read **once per open-file batch** (`getBatchAction()`) and deleted on every read, and ignored if older than 5 seconds — generous for launch/wake latency, tight enough that a stale flag can never leak into an unrelated later double-click. Only the two known action names are accepted; anything else is treated as no flag.

**Read-once matters:** both `library:load` (deciding whether this is a file-open launch) and `flushOpenFiles` (delivering the batch) need the answer, and reading consumes it. The promise is memoised per batch and reset when the next batch opens.

**The legacy flag is still honoured.** The pre-2.0 bundle wrote `service-add-to-queue.flag` (a bare `touch`, no action name). It's mapped to `add-to-queue` because the installer can only update that bundle *at launch*: a user who triggers the old Service before ever launching the new build would otherwise fall through to the file-open path and **have their library replaced**. Both flag files are consumed on every check so a stale one can't fire later. Safe to delete once every install has launched at least once.

**Delivery:** `flushOpenFiles` sends `service-action` (`{ action, tracks }`) instead of `open-external-file`. A Services batch is deliberately *not* consumed by `library:load` — it falls through to the saved session, and `loadLibraryState`'s `finally` hands the claim back so the batch is delivered once the renderer has a library to apply it to. `App.jsx`'s `queueTracksFromService` dedupes by `filePath` for `add-to-queue` (an already-present track is a no-op — there's no ordering to resolve). `play-next` deliberately does **not** dedupe the same way: every selected track is queued regardless of whether it was already in the library, since Play Next is an explicit "play this file next" request, not a request to add a row — an already-present track's row is instead pulled out and reinserted right after the current track, alongside any brand-new ones. Either way, unshifting onto `forcedNextQueueRef` is what actually drives playback order (see `playNext()`); repositioning rows alone isn't enough, since shuffle ignores list position entirely. The drag-and-drop / "Add Files" confirm modal's Play Next button (`resolvePendingTracks`) follows the identical shape for the same reason.

## Metadata index, thumbnails, play stats (`electron/indexStore.mjs` + `main.js`)

The scale architecture: **no full-resolution base64 artwork ever lives in renderer heap.** Three persistent stores in `userData`, all plain JSON (no native deps — `indexStore.mjs` isolates storage so a future SQLite swap is contained):

- **`library-index.json`** — parsed metadata per filePath (`{ version, tracks: { path: { …fields, mtimeMs, dateAdded, thumb } } }`). Debounced 1s, written atomically (temp + rename — fine in userData; *never* copy this pattern to `fs:writeTag`, which deliberately writes music files in place for macOS permission reasons). A version mismatch or corrupt file just means an empty index → background reindex.
- **`play-stats.json`** — `{ path: { playCount, lastPlayed } }`, kept **separate** so bumping a play count never rewrites the big index. Debounced 2s. Both stores flush on `before-quit`.
- **`thumbs/`** — one ≤300px JPEG (q70) per track, named `sha1(filePath)`, sharded by first 2 hex chars, written by `writeThumb` in `main.js` via `nativeImage` (if Chromium can't decode the source — WebP/GIF embeds — the original bytes are stored untouched with their real extension). Served by the privileged `sonus-thumb://art/<sha1>.<ext>?v=<contentHash8>` protocol; the `?v=` busts the renderer's HTTP cache when art changes. The scheme **must** keep `corsEnabled: true` in `registerSchemesAsPrivileged` — without it renderer `fetch()` of thumbnails is refused outright regardless of response headers (`<img>` would still work, but `fast-average-color` fetches).

Track objects carry `thumb` (a tiny URL string) + text metadata + `dateAdded` (birthtime on first index / reindex, `Date.now()` for user-initiated adds — preserved across re-parses) + `playCount`/`lastPlayed`. Rows, the player bar, Home cards, and `fast-average-color` all use `thumb` directly; **`mediaSession` artwork is a `blob:` URL fetched from the thumb** (`MediaImage` rejects custom schemes — passing `sonus-thumb://` logs an error and shows no art in the macOS now-playing widget; the previous blob URL is revoked on replace via `mediaArtUrlRef`); **Now Playing and the Tag Editor** load full-res on demand via `fs:readArtwork`, showing the thumbnail upscaled until it resolves. The Tag Editor **blocks Save while its full-res load is pending** (`editArtLoading`) — the WAV writer rebuilds the whole tag chunk, so saving early would silently strip embedded art.

## Artwork normalization and repair (`electron/artwork.mjs`)

`music-metadata` returns artwork in `metadata.common.picture[0]` as `{ format, data }`. `normalizePicture` (pure, unit-tested — no Electron imports) handles three classes of corruption; `pictureToDataUrl` wraps it for `fs:readArtwork`:

1. **Bare extension format strings** — some taggers write `"jpg"` instead of `"image/jpeg"`. Normalized via a lookup table; `"image/jpg"` is also corrected to `"image/jpeg"`.
2. **BMP format** — skipped entirely (set to `null`). Uncompressed BMP embeds can be 500KB+; Chromium renders them poorly as blobs.
3. **Apple Music/iTunes APIC header stripping** — Apple's ID3 writer produces APIC frames where `music-metadata` strips leading bytes from the image header. Two variants:
   - **JPEG:** first 5 bytes (`FF D8 FF E0 00`) missing. Detected by checking that bytes 1–4 equal `JFIF` (`4A 46 49 46`). Fix: prepend `Buffer.from([0xFF, 0xD8, 0xFF, 0xE0, 0x00])`.
   - **PNG:** up to 9 bytes missing (8-byte PNG signature + first byte of IHDR chunk length). Detected by finding `IHDR` (`49 48 44 52`) within the first 16 bytes at offset > 0. Fix: prepend `PNG_PREFIX.slice(0, 12 - ihdrOffset)` where `PNG_PREFIX` = PNG signature + `00 00 00 0D` (IHDR chunk length). Formula works for any prefix length 1–11.
   
   Both checks only run when the format is the correct type but the leading magic bytes are wrong — they will not trigger on legitimately valid images.

## Custom application menu (`buildAppMenu` in `main.js`)

`main.js` calls `Menu.setApplicationMenu()` with a hand-built template instead of leaving Electron's auto-generated default menu in place. This exists for exactly one reason: **Cmd+A**. Electron's default menu binds Edit > Select All to `role: 'selectall'`, and that role's accelerator is handled natively, before the keystroke ever reaches the renderer — a `window.addEventListener('keydown', ...)` listener (the pattern used for Backspace/Delete in `App.jsx`) never sees it. Reassigning `.click` on the existing role-based `MenuItem` also does not work — the native role behavior still wins. The only fix is rebuilding the whole menu from scratch with that one item changed to a plain `accelerator + click` (no `role`), which sends `menu-select-all` over IPC to the renderer.

Everything else in the template (`role: 'appMenu' | 'viewMenu' | 'windowMenu'`, the Edit items, plus Substitutions/Speech submenus) replicates Electron's default exactly, so Quit/Hide/Cut/Copy/Paste/Undo/Redo/DevTools/zoom/fullscreen etc. are unaffected. The File menu is the exception, and there is a Controls menu that Electron's default does not have: see [File and Controls menus](#file-and-controls-menus) below. If you ever need another `role: 'selectall'`-style override, this is the only place it can go — don't try to patch the default menu instead.

In `App.jsx`, the `onSelectAll` handler checks `document.activeElement` first: if a text `<input>`/`<textarea>` is focused, it calls the native `.select()` on it (replicating what the role used to do for in-field select-all, e.g. in the Tag Editor); otherwise it routes to `activeSelectionRef.current?.selectAll()` — the Library's or the open detail view's selection, whichever is on screen (see "Tracklist engine"). This check is required — without it, removing `role: 'selectall'` would silently break Cmd+A-to-select-text inside the Tag Editor's inputs.

### Add-songs dialog (`AddTracksDialog.jsx`)

Opened (as `pendingNewTracks` in `App.jsx`) when drag-and-drop, the title bar's + button or File > Add Music adds songs to a **non-empty** library; with an empty library the songs just play. It names what is being added (`describeAddition` in `trackUtils.js`: one song's title and artist, or "N songs" led by the first) and offers **Play now**, **Play next**, **Add to queue** and Cancel. The buttons carry only their names; what each does (**Play now**: "Replaces your current library" — it really does, `replaceLibraryWith`, which the old dialog never said; **Play next**: right after the current song, or at the top when nothing is playing; **Add to queue**: at the end of the library) shows in a single hint line under them (left of Cancel; under the row in mini) for the button the pointer is over, else the focused one, which starts as Play so the line always says what Enter will do. Escape and a click outside cancel; Play is focused so Enter confirms it.

- **Two layouts, one component.** Regular (also used for narrow windows, which only shrink its width to `min(380px, 100vw - 32px)`): a row per action with a one-line hint. Compact (`compact={isMiniLayout}`): one row of three buttons, Cancel in the header, the hint line underneath. The mini player's window is only 180-420px tall and the macOS traffic lights sit in its top-left corner, so the compact dialog has 30px of top padding (its title row starts at 30px) and the old fixed-340px, four-stacked-buttons dialog was clipped and overlapped them.
- **The window can still be dragged while it is open, and (regular layout) clicking outside still cancels.** First built as native `-webkit-app-region` areas (a `drag` band before the no-drag panel, the mini panel as `drag`) — and it did **not** work for the user, while every computed-style check passed: tests cannot drag a real window (`sendInputEvent` bypasses the OS drag layer), so a drag region can only ever be *asserted*, never exercised. It is now **page-driven**: `useWindowDrag` (in `AddTracksDialog.jsx`) sends `window:drag` `start` on mouse-down on the 42px `.add-dialog-drag-strip` (regular) or on the panel's background (mini) — never on a button — a `move` tick on each mouse-move while held, and `end` on release; `main.js` positions the window from the **OS cursor** (`screen.getCursorScreenPoint()`) relative to where it was at `start`. Using the cursor, not the renderer's mouse coordinates, keeps it to one coordinate system, and is what lets the smoke suite exercise it: synthetic input events carry no screen coordinates, so the test moves the real cursor (`CGWarpMouseCursorPosition`) and checks the window's position. **The click that follows a drag is swallowed** (a one-shot capture listener): the window lags the pointer, so the release can land on the backdrop, and a click there cancels the dialog.
- **Mini: the dialog IS the window** (`.add-dialog--compact`: `100vw`×`100vh`, no inset, border or radius), like the mini card itself. An inset card straddled the macOS traffic lights with its edge, and looked wrong. There is therefore no "outside" in mini; Escape and Cancel close it. The focus ring is an inset ring (a halo looked heavy on the primary button).
- **Tests:** `AddTracksDialog.test.jsx` (content, actions, focus, both layouts) and the `adddialog` smoke section, which opens it through `window.__sonusTest.openAddDialog` and measures the real layout at 1000x700, 440x760, 380x560, 440x300, 380x205 and 380x180 (not clipped, four buttons inside the panel and actually hit, no cut-off labels, title row clear of the traffic lights in mini, Escape), then runs Cancel / Add to queue / Play against the real library. Proven to fail when mini is given the regular layout.

### File and Controls menus

The File menu is no longer the `fileMenu` role (which only ever had Close Window): **Add Music… (⌘O)**, **Filled Screen Mode (⌃⌘M)**, **Narrow Mode (⌥⌘2)**, **Mini Mode (⌥⌘3)**, **Chill Mode (⇧⌘C)**, then the `close` role. A **Controls** menu sits between View and Window: Play/Pause, Next (⌥⌘→), Previous (⌥⌘←), Shuffle (⇧⌘S, a checkbox), Repeat (⌥⌘R, the label reads `Repeat: Off|All|One`), Go to Current Song (⌘L). The templates live in `electron/appMenu.mjs` and the window geometry in `electron/windowModes.mjs`, both Electron-free so vitest covers them; `main.js` only injects `send` / `setWindowMode`.

- **Chill Mode is a resize plus a message** (`enterChillMode` in `main.js`): it fills the screen like Filled Screen Mode (unless the window is already in native full screen, which it leaves alone), then sends `enter-chill`; the renderer opens Now Playing (`expandNowPlaying`) and turns Chill on. Like Next/Previous it is greyed out without a loaded song (`hasTrack`). Leaving Chill mode afterwards does NOT undo the resize, by request. If the window was narrow or mini, `chillActive` only becomes true once the resize makes it full-width, which is why it works from either.
- **Menu items are messages, not logic.** Each sends `menu-command` to the *main* window (even if the Tag Editor has focus; `sendMenuCommand` also un-minimises and focuses it) and `App.jsx` runs the handler the on-screen control uses (`handleAddFiles`, `togglePlay`, `playNext`, ...), so queue, history and the confirm modal keep one set of rules. The handlers sit in `menuCommandsRef`, refreshed every render, because the subscription is made once.
- **The renderer pushes state back** (`menu:set-state`, `applyMenuState`): labels and tick marks are changed on the live `MenuItem`s by id (`controls-play-pause`, `controls-shuffle`, ...). Next / Previous / Go to Current Song start disabled and are enabled by `hasTrack`. Note a checkbox item flips its own `checked` when clicked, so the smoke suite confirms shuffle through the pill's accent colour, not the tick.
- **The three size items also end Chill mode** (`exit-chill` → `setIsChillMode(false)`, the exit button's effect: you stay on Now Playing). Chill is a setting in the page, not part of the window size, so a resize alone left it on: Filled Screen Mode right after Chill Mode changed nothing (the window was already full), and a Narrow/Mini excursion brought Chill back when the window grew again (`isChillMode` outlives those). The message lives in the *template's* click handlers, not in `applyWindowMode`, because `enterChillMode` calls that to fill the screen and must not cancel itself. Chill Mode (⇧⌘C) is the way back in.
- **Apart from that, the three sizes are only resizes.** "Narrow" and "mini" are not states: the renderer derives them from the window's size (560 wide / 420 tall), so Narrow Mode (a fixed 440×760, capped to the display; it was once "at least 760", which kept a tall window's height and so landed on a different size from Filled Screen than from Mini) and Mini Mode (380×200) just call `setBounds`, and Filled Screen Mode sets the display's work area (menu bar and Dock stay). There are no checkmarks and no "restore": choosing another size is the way back. The window keeps its top-left corner, nudged only as far as needed to stay on its display; from native full screen it leaves full screen first (`leave-full-screen`, then resizes).
- **Accelerators that would break typing are avoided on purpose.** A menu accelerator wins over the focused text field, so Play/Pause has *no* accelerator (Space is still the renderer's own handler and keeps typing a space in Search and the Tag Editor), and Next/Previous are ⌥⌘←/→ rather than ⌘←/→ (line start/end while editing). Repeat is ⌥⌘R because ⇧⌘R is Force Reload in the View role. The smoke suite asserts that no two items in the whole menu share an accelerator.
- Go to Current Song switches to Library if needed, waits 150ms for it to be on screen and restore its own scroll, then selects and centres the row. It does nothing in the mini player (the Library is hidden there).

## Vibrancy and forced dark mode

`nativeTheme.themeSource = 'dark'` is set immediately after `app.setName('Sonus')` in `main.js`. This forces macOS's `under-window` vibrancy material to always render the dark variant, regardless of the user's system Light/Dark Mode setting. Without it, opening the app in Light Mode (or with light content behind the window) makes the vibrancy material go medium-gray — white text in Now Playing appears gray against it regardless of any CSS changes. Don't remove or comment out this line.

## Artwork-derived color (`artworkRgb` / `bgColor`)

`App.jsx` extracts a single dominant color from the current track's cover art via `fast-average-color` (`FastAverageColor.getColorAsync` on **`currentTrack.thumb`** — the 300px thumbnail is plenty for an average color and avoids touching full-res; in the same `useEffect` that sets `mediaSession` metadata on `currentTrack` change) and stores it as `artworkRgb` (`{ r, g, b }`, `null` when there's no artwork). It drives four things, all unconditional (not gated to Now Playing):
- **`bgColor`** — the app's background tint, `rgba(r, g, b, 0.5)`, applied to `.app-container` everywhere.
- **Now Playing's ambient "blur furnace"** — three blurred, independently-animated circles behind the artwork (`np-flare-1/2/3` keyframes) tinted with `artworkRgb`, paused when playback is paused. (Now lives in `AmbientFlares.jsx`, shared with the mini player — see "Mini player" — and its colour now eases between tracks.)
- **Now Playing's artwork glow** — the `boxShadow` around the artwork card and the radial glow behind it.
- **The full-width player pill's background tint and ambient halo** (`PlayerPill.jsx`, see "Player pills" above) — the one place `artworkRgb` itself feeds a *background*, not text/controls. Its own luminance-based alpha clamp (see "Player pills" above) is a deliberate, narrower version of the same caution the next paragraph describes — clamped toward 0 for a bright/near-white cover now that the pill is dark glass with white icons (was clamped toward 0 for a dark cover, back when the pill was light glass with dark icons).

`HomeDetailView`'s own hero (see "Detail hero redesign" above) does **not** use `artworkRgb`, or any color extraction of its own — it briefly did (a page-local `FastAverageColor` extraction tinting a gradient scrim), but that whole approach was replaced by a CSS mask-to-transparent once the tinted-gradient version turned out to render as a hard dark band rather than a blend (the actual surface behind the page isn't black, so fading toward black doesn't disappear into it). A mask needs no color input at all — it just reveals whatever's really behind it — so there was nothing left for a color extraction to do, and it was removed rather than left unused.

Now Playing's own text and transport controls, and the player pill's transport controls (Skip/Play/Skip/Repeat/Shuffle) — all of them now, everywhere, since the pill switched to the same dark-glass theme — are fixed `var(--chrome-text)` static colors, **not** tinted by artwork. This was tried for the pre-pill dark panel's controls specifically (matching the artwork's hue) and explicitly reverted: it made the icons hard to see against some album art, and always-white was preferred. Don't reintroduce per-track icon tinting there without raising it again — CSS has no load-bearing hook for it (`--np-slider-color` in `index.css`'s `.wow-slider` rule is dead — nothing sets it; it always renders its hardcoded fallback gradient).

## Now Playing glass backdrop — contrast guarantee

The Now Playing overlay has a full-panel glass div with `zIndex: 5`, `background: 'rgba(0,0,0,0.2)'` and `backdropFilter: 'blur(40px)'`, shared by both narrow and full-width NP. (An earlier version of this section claimed 0.55 and a pixel-verified 14.7:1 ratio; the code has been 0.2 for as long as git history goes back, so treat that as stale.) On **desktop** the scrim's strength barely matters for the artwork column's own title/artist text, because desktop's Now Playing renders its own (now-white, `--chrome-text`) title/artist and transport controls directly — see "Now Playing artwork sizing" below — independent of both this scrim and the floating pill, which hides while Now Playing is open.

**Narrow Now Playing's title/artist and the artwork's drop shadow — a real bug, and a lesson in what *not* to trust.** Narrow NP renders the title/artist directly under the artwork card. That card is `zIndex: 1` and carries `boxShadow: '0 24px 60px rgba(0,0,0,0.6)'` — offset 24px *downward*. At the window's minimum height the artwork fills its `flex: 1` row and the title block sits flush against the card's bottom edge (measured: a 0px gap), so the shadow is painted **on top of the text**, turning declared-white into a measured ~186/255 gray. At larger heights the artwork is centered with room below it and the shadow never reaches the text, which is why it looked fine most of the time — size-dependent overlap, not a regression. The fix is the title/artist wrapper's `position: 'relative', zIndex: 2` in `App.jsx`, so it paints above the shadow; nothing visual changes and the shadow still falls where it did. (Making the text literally `#fff` was tried first as the fix and did nothing, because the color was never the problem. It's now white for a different reason — see next paragraph.)

**Chrome text colors (`--chrome-text` / `--chrome-text-dim`, `index.css`).** Both pills (full-width and narrow) and Now Playing — both widths — use these two variables instead of `--text-primary` (0.95) / `--text-secondary` (0.55): `#fff` for titles, transport/⋮/back buttons, lyrics body and *off*-state toggles (on-state stays `--accent-color`); `rgba(255,255,255,0.85)` for the artist/album/year line, time labels, the "LYRICS" heading and the "No lyrics"/"Nothing playing"/"Play a track" placeholders. A user-requested, deliberate departure from the rest of the app: this text sits on artwork glow and blurred backdrops, where the standard 0.95/0.55 read as gray. The nav pill (`.nav-pill-btn`) also uses these two — it floats over the same blurred title-strip backdrop the old hamburger button did. The full-width pill briefly had its own scoped `--pill-icon`/`--pill-icon-dim` pair for a dark-on-light theme; that was reverted along with the rest of its light-glass look, and `PlayerPillNarrow` was built after the reversion, so it never had a separate pair to begin with — there's no exception here anywhere in the app anymore. The track list, its column header, Home, and the detail-page hero are **not** part of either of these and keep the standard variables; the inactive Song|Lyrics tab and the closed lyrics toggle deliberately stay dim (0.4), since dimness *is* their state indicator.

Why it took several wrong turns to find: **every standard inspection tool said everything was fine.** `getComputedStyle` reported `color: rgb(255,255,255)`, `opacity: 1`, no filter/blend-mode anywhere up the chain — all true. `document.elementFromPoint()` at the text's center returned the text itself — also true, and actively misleading: **box-shadows paint over later siblings but are never hit-testable**, so a hit-test cannot see one covering an element. Forcing the text onto its own compositing layer (`translateZ(0)`, `will-change`, `isolation: isolate`) changed nothing, because none of those change z-order. The only thing that exposed it was `webContents.capturePage()` + PIL, sampling the rendered pixels and comparing them to the artwork's own white. When a color looks wrong on screen but the CSS says it's right, go straight to pixels.

## Now Playing artwork sizing

**Full-width Now Playing has its own built-in title/artist, seek bar, and transport row now** — below the artwork, in the same left column, reusing `renderTransportControls` (the same function narrow's Song tab uses, see "Narrow layout" below) sized up (`playSize: 96` vs. narrow's `64`) rather than duplicated. Before this, full-width NP showed *only* the artwork and relied entirely on the floating pill for everything else, visible or not; the pill was always present regardless of NP state. The pill now hides while Now Playing is open (see "Player pill" above) — full-width NP is self-contained, matching how narrow's own Song tab has always worked, not floating a separate object over a "calmer" full-screen view. The seek bar reuses full-width's own mouse-hover-reveal interaction (`isSeekHovered`/`hoverTime`, the exact state the pill used before it hides here) rather than narrow's always-on touch styling — narrow and full-width Now Playing are stylistically related but not implemented as the same JSX, same as the transport row itself.

**Layout: artwork fills available space, controls dock at the bottom — not both centered together as one group.** The left column is a `height: 100%` flex column; the artwork sits in a `flex: 1` area that takes whatever height the controls block below doesn't need, and the controls block itself is `flexShrink: 0`, naturally landing at the bottom of the column since the artwork area above it consumes all the remaining flexible space. This replaced an earlier version where the artwork and the controls were centered together as a single group with a fairly conservative fixed artwork size cap (640px) — a lot of unused space around both on a large window, and no real "big artwork, controls docked at the bottom" feel. The controls block's own width is capped independently of the artwork (`min(100%, 640px)`) rather than matching the artwork's own (often much wider) size — matching it would make the seek bar/title stretch absurdly wide on a big screen, the same reason narrow caps its own block at 420 despite having a much bigger screen than 420px to work with.

**Sizing the square artwork uses CSS container queries, not a hand-computed pixel budget.** The artwork's wrapper gets `containerType: 'size'`, and the artwork itself is sized `width: min(100cqw, 100cqh, 820px)` with `aspect-ratio: 1/1` — `cqw`/`cqh` are 1% of that wrapper's own actual width/height, so this literally means "as big a square as fits within whichever of my container's own width or height is smaller," with `820px` as a taste ceiling so it doesn't get cartoonishly large on an ultrawide monitor. This self-adjusts to *whatever* the flex layout leaves available — it never needs manual re-tuning when something else in the column changes size, unlike the previous `calc(80vh - Npx)` approach this replaced, which needed a new hand-derived constant three separate times (the breadcrumb, then the transport row, then again for this pass) and was getting genuinely fragile.

**The "obvious" alternative — `width: 100%; maxHeight: 100%; aspect-ratio: 1/1` — was tried first and is wrong, confirmed live, not just in theory.** It looks like it should produce "shrink to fit both constraints," but it doesn't: `width: 100%` is a *definite* value, and CSS only recomputes width from a height that's been clamped by `max-height` when the width was `auto` to begin with. An explicit `100%` is never revisited once `max-height` clips the height, so the result is "height capped, width uncapped" — a non-square rectangle, not a smaller square. Measured directly (`getBoundingClientRect()`): `820×449.5` instead of a real square. Container query units don't have this problem, since `min(100cqw, 100cqh)` applies the exact same clamp to both dimensions symmetrically, rather than clamping one and leaving the other alone. If a future change to this area reaches for `aspect-ratio` + `max-width`/`max-height` again, verify it actually renders square before trusting it — this failure mode is easy to miss by eye at one window size (the two dimensions can look "close enough") and only shows up clearly once you actually measure both.

## Chill mode (the turntable)

A full-width-only variant of Now Playing: a photo fills **the whole window** and the playing song's artwork is part of it. There are three bundled **scenes** (see "Scenes" below): a turntable, where the artwork **is the record**, spinning calmly (one turn per 2.8s, ~21 rpm — a real record's 33⅓ rpm looked too fast on screen). A record-icon button (`.chill-enter-btn`, `Disc3`) sits left of the ⋮ in full-width Now Playing's header; an exit button in the title strip next to search (`.chill-exit-btn`) or **Escape** leaves it. Files: `src/ChillScene.jsx` (component), `src/chillScene.js` (turntable geometry), `src/chillBeach.js` (hammock geometry), `src/chillGeometry.js` (shared maths), `src/chillScenes.js` (registry), `src/useChillChrome.js` (the idle clock), `electron/pointerMotion.mjs` (cursor movement from main, unit-tested), `src/assets/chill/turntable.jpg` (2752×1536, ~1.3MB), `.chill-*` in `index.css`. No network calls; the photo is bundled.

**State.** `isChillMode` in `App.jsx` is a *preference* that survives leaving Now Playing and a narrow/mini excursion; `chillActive = isChillMode && isNowPlayingOpen && !isNarrowLayout && !isMiniLayout && !!currentTrack` is what actually renders. Narrow windows get no button and no scene (the preference is simply dormant until the window is wide again). While active, the glass blur layer and `AmbientFlares` are **not mounted** (the photo is opaque and brings its own light), so Chill mode is cheaper than ordinary Now Playing — the smoke suite's frame-time probe samples both (`metrics.frameTimeMs.chill`), measured not asserted. Escape belongs to whatever is on top first: `exitOnEscape` is `!searchOpen && !trackMenu && !pendingNewTracks`.

**One stage, scaled as a unit.** Everything lives in a box that is the photo's own 2752×1536 px (`.chill-stage`), translated and scaled by `computeFraming` — so every layer is positioned in *photo pixels* and the disc stays glued to the record at any window size. Layers, back to front:
1. the photo;
2. the **disc**: a 1000px square whose *parent* carries `matrix3d` (`discMatrix3d()`, a homography mapping the square onto the record's tilted ellipse), containing the spinning artwork (`.chill-spin`, rotated) and **fixed** layers that do not rotate — warm light (multiply), soft grooves, bevel shade, two sheen wedges (screen), the dark reflection of the bookshelf on the right/back, a window-light rim. Fixed lighting over rotating art is what reads as a real object;
3. soft contact shadows for the tonearm and the spindle pin (the real record had them; the artwork disc doesn't);
4. **a second copy of the photo clipped to the tonearm/headshell polygon, and another clipped to the spindle pin**, drawn over the disc — that is how the arm and pin stay *in front of* the artwork with zero image editing.

**Calibration is per photo.** `HOMOGRAPHY` was fitted (Levenberg-Marquardt, 23 hand-read edge points + the spindle's base → rms ≈ 0.03 of the record's radius, ~10px on a ~760px record) and `ARM_POLYGON`/`PIN_POLYGON`/shadow polygons were traced on 4–5× zooms. Replacing the photo means redoing all of it. The disc element's edge sits at `DISC_RADIUS = 1.012` of the fitted circle so the photo's own bright rim bevel never peeks out.

**Framing (`computeFraming(width, height, dpr)`)** — automatic, for any container shape: scale so the record is ≈45% of the width, but never let record + tonearm overflow the width, never magnify beyond `MAX_UPSCALE` (1.6) device px per photo px, and **always cover the container** (cover wins over everything — a big Retina window must be filled). Then centre the record horizontally and at 44% of the height (the bar along the bottom stays clear), clamped so no edge is empty. Unit tests assert coverage for 12 sizes × 2 DPRs and record-in-frame for ordinary shapes; the smoke suite checks covered / in-view / clear-of-bar at five real window shapes. **Known limit:** the photo is only 2752px wide, so a 5K display or a full-screen Retina window upscales it ~1.9× — the backdrop goes soft while the artwork on the disc stays sharp. A ≥4K version of the same scene would fix that (and need recalibrating).

**The spin — and the trap in it.** A Web Animations rotation (`.chill-spin`, `SPIN_MS` = 2800ms/turn), so at steady state it runs on the compositor with nothing on the main thread. **Do not ease it by changing `playbackRate` every frame**: that keeps the animation permanently *pending* — `currentTime` does not advance until the changes stop, so the record sits still through the whole ramp and then jumps to full speed (it reports `playState: 'running'` the whole time, which is why it's easy to miss). Measured alternative, now used: `updatePlaybackRate` in coarse 90ms steps (`tau` 0.5s spin-up / 0.55s coast-down), which tracks the expected angle to ~10ms over a 2s ramp. The animation is `pause()`d (not left at rate 0) once it has coasted to a stop. The smoke suite asserts `playState`/`playbackRate` *and that the angle actually changes*.

**Measure with layout size, not `getBoundingClientRect`.** The scene sizes itself from `clientWidth/clientHeight`: Now Playing fades in with `scale(0.96 → 1)`, and a bounding rect includes ancestors' transforms — entering Chill mode mid-fade framed it for a box 4% too small. (`ResizeObserver` would never have corrected it: a transform isn't a resize.)

**Scenes.** A scene (`chillScenes.js`: `CHILL_SCENES`) = a photo + the geometry measured from it + a framing rule, rendered by `ChillScene.jsx` (the shared shell: framing, artwork crossfade, bar, drag band, Escape) with one layers component per kind — `ChillTurntable.jsx`, `ChillBeach.jsx`. Adding one means a photo, a measurements module like `chillBeach.js` / `chillRoom.js`, an `fx` for the shared engine if it is to move (below), and a layers component (`ChillTurntable.jsx` / `ChillBeach.jsx` / `ChillRoom.jsx`). The shell draws everything scene-specific inside the **stage** (the photo's own pixel box, scaled and shifted as a unit), so overlays stay glued to the photo at any window size. Generic maths — `computeFraming(w, h, dpr, framing)`, `homographyFromQuad`/`quadMatrix3d` (a rectangle onto any quadrilateral, solved exactly from 4 corners), `polygonClipPath` — is in `chillGeometry.js`; each scene supplies a `framing` object (`keep` region, `focus` size/fraction/axis, resolution cap, vertical focus). The user's choice is remembered in `localStorage['sonus.chillScene']` (guarded: private windows / cleared data fall back to the turntable) and changed from a **picker** — a small popup of thumbnails (`ChillScenePicker.jsx`) under a scene button in the title strip (`.chill-scene-btn`, left of the exit button). The picker holds the chrome up while open, closes on an outside click or Escape (claimed in the capture phase, so Chill's own Escape-to-exit never also fires), and `ChillScene` is keyed by scene id so switching remounts it (and fades the new one in). Test hooks: `window.__sonusTest.setChillScene(id)` / `getChillScene()`.

**The hammock scene.** A man in a hammock holds a phone (`beach.jpg`, 2752×1536). Two layers, neither warping the people:
- **The phone's screen is redrawn live** (`ChillPhoneScreen.jsx`) over the photo's own, whose text is AI-garbled and whose pause icon never changes: a blurred copy of the cover as the background, the artwork tile, the real title/artist, a progress bar and times that move, a play/pause icon that follows the real state, and a real clock. It is laid out in a 270×600 local space (2× the screen's 134.5×300 px) and mapped onto the screen's quadrilateral (`PHONE_SCREEN_QUAD`, read off 4–5× zooms; the phone is almost face-on, so ~a rectangle) by `quadMatrix3d`. A hair of blur and a glare keep it from looking pasted onto a soft photo. `pointer-events: none` — it is a picture. The artwork there is small by nature (~114px of a 2752px photo).
- **The photo is gently alive** (`ChillLivingPhoto.jsx`): a WebGL canvas draws it through a fragment shader that nudges the texture lookup *only where a mask says so* — palm fronds sway (slow wind + a faster flutter, phase varying across the picture); the open sea moves as **wave trains travelling toward the viewer** (phase advances with distance from the horizon, waves finer and fainter far away, noise-warped so the rows aren't regular, a slow swell on top, crests a touch brighter and troughs a touch darker, and the **horizon itself held still** — amplitude is 0 there); **the shore surges** (each stretch of shore on its own ~6.8s beat: a quick advance up the sand, a slow drain back, a few px of travel, lacy foam on the leading edge but never on dry sand, wet sand darkening as the water covers it); the sun glitter twinkles; and **the hammock swings with the man in it** (next bullet). Masks come from `scripts/make-chill-beach-mask.py` (Pillow only; it also writes `beach-body.png`): R = palm weight, G = sea weight, B = **shore weight** (the breaking-foam bands on the right and the small wash on the far left, hand-drawn polygons, feathered), at half resolution (`beach-mask.png`, ~70KB). The sea's depth is no longer stored: it is a function of y, computed in the shader. Fronds are found by **hue** (45–150°, saturated) — *not* "green dominant": sunlit fronds are yellow-green with R ≥ G (e.g. 144,130,59), which a green-dominant test rejects; trunks, skin and sand sit below ~35°. The sea is found by blue-over-red plus one hand-drawn glitter polygon (too white for a colour test) whose left edge is ramped in over ~180px so the ripple amplitude doesn't jump at a visible seam. The mask texture is uploaded with `UNPACK_COLORSPACE_CONVERSION_WEBGL = NONE`: it carries **data**, not colour, and a colour-managed decode would corrupt the weights.
- **The swing.** The hammock, the man and the phone are ONE body (`beach-body.png`, below), moved by `swayAt(t)` in `chillBeach.js`, which is the single definition driving both the photo shader and the phone overlay. What makes it read as a real hammock: **(1) an ellipse, not a line** — across-the-axis swing is partly toward the camera, so the sideways part `dx` (weighted by `swayRampX(y)`: 0 at the horizon, full low in the frame) and the vertical part `dy` (weighted by `swayProfileY(x)`: 0 at the right-hand trunk anchor, full over the man, a 0.55 floor at the far left where the hammock runs out of frame) are a quarter-cycle out of phase; **(2) it never repeats mechanically** — two incommensurate periods (6.4s, 9.7s) plus a quiet third (3.9s), and an amplitude that drifts over ~37s; **(3) the freely hanging ropes lag** — the rope bundles and the tassel get an extra sideways swing (`hang`) that trails the body by ~0.6s and grows toward their tips (hang factor 0 at the attachment → 1 at the tip, baked into the mask's blue channel), like the pendulums they are. Amplitudes: ±9px sideways, ±6px vertical, ±7px extra at a hanging tip (photo px at full weight; ~60% of that on screen). **The GLSL gets its two weight functions generated from the same constants** (`SWAY_GLSL`), and the phone's overlay evaluates `swayRampX`/`swayProfileY` at the screen's own centre, so the shader and the overlay cannot disagree. **The phone's screen is DOM, not in the shader, so it must be given the same offset or it would drift off the phone in the man's hands**: `ChillLivingPhoto` reports `swayAt(t)` every frame through `onSway`, and `ChillBeach` writes the translate straight onto a wrapper (`.chill-phone-sway`) — not through React state, which would re-render 30 times a second for a transform. Verified by capturing the swing's two most different moments: the screen sits inside the bezel at both.
- **The body mask has to be accurate, because sand must not move.** The first version was a rough outline feathered 45px; it dragged the sand in the lower-left corner (and smeared the net's edge on the sand) along with the hammock. `beach-body.png` is now a union of **traced polygons with an 8px feather** — the net's real right edge, the diagonal lower-left edge **including its thick brown rim**, each hanging rope bundle and the thin rope between them on their own (the sand between them is background), the cream tassel, the man's head and headphones. Channels: R body, G freely-hanging ropes, B hang factor. Verified by differencing the two extremes: the net, man, bundles and tassel change, and the pure-sand boxes (between the bundles and the net, right of the net, below its lower-left edge) change by exactly 0.00. **Holes in the net show background that moves a little with it** — acceptable because that background is out of focus; a bigger swing would need the background inpainted. Local *sharpness* separates the in-focus net from the blurred background well (net 11-14 vs sand 4-5) but NOT the hanging bundles, which are out of focus too (4.4 vs sand 3.9), so those are traced by hand.
- **The plain `<img>` is always rendered underneath**; the canvas (opacity 0, `data-live="false"`) fades in after the first frame. No flash while textures load, and if WebGL is unavailable, the texture is too large, or the context is lost, the scene is simply the still photo (`data-gl="fallback"`; unit-tested in jsdom, where `getContext` is null).
- **Cost.** By choice it keeps moving while paused, so it is kept cheap: 30fps cap, a drawing buffer of `min(1, max(0.45, k·dpr))` × the photo's pixels (never more than the photo has or the window shows), `powerPreference: 'low-power'`, and no drawing while `document.hidden`. Measured in the smoke suite's frame-time probe (`metrics.frameTimeMs.chillBeach`) alongside `chill` and `nowPlaying`; compare on the 2017 iMac. `data-frames` (updated every 10 frames) is how the smoke suite proves it is really drawing.
- **Framing** (`BEACH_FRAMING`): `keep` spans from the hammock to the photo's right edge — **so the sea, glitter and shore waves are actually on screen**. (The first framing centred on the man and the phone and cropped everything right of x≈2085 out of a 1600×900 window: the shore the waves were being built for wasn't visible. Check that an effect is *in frame* before tuning it.) The phone is targeted at ~26% of the window's height but fitting `keep` into the width usually wins (~22%); resolution cap 1.6 device px per photo px; covering always wins. In windows too tall for `keep` to fit, the view centres on it and the right edge is cropped first; `must` (the man's head and headphones, the phone, the hammock's right side) is what stays in view even then — `computeFraming` ignores it, the unit tests hold the framing to it.
- **Two shader traps found building the waves.** (1) Keying the glitter twinkle on *brightness* made the whole nearly-white right-hand side speckle like grain — only pixels well above their surroundings (a 4-tap local-contrast test) should twinkle. (2) Value noise that is tall and narrow reads as **vertical streaks** on a shoreline; stretch it ALONG the shore (the foam lace samples ~70 cells across and ~300 down).

**The shared animated-photo engine (`fx`).** `ChillLivingPhoto.jsx` is scene-agnostic: a WebGL canvas draws the photo through a fragment shader that nudges the texture lookup only where a scene's masks say so. What is scene-specific is that scene's `fx` (`scene.fx`): `frag` (the shader), `masks` (`[{ uniform, url }]`, uploaded as data textures), an optional `create()` (per-mount state, e.g. the typing clock), and `update(t, set, state, live, dt)` which sets the frame's uniforms by name and **returns the values the scene's DOM overlays need**; the engine hands them to `onFrame`. `liveState` (e.g. `{ isPlaying }`) is read afresh every frame. The hammock's effects are `createBeachFx` (`chillBeachFx.js`), the room's `createRoomFx` (`chillRoomFx.js`). Everything generic — the `<img>` fallback, the 30fps cap, the buffer sizing, context-loss handling, `data-gl` / `data-live` / `data-frames` — lives in the engine once.

**The study room.** A girl at a desk by a rainy window, typing on a laptop, posters and polaroids on the walls (`room.jpg`, 2752×1536). Calibration in `chillRoom.js`, masks from `scripts/make-chill-room-mask.py` (`room-mask.png`: R window glass, G the string-light column, B her back and shoulders), poster spots in `chillRoomPosters.json`, shader in `chillRoomFx.js`:
- **Rain running down the glass.** Three layers of drops, each in its own columns. A drop **grows** as it slides (it collects water), moves **stop-and-go** (a monotone curve `g + a·sin(2πk·g)/(2πk)` with a≈0.95: nearly flat k times per pass, so it hangs and then lurches), leaves a thin **wet trail** and a few **beads**, and its body is a **lens** that shows the world behind the glass inverted and compressed (sampling the photo at `centre − d·1.7`), with a darker rim and a highlight. Each column has a drop on the glass for only part of its cycle, so they come and go. The photo's own painted drops stay as the still, beaded ones; the moving ones sample the same photo, so the colours match and they read as more drops on the same pane. **They are sized like the photo's own painted drops** (radii ~1.3-5.4 photo px across the three layers; the first version's 5-9.5px read as twice the painted ones). The glass mask excludes the lamp, the mullion, the blind and the pencil cup. **The glass borders are measured, not hand-placed, and are NOT axis-aligned**: the first polygons (a vertical right edge at 2275, a flat bottom at 985, a vertical 1755 for the left pane) let drops land 6–23px outside the glass — on the left frame, the slanted right edge of the left pane (it runs from x=1757.8 at y=62 to 1747.1 at y=830), the dark frame and grey mesh strip between the panes, the right frame (its edge moves from 2281 at y=100 to 2252 at y=880) and the dark seal, white bevel and sill below the right pane (the bottom edge slopes from (1840,963) down to (2020,977)). They were fitted with the poster tool's edge-profile line fit (`fit_side`) plus luminance profiles across each border, then inset 2px and softened by only 1.5px (`GLASS_LEFT`/`GLASS_RIGHT` in `make-chill-room-mask.py`, with the measurements in a comment above them). **The smoke suite's spill strips were calibrated on BOTH masks**: my first version of that check measured regions the old mask never reached and passed on it too (vacuous). The strips now sit exactly where the polygons differ (left frame, the slanted pane edge, the gap between the panes, the right frame, the sill) and read 0.00–0.23 on the measured mask against 0.55–1.08 on the old one; the limit is 0.45. Always prove a regression check fails on the bug it guards.
- **The coffee's steam** (`steam()` in `chillRoomFx.js`): a plume rising from the mug's opening (~(1881,1026)), evaluated only inside a small box (1790–1980 × 880–1042). A noise field scrolls UP (`fbm`), wisps drift sideways on two slow S-curves of different periods that grow with height, a domain warp makes them curl instead of rising in straight columns, the cone widens with height, density fades in just above the rim and out toward the top (~130px), and it is clipped at the rim so it never paints over the mug's body. Rendered as a soft warm white (alpha ≤0.46, stronger over dark backgrounds) over the sill and the window's lower edge — physically right, the mug is in front. It moves regardless of playback (like the rain). The photo's own faint static wisp stays under it. Smoke: the steam box changes (mean ~4.7), the mug body changes by exactly 0.
- **Rain falling outside:** faint slanted streaks over the yard, behind the drops (two layers at different scales and speeds).
- **Her typing — and stopping, on the laptop's screen.** `createTypingClock` (`chillRoom.js`, pure): she types for 3.2–7.4s then stops for 1.8–3.6s, over and over, the lengths fixed by a hash of the segment's index (so it is testable), eased in and out. The clock **only advances while she is "on"**: pausing the music gates it down (~0.35s), freezing the schedule where it was, and playing resumes it — unlike the hammock and the record, she is tied to playback. **There is deliberately no finger animation.** The first version warped the hand pixels per finger-band (dips on random 9Hz beats, then blended across bands to remove seams); at ~1-2px it read as *wiggling fingers*, not typing, and it was removed (the user's call: "remove it if you can't make it look real"). Warping a flat photo of hands can't show a finger pressing a key. What reads is the laptop's screen (below): the text grows while she types and holds still while she stops.
- **Lightning, every so often — as a change of EXPOSURE, not a white overlay** (`lightningAt` / `FLASH` in `chillRoom.js`, pure and deterministic). The first flash comes ~4.5s after the scene appears (so it is seen), then one every 11–26s; each is a *soft* flicker: a main pulse that rises over ~60ms (a smoothstep, never a hard step) and fades over ~0.3s, an echo ~0.25s later at most half as strong, sometimes a faint third. The picture's own colours are multiplied by `1 + 0.30 · flash · weight(x)` (**+30% at the peak**, weight 0.82 at the far wall rising to 1.10 at the window), through a **highlight roll-off applied to the increase only** (`out = c + (roll(v) − roll(c))·(1 − c)/(1 − roll(c))`): a bright pixel is lifted toward white but never pinned to it, and white itself doesn't move. **One definition drives everything**: `FLASH_GLSL` is generated from the same constants as `flashGain` (the DOM side), so the shader and the overlays cannot disagree; posters and the laptop apply the same gain through `brightness()` and a `--flash` / `--fw` CSS variable pair (`ChillRoom` writes `--flash` to a `display: contents` wrapper only when it changes). **The first two versions were white washes and the user rejected both**: the first mixed the glass toward white and added white to the room; the second, "strengthened" because the soft version was invisible on a captured frame, did it again. Lessons: *judge a flash by measured per-region luminance ratios* (the smoke suite holds the flash at 0 and 1 via `window.__sonusFlashOverride` — honoured only under `?test=1` — captures real pixels, and asserts every region brightens by about 5-40%, equally on all channels, with no flat-white pinning), not by eye on one frame; and a roll-off applied to the *colour* (instead of the increase) darkens highlights at a weak flash — a dip at the start of every flash — which a monotonicity unit test caught.
- **Breathing:** her back and shoulders rise and fall ~1.8px on a ~4.8s uneven cycle (`breathAt`), weighted by a torso mask and a vertical profile (nothing at the neck or the waist).
- **Twinkling string lights:** only the bright bulbs (pixels well above their surroundings) twinkle, plus a faint warm glow; the wall around them doesn't.
- **The artwork on the posters** (`ChillPosters.jsx`, DOM, outside the shader): **24 spots, 21 fitted** — the big posters, framed prints and polaroids on both walls — listed in `chillRoomPosters.json` (`id`, `look`, `seed`, `quad`, `fit`, `light`). Each is a box in its own local space mapped onto the print's corners in the photo by `quadMatrix3d`, **the cover image only (no text)**, in different `look`s so it isn't one copy pasted two dozen times — `full` (the cover cropped to the print's shape), `mono` (a black-and-white print, like most of the wall), `detail` (a zoomed part of the cover, `zoom`/`at`). Crossfades on track change like every other artwork; with no artwork it draws nothing and the room keeps its own posters. **Detail crops** use gentle zooms (1.5–2.0x) near the middle of the cover, so each shows something recognisable, not an arbitrary fragment.
  - **The fit is MEASURED, not eyeballed** (`scripts/fit-chill-room-posters.py`). Hand-placed corners were off by 2–7px on average and up to 12px from the printed edges (art overshooting on one side, the print showing on the other), and the first re-measure by eye at 2–6x still wasn't good enough. The edges are straight (a line fit leaves 0.1–0.3px of scatter), so *one homography per print is right* and each print already has its own angle — what it needed was accurate corners. The tool starts from a hand-placed `seed` quad and, per side, samples 26 luminance profiles along the outward normal, picks the *nearest* edge at least 40% as strong as the strongest (a print with a white mat has two edges and the outer one is stronger — the cream frame first locked onto the mat), drops samples whose edge direction disagrees with the majority, fits a robust line, and intersects adjacent lines (three narrowing passes: ±5, ±3.5, ±3px). **A print passes only if every side checks out** (scatter ≤0.7px, ≥60% inliers, a real edge ≥4 levels/px, the mean gradient peaking within 0.5px of the line) **and no corner moved more than 9px from its seed** — a seed further off than that fails rather than being "rescued" by a wrong edge (the trio's top edge once slid onto an unrelated shading band). Prints that don't pass get **no artwork** and keep their original (`POSTERS` is `ALL_POSTERS` filtered by `fit.ok`): of 24, three are dropped — `face-sm` (a second edge beside its right side), `suit` (its left edge blurs into the next frame) — `dancer` (white print on a white mat has no top edge). Workflow: run it, look at its overlays (red seed, green fitted, amber rejected), `--adopt id,...` re-seeds a print from its reviewed fit, `"hold": ["top"]` pins a side the detector can't see. **A bad SEED passes every other test — hence the outer-edge check.** The New York print's top edge was fitted to the top of its *lettering*, ~10px below the print's real top (the frame's inner edge), because my hand-placed seed sat on that interior edge and the fit just refined it: scatter 0.27px, strength 12, gradient peak on the line, drift 0 — every test green — and the user saw a strip of the original print above the art. The signature is a dark trough between the fitted (bright→dark) edge and a stronger dark→bright edge 4–16px further out (`outer_edge_check`); sides whose check was a confirmed false positive (a neighbouring frame) are marked `"trust"` after looking at 6x+. A first version of the check only looked for an outer edge in the *same* direction and could not have caught it (the signs are opposite), which a test on the known-bad quad showed — **`--self-test` keeps that quad as a permanent regression case**. Lesson: *a test of the fit cannot catch a wrong seed; test the thing you actually care about (is there print outside the line?) against a known-bad case.* **A bad SEED passes every fit test** — the New York print's top edge was first fitted to the top of its lettering, ~10px inside the print (a strip of the original showed above the art; the user spotted it, the tool didn't): the hand-placed seed sat on that interior edge, the fit refined it to 0.27px scatter, and the drift limit only compares against the seed. So `outer_edge_check` looks for the signature — a bright→dark fitted edge followed, 4–16px outward, by a stronger dark→bright edge across a dark trough (the print's own dark border band, then the frame) — and fails the print. (My first version looked for an outer edge in the *same* direction as the fitted one and could never have caught it: the signs are opposite. `--self-test` keeps the old bad quad as a regression case.) `"trust": ["left"]` skips this one check on a side confirmed by eye at 6x+ — `big-left`'s left edge is flagged by the frame beside it; sides are listed top, right, bottom, left, and I once trusted the wrong one. Every fitted print's top edge was then reviewed over the original on a contact sheet. **Don't trust the tool blindly in either direction**: I first judged the trio's top edge by eye at 6x and held it wrong (a visible wedge of un-covered print), then trusted the tool's steeper line, which at 7x follows the true frame/picture boundary exactly.
  - **Each print is as soft as its own edge**: the same tool measures a Gaussian sigma from the edge's steepest slope (`fit.blur`, 0.8–1.7px), `ChillPosters` converts it to the box's local pixels (the CSS filter runs before the homography, so a small print's box is scaled up more and needs a larger local blur — up to ~8px), and the art gets the photo's grain (an SVG-noise `::before`, overlay blend).
  - **The original glare goes back on top**: the fairy lights' bokeh on a print would be hidden by the art, so `room-glare.png` (from `make-chill-room-mask.py`) holds just that light, screen-blended over the posters. Detection took three tries: warm+bright picked up lettering as a ghost of the old print; a flatness test fixed that; a lower brightness threshold then picked up a face's warm skin as a faint ghost. It now keeps only R>205 smooth blobs, restricted to the fitted quads. Few pixels (the bokeh on the right edges of a few prints), which is right.
  - **The room's colour.** The art is *not* shown as-is (bright, saturated, pasted on). `scripts/make-chill-room-mask.py` measures the room's lighting around each print from the original photo and writes it back into the JSON as `light`: a colour cast (`tint`, from a 150px window, eased 35% toward neutral so an orange corner doesn't become a flat orange wash), the multiply colour at the print's left and right side (`left`/`right`, so the warm falloff from the fairy lights runs across the print), and a dimness (`dim`, 0.58-0.9, from how dark the original print is at that spot). CSS applies them (`.chill-poster`: `brightness(dim·0.92)`, desaturated, a hair of blur; `::after` multiplies by the left→right light gradient and a vignette). Prints by the lamp and lights come out warm; the cool far-left ones neutral and dimmer.
- **The live laptop screen** (`ChillLaptopScreen.jsx`, a 2D canvas mapped onto the display's corners): a window with a page of text that **grows while she types** (the caret at the end of the line, the line filling at ~4.6px per character, a new line, the page scrolling) and holds still while she has stopped, the caret blinking. It follows the engine's typing values through `onFrame` and redraws only when something changed; its page is a soft grey-white and the canvas is dimmed and slightly desaturated (a screen in a warm, dim room), and brightens with the lightning. `data-typing` / `data-chars` on its canvas are how the smoke suite sees her typing and stopping. Its four corners were first measured from a coarse crop and sat too high (the photo's own dock peeked out under the overlay); they were corrected by drawing candidate quads over the original photo.
- **She types the song's lyrics** (`chillLyrics.js`, pure and unit-tested; drawn by `ChillLaptopScreen.jsx`). When the playing track has lyrics (`currentTrack.lyrics`, passed down as `liveState.lyrics`), the laptop's page shows THEM as real text instead of the generic grey lines, typed at the **same speed** (6.5 chars/s) **and stopping only at the lyrics' own breaks**. Not synced to the song, by design: she drifts relative to the singer, so it is ambience, not a lyrics display. `parseLyrics` keeps only the words (LRC timestamps `[00:12.34]` and `[ar:…]` tags stripped, whitespace collapsed, a blank line = a verse break, runaway lines cut at 140 chars, 400 lines max, "lyrics" with no letters or digits like a lone `♪` rejected → `null`, and `null` means the scene keeps its **generic typing exactly as before**). `createLyricsClock` types line by line: **within a verse she types straight on** (just a 0.14s beat for Enter; the typing envelope does not dip between lines), **stops for 1.8–3.6s at a verse break** (the same "couple of seconds" as the generic typing, a hash of the line index so it is testable), and lyrics with **no blank lines at all** would never rest, so every 6 lines she takes a 1.1s breath. After the last line she rests ~5s, then **clears the page and starts again** (`cycle` counts the loops) so she keeps working for the whole song; a different track (a new `lyrics` string) starts a fresh clock from the first line. Pausing the music gates the clock to a stop (the schedule freezes where it was) and playing resumes it, as with the generic typing. `createRoomFx` owns both clocks and returns `lyric: { script, lineIndex, partial, cycle }` through `onFrame`.
  - **Drawing it.** The page is a 288x248 local-px area on the 480x330 canvas; the lyrics use a 12px bold system font, 15px line height, ~13 rows, wrapped to the page's width by measuring the real font (`ctx.measureText`), the oldest rows scrolling off the top. **Right-to-left lyrics are right-aligned and typed from the right edge**, decided per paragraph with `isRTL` (a song can mix scripts), with the caret at the left end of the line being typed; verified with Hebrew. **The canvas is supersampled 2x** (bitmap 960x660, `ctx.setTransform(2,…)`, CSS size 480x330): the screen is only ~275 photo px wide, and a 1x bitmap blurs the text when the browser downsamples it through the perspective transform. At a 1600px-wide Retina window the text comes out ~8 device px and reads (35-40 characters per line); on a small non-Retina window it is closer to texture, which is the honest limit of a 275px screen.
  - **Smoke hooks:** `data-lyrics`, `data-lyric-line`, `data-lyric-chars`, `data-lyric-cycle`, `data-lyric-rows`, `data-typing` on the laptop canvas, and `window.__sonusTest.setCurrentLyrics(text|null)`. The suite asserts the page types THEM (not generic text), straight on inside a verse and a real stop at its end, real dark text pixels on the canvas, pausing freezes the line and character, a different track starts over from line 0, and `null` brings the generic typing back. Gotcha when adding such checks: an injected script is a JS template literal inside the smoke file, so a lyric's line break must be written `\\n` there — a single `\n` becomes a real newline inside a quoted string and the whole injected script fails with `Invalid or unexpected token`.
- **Framing:** wide, so nearly the whole room (covering the window wins); `must` is the window's top down to the hands (y 40–1140) — an ultrawide window loses floor, not window.

(Compare only frames taken *after* the scene's 0.5s fade-in and *before* the idle fade, which dims the bottom third — both look like motion everywhere.)

**Idle chrome — one clock for everything (`useChillChrome`).** The bottom bar (title/artist marquee, the shared `renderTransportControls`, seek line with times), the title strip's buttons (the Home/Library tabs, search, add, and the exit button) and the traffic lights are one group. Paused always shows them. They are held up while the search panel, a track menu, the drop dialog or the scene picker is open, and while the pointer really rests on a `[data-chill-chrome]` element — **asked of the browser (`document.querySelector('[data-chill-chrome]:hover')`) at the moment the idle timer fires, never remembered from an earlier mouse move.** (The first version remembered the last `mousemove`'s target. It went stale whenever the pointer left without an event to say so — the smoke suite's window resizing away from a parked cursor, or a user tabbing away after resting on the bar — and then held the chrome up forever. It looked like a flaky smoke check for several runs before the log showed a real mousemove whose target was the seek bar.) Waking: any page `mousemove`/`mousedown`/`keydown`/`wheel`, **and** `window:pointer-moved` from main. The traffic lights can't fade (macOS draws them), so they hide `CHILL_LIGHTS_DELAY_MS` (600ms) after the fade starts — i.e. when it ends — and show instantly when the chrome returns.

**Why main reports pointer movement, and the drag band.** The title strip is `body`'s `-webkit-app-region: drag` area and Electron hands drag areas to the OS, so the page never sees the pointer over it — a page-only idle clock would never wake while the pointer was up there. `pointerMotion.mjs` polls the OS cursor (only while chill is on). Separately, the full-window layer is `no-drag` and would carve the whole strip out of the draggable area, making the window immovable, so `.chill-drag-strip` (42px — `.app-container`'s `padding-top`, `-webkit-app-region: drag`) restores it; it stays draggable while the chrome is hidden. **Its position in the document is load-bearing**: Electron builds the draggable area by walking the page in document order — a later `drag` region is *unioned over* earlier ones and a later `no-drag` is *subtracted* (z-index plays no part). `ChillScene` is therefore rendered **before** the title-bar buttons in `App.jsx`, so their `no-drag` carves them back out of the band; rendered after them (the first version) the band re-claimed their area and none of them could be clicked, while every test passed (JS `.click()`, CDP and `sendInputEvent` all bypass the OS drag layer, and a real synthetic click needs the Accessibility permission). The smoke suite asserts each button is `no-drag` and follows the band in document order.

**Traffic-light safety.** Hiding them is the dangerous half of this feature, so the restore is structural: main restores them whenever chill tracking stops, whatever the reason (see the IPC section), and the renderer never asks for "hidden" except from inside an active chill session. Smoke asserts the requested state through hide → wake → pause → exit → narrow excursion. The real native lights and the window-corner clipping of the full-bleed layer can't be seen from the test environment (`screencapture` is denied) — ask the user to look.

Start Mix leaves Now Playing (so Chill mode, which only renders on Now Playing, steps aside) and its back chevron returns to Now Playing where Chill resumes. Clicking the record toggles play/pause. The record's artwork and the idle behaviour are otherwise as above.

## Lyrics feature

**Storage:** lyrics are read from the file via `music-metadata` and mapped to `common.lyrics[0]` (an object `{ language, descriptor, text }` — always use `.text`). Supported formats: MP3 (USLT ID3 frame), FLAC (`LYRICS` Vorbis Comment), WAV (USLT ID3 frame in `id3 ` RIFF chunk). `parseFilePaths` in `main.js` reads lyrics for `.mp3`, `.flac`, and `.wav`; all other formats get `null`. Written back via `fs:writeTag` — each format's writer handles the appropriate container (see IPC surface above).

**Tag Editor:** a `<textarea>` (`flex: 1`, `resize: none`) lives in the right column of the Tag Editor layout (see Tag Editor section below), rendered for `.mp3`, `.flac`, and `.wav` files. RTL detection: `teaLyricsIsRTL = isRTL(editTags.lyrics || '')` (reuses the module-level `isRTL()` function, reactive to every keystroke). When true, applies `direction: rtl, textAlign: right` to the textarea — right-alignment is standard for RTL text input (cursor starts at the right edge).

**Now Playing lyrics panel:** a two-layer structure to the right of the artwork column:
- **Outer div** (`position: relative`, width transitions `0% ↔ 50%` with cubic-bezier). This div is NOT `overflow: hidden`, which is critical for the artwork/glow content it contains.
- **Inner div** (`position: absolute, inset: 0, overflow: hidden`) — owns the scrollable lyrics content. Opacity fades in after the width transition starts (`transition-delay: 0.1s`).
- **The toggle button** (`.lyrics-open-btn`) is a sibling of the back button, not nested inside the (width-animating) artwork column — `position: absolute, top: 16, left: '50%', transform: 'translateX(-50%)'`, centered on the same top row the back button occupies at the opposite corner, so it stays put regardless of the artwork column's own width. It renders the same `Mic2` icon as the track list's row indicator (not a chevron), colored inline — `#fff` when open, `rgba(255,255,255,0.4)` when closed — matching the narrow view's Song/Lyrics tab text exactly (same two colors, same "just the state that matters" plainness, deliberately no hover treatment and no attention-hint animation; an earlier version used `ChevronRight`/`ChevronLeft` with a pulsing glow, both removed at the user's request in favor of this look). Because the color is set inline, a `:hover` rule in CSS could never win against it anyway (inline style always outranks a class selector) — `.lyrics-open-btn` in `index.css` only carries type/chrome, not color.
- `isLyricsOpen` does **not** reset on track change — it's a plain `useState` with no effect watching `currentTrack`. Switching to a track with no lyrics while the panel is open leaves it open, showing "No lyrics for this track." (both the desktop panel and narrow's Lyrics tab handle this the same way) rather than snapping shut, so the toggle button stays a valid way to close it either way. `lyricsScrollRef` scroll position does reset, on `currentTrack.filePath` change.

**RTL language detection:** `isRTL(text)` (module-level in `App.jsx`) counts Hebrew (`֐–׿`) and Arabic (`؀–ۿ`) characters against total letter count using `\p{L}` (Unicode property escapes). Returns true when RTL characters exceed 30% of letters. `lyricsIsRTL` is derived from `currentTrack?.lyrics` and applied as `direction: rtl` + `textAlign: center` on the lyrics label and text divs. `direction: rtl` ensures correct bidi character rendering; `textAlign: center` keeps RTL lines centered in the panel rather than hugging the right edge (which looked cramped). The scroll container padding is the same for both directions (`'24px 16px 24px 32px'` — 32px left for breathing room from the divider).

## Background playback / window lifecycle (macOS-specific)

Clicking the red close button hides the window (`event.preventDefault(); mainWindow.hide()`) rather than quitting, so the `<audio>` element keeps playing — matches native macOS media-player behavior. Real quit only happens via `Cmd+Q` (`before-quit` sets a `forceQuit` flag the `close` handler checks). The dock icon's `activate` event re-shows the hidden window.

## Tag Editor — a separate window, not a `view`

Unlike Library/Home/Now Playing (all `view` values inside the single main-window renderer), the Tag Editor is its own singleton `BrowserWindow` (`electron/main.js`'s `createTagEditorWindow`), loading the *same* Vite bundle as the main window but with a `?editor=1` query flag — `src/main.jsx` reads that flag and mounts `<TagEditorWindow/>` instead of `<App/>` (same pattern the `?test=1` smoke-test gate already used, so no second Vite entry point/build target was needed). `view` in `App.jsx` never has a `'tag_editor'` value.

**Opening it:** the "Edit Tags…" context-menu item (Library rows and Now Playing's ⋮ menu) looks up the full track object from `library` and calls `window.electronAPI.openTagEditor(track)` → `open-tag-editor` IPC → `createTagEditorWindow(track)`. Singleton: if the window is already open, it's focused and sent the new track (`tag-editor:load`) rather than opening a second window. Fixed width (960), not resizable by the user — deliberately decoupled from the main window's own size. Height auto-fits to content; see "Auto-fit height" below.

**Receiving its track:** `TagEditorWindow.jsx` has no `library` state of its own (separate renderer process) — the full track object is passed over IPC (`onTagEditorLoad`), not just a filePath. A `loadedPathRef` guard (comparing `track.filePath`) resets `editTags`/`artworkSelected`/search state whenever a genuinely different track arrives, including a second "Edit Tags…" invocation while the window is already open.

**Saving:** `saveTags()` in `TagEditorWindow.jsx` only calls `window.electronAPI.writeTag(...)` and sets local `saveStatus` — it has no `library`/`currentTrack`/`<audio>` to update itself. `fs:writeTag`'s handler (`main.js`) broadcasts `tag-editor:saved` to the **main** window after every successful write, regardless of which window called it; `App.jsx`'s own `onTagSaved` listener is what merges the change into `library`/`currentTrack` and — if the edited track is the one currently playing — reloads `<audio>` and resumes playback position (this logic used to live inline in the old `saveTags()`, now lives here instead). **The reload must stay in the handler body, not inside the `setCurrentTrack` updater**: it lived in the updater once, and React `StrictMode` (dev only) double-invokes updaters — the first call's `audio.load()` synchronously resets the element to 0/paused, so the second call captured "resume at 0, wasn't playing" and every Save stopped the song at the start under `npm run dev`, while the packaged app (and the smoke suite, which runs the built app) was fine. The path check uses `currentTrackRef`; the `save-while-playing` smoke case (a realistic ~5MB file, cover art included, asserting still-playing / same position / same track / no media error) guards the production path. One behavior difference from the old inline version: it used to pass the just-edited full-res picture straight to `npArtwork` to skip a refetch; the cross-process version doesn't have that data in the main window, so it just lets the existing `npArtwork` effect (keyed on `currentTrack.thumb`) refetch via `fs:readArtwork` when the thumb changes — a trivial, already-LRU-cached cost for the architectural simplification.

**Scrolling — a real gotcha hit building this:** the scroll container needs `overflowY: 'auto'` on a bounded height (the form is reliably taller than the fixed window), but that alone wasn't sufficient — real mouse-wheel/trackpad scrolling felt broken even though `scrollTop` was settable programmatically. Root cause: `index.css`'s `body { -webkit-app-region: drag }` (how the frameless window becomes draggable by its background) is inherited by any descendant unless explicitly opted out via the `button, input, textarea, a, .clickable, .scrollable { -webkit-app-region: no-drag }` rule, and the div wasn't in that allowlist. Fixed by giving it `className="scrollable"` (reusing the exact class the main window's own scroll container already relies on for this same reason). A `drag` region silently breaks real wheel/gesture scrolling, not just clicks — if you ever add another top-level scrollable region in either window, it needs this too.

**Dragging the window — a second gotcha, caused by the first fix:** giving the root wrapper `className="scrollable"` (above) fixed scrolling but broke window dragging — `.scrollable` opts out of `-webkit-app-region: drag`, and since that div was `height: '100vh'` (the *only* element in the window, with `.glass-panel` as its sole child), it covered 100% of the window's surface, leaving no background pixel anywhere still eligible for `body`'s draggable region. Fixed the same way the main window avoids this: the actual root is now a plain (unclassed) `height: '100vh'` flex column, containing a 42px empty drag strip followed by the `.scrollable` content div (`flex: 1` instead of `height: '100vh'`, `padding: '0 32px 32px'` instead of `'42px 32px 32px'` — the top 42px moved from padding-on-the-scrollable-div to a separate sibling strip, so total spacing above the content is pixel-identical). This exactly mirrors `App.jsx`'s own `.app-container { padding-top: 42px }` — a full-width strip above `.glass-panel` that stays part of `body`'s drag region because nothing there is `.scrollable`/`.clickable`. Any new top-level `.scrollable` region that fills 100% of a window's surface will reproduce this bug — it needs a plain, unclassed sibling strip carved out above it.

**No back/breadcrumb header** — unlike the old inline version's `‹ [origin]` breadcrumb, the standalone window has nothing to navigate "back" to; closing it (red traffic light or Cmd+W) is the only dismissal, and does so silently discarding any unsaved edits (matches the old inline behavior — no confirmation dialog). It sets `document.title = 'Edit Tags'` so the Dock/Window menu shows something distinct from "Sonus". It has its own `onSelectAll` listener (native `.select()` on the focused input) since `menu-select-all` is sent to whichever `BrowserWindow` is currently focused — Cmd+A works in either window independently.

**Window position — never rely on `BrowserWindow.center()`.** The window is created at a fallback height and only resized once the renderer reports the form's real height, and `setContentSize` **pins the top-left corner** — so without an explicit reposition the window's centre drifts by half the height change (measured ~67-82px too low for a tall form, and too high for a short one). `centerInWorkArea()` in `main.js` computes the position from `display.workArea` directly: Electron's own `center()` was measured placing an 857px window at `y=74` on a `1728x1020` work area where the centre is `y=114`, i.e. ~40px high. The smoke suite asserts both axes land within 2px.

Re-centring happens on first show, and thereafter only if the fitted height moves by more than `TAG_EDITOR_RECENTER_DELTA` (100px), so a window the user dragged somewhere is not yanked back each time another track is loaded into it. **In practice that threshold never fires**: the form's height is the same with and without the Lyrics column (measured: 857px both ways), because the two columns stretch to whichever is taller and that is always the left Track Info column. It is a guard for future layout changes, not something that triggers today. `keepWindowOnScreen()` handles the non-centring case so a resize can't push the window off the bottom.

**Auto-fit height:** the window's height is fit to the form's actual content instead of a hand-picked constant, but width stays fixed at 960 (the two-column Track Info/Lyrics layout is tuned for that width — see "Layout" below). Mechanism: `TagEditorWindow.jsx` refs the `.scrollable` content div (`scrollableRef`) and tracks a `loadedTrackKey` state that's set once per genuine track load, batched into the *same* React commit as the `setEditTags(...)` call in the track-load effect — so a separate `useLayoutEffect` keyed on `[loadedTrackKey]` alone is guaranteed to fire only after the form has actually re-rendered with the new track's data. That effect reads `scrollableRef.current.scrollHeight` (the natural, unclipped content height) and sends it over a new `resizeTagEditor` preload call → `tag-editor:resize` IPC (renderer→main, fire-and-forget `send`) → `main.js` clamps it (`Math.max(500, Math.min(contentHeight + 42, display.workAreaSize.height - 80))` — the `+42` accounts for the drag strip above `.scrollable`, described above) and calls `tagEditorWindow.setContentSize(960, clampedHeight, true)` (animated). **Critically, `loadedTrackKey` is never touched by anything except a genuine track change** — not by typing, not by the async artwork refetch, and not by "Search Online" populating `tagSearchResults` (which renders inline *inside* the same `.scrollable` div and pushes its `scrollHeight` well past the window's fixed height) — so none of those can ever trigger a resize; the extra content simply scrolls, exactly like before this feature existed. The window is created with `show: false` and only calls `.show()` inside the resize handler (guarded by `!isVisible()`, so it's a harmless no-op on later resizes from singleton reuse) — this avoids a flash at the old fallback `960×720` size before the fitted size is known. A 1.5s fallback timer after `did-finish-load` force-shows the window if `tag-editor:resize` never arrives, so a preload/renderer failure can never leave it permanently hidden.

**Search results** (from "Search Online") render as a **centred overlay**, not inline. They used to sit below the form in the same glass panel, which inflated its `scrollHeight` past the window's fixed height so the results could only be reached by scrolling. - Opens the moment the search starts, so the spinner, any error, and the results all appear in one place; `tagSearchError` no longer renders beside the action buttons.

The smoke suite asserts the computed value.

**Result limits and de-duplication** live in `src/tagSearch.js` (a separate module so `TagEditorWindow.jsx` only exports a component, which Fast Refresh requires). `SEARCH_FETCH_LIMIT` (50) is the pool requested from the API; `SEARCH_MAX_RESULTS` (10) is what's shown.

`dedupeSearchResults` drops only *exact* repeats — identical title, artist, album **and** year — so different releases of the same song survive, which is the point when tagging. Two ordering rules matter: it runs **before** the list is truncated (de-duplicating an already-sliced 10 would leave fewer than 10 and quietly undo the limit), and it keeps the **first** occurrence so each API's relevance ranking is preserved. Unit-tested in `src/tagSearch.test.js`; the smoke suite additionally drives the popup through a `?test=1` hook (`window.__sonusTagEditorTest`) so the suite never calls iTunes or MusicBrainz.

**Artwork interactions:** The 200×200 artwork square has `tabIndex={0}` and three interaction modes:
- **Single click / focus** → selects the artwork (`artworkSelected` state → `true`). CSS class `.tag-artwork--selected` adds an accent-colored `box-shadow` glow. Hint text below changes to `⌘C copy · ⌘V paste · double-click to change`.
- **Double click** → opens the hidden `<input type="file">` file picker.
- **⌘C** (while selected) → calls `electronAPI.writeClipboardImage(editTags.picture)` to copy the artwork to the system clipboard.
- **⌘V** (while selected) → calls `electronAPI.readClipboardImage()` and sets the result as `editTags.picture` if non-null. Works with screenshots and any clipboard image source.
- **Escape / blur** → deselects (`onBlur` guards with `e.currentTarget.contains(e.relatedTarget)` so clicking the X button inside the wrapper doesn't accidentally deselect).
- **X button** (`position: absolute, top: 8, right: 8` on the `position: relative` wrapper — NOT inside the `overflow: hidden` image div, to avoid clipping) removes artwork: sets `editTags.picture = null`, which signals explicit removal to the main process on save. `artworkSelected` resets to `false` whenever a new track loads (the `loadedPathRef`-guarded effect described above), so selection state never bleeds from one track into the next.

New artwork (from file picker, clipboard paste, or "Use this" online search) is stored as a base64 data URL in `editTags.picture`.

**"Search Online" auto-fill:** a renderer-side feature — no IPC beyond the normal `fs:writeTag`/`fs:readArtwork`. Works entirely via `fetch()` from the renderer (`webSecurity: false` on the Tag Editor `BrowserWindow` too, same rationale as the main window, allows cross-origin requests). Flow:
1. `handleTagSearch()` builds a query from `editTags.artist + editTags.title`, tries iTunes Search API first (`https://itunes.apple.com/search?term=…&entity=song&limit=5`). If iTunes returns zero results, falls back to MusicBrainz (`https://musicbrainz.org/ws/2/recording/…&fmt=json`). Both sources are normalized to `{ title, artist, album, year, genre, artworkUrl, source }`.
2. Results render as a picker below the form (the glass-panel switches to `flexDirection: column` to accommodate this). User selects one card.
3. `handlePickResult()` fills all `editTags` fields immediately, then async-fetches: ① full-res artwork (iTunes: replaces `100x100bb` → `600x600bb`; MusicBrainz: Cover Art Archive `/release/{id}/front-250`) as blob → `FileReader` → base64 data URL; ② lyrics from `https://lrclib.net/api/search?…` (fuzzy, picks first result with `plainLyrics`), with `https://api.lyrics.ovh/v1/{artist}/{title}` as fallback. Lyrics are only attempted for `.mp3`, `.flac`, and `.wav` files.
4. All network calls go through `fetchWithTimeout(url, options, ms=15000)` — module-level in `TagEditorWindow.jsx`, an `AbortController` helper that aborts after 15 seconds. Both `handleTagSearch` and `handlePickResult` use `try/finally` to guarantee `isTagSearching` and `pickingResult` are always reset to idle, so the UI never gets permanently stuck in a loading state regardless of network failure.
5. **Music playback (main window) is unaffected by any of this** — it's a wholly separate renderer process now, not just separate state; the `<audio>` element reads local `file://` paths and never makes network requests regardless of what the Tag Editor window is doing. The "Search in YouTube" context-menu item (main window) uses `shell.openExternal` (fire-and-forget via `open-external-url` IPC) and similarly has zero impact on playback.

## Now Playing navigation and `previousView` invariants

`expandNowPlaying()` saves `view → previousView` then sets `view = 'now_playing'`. `collapseNowPlaying()` restores `setView(previousView)` with no special cases — wherever you came from is where you go back.

**Back button label (`npBackLabel`)** is computed from `previousView` and `homeDetailItem`:
- If `previousView === 'home'` and `homeDetailItem` is set, the label is the detail view title (album/artist name, or "Missing Art" / "Missing Lyrics" / etc. for metadata views).
- Otherwise maps `previousView` → "Library" / "Home".

(The Tag Editor being its own `BrowserWindow` rather than a `view` value means `previousView` can never point at it — the stale-pointer problem this used to guard against doesn't exist anymore.)

**Full-width back button styling (`.np-back-button`):** the label is real navigational information, not decoration — it names the specific screen "back" returns to, which can be an arbitrary Home detail page, not just "Library"/"Home" — so it was never a candidate for icon-only treatment despite otherwise looking like one. It renders as a small glass pill (translucent `--glass-bg` background, `--glass-border`, `backdrop-filter: blur(20px)`, fully rounded, hover/active states matching `.glass-button`'s own convention) rather than bare chevron+text floating directly on the Now Playing artwork glow behind it, which is variable enough in color/brightness to make plain text hard to read — an earlier version was exactly that bare text and was replaced for this reason. Position (`top: 16, left: 16`) and the `maxWidth: calc(50% - 32px)` + ellipsis truncation for long labels are unchanged from before; only the visual chrome changed.

## "Playing from" breadcrumb (`queueSource`)

Now Playing shows `Playing from "X"` above the artwork whenever the current queue came from a named multi-track source (an artist/album Play All or Shuffle, a Home card, a Mix) — clicking the quoted name jumps back to that source's own detail page. Plain single-track picks and unlabeled grab-bags (Quick Picks) show nothing.

**State: `queueSource` (`App.jsx`)** — `null`, or `{ label, item }` where `item` reuses the exact shape `homeDetailItem` already uses (`{ type, key }`, including `type: 'mix'`). Purely in-memory UI state, never persisted.

**Set only through `playTrack`'s third parameter**, which has three meaningful states, not two:
- **omitted (`undefined`)** — a plain queue *continuation* (skip next/prev, natural end-of-track advance, the forced-queue drain after Play All) — leaves `queueSource` untouched, since playback is still inside the same list.
- **`null`** — an explicit fresh single-track pick, breaking away from whatever was queued — clears it. `playTrackFresh` (handed to plain row-click/double-click/Enter in Library and Home's own rows, e.g. Quick Picks) always passes this; picking one specific track there is a deliberate break from whatever multi-track queue was playing, so the breadcrumb would be lying if it stuck around.
- **an object** — a new multi-track source — replaces it. `playAllTracks`/`detailPlayAllTracks` pass this, built from whichever `homeDetailItem` (or equivalent) is currently open.

**Single-track picks on a details screen (Artist/Album/Year/Quality/Mix) are the one exception to the `playTrackFresh`/`null` rule above** — double-clicking a row, clicking its artwork's play button, or pressing Enter on it continues through the *rest* of that same list afterward and labels the breadcrumb, exactly as if Play All had been started from that row, rather than clearing `queueSource` like a Library pick does. This is `App.jsx`'s `detailPlayTrack`, the `playTrack` prop `HomeDetailView` is given (in place of `playTrackFresh`): it receives `(track, isBack, tracks, index)` — `tracks` is the exact same already-sorted array `sortApi.sorted` that page's own Play All button uses, and `index` is the picked row's position in it — and calls `playAllTracks(tracks.slice(index), false, source)`, i.e. "Play All starting here." The `(tracks, index)` pair is forwarded generically by `TrackList`'s `handlePlayToggle`/`handleRowDoubleClick`/the Enter-key case in `handleKeyDown`, added specifically so a details-screen row could carry this context — Library's `playTrackFresh(track, isBack)` simply ignores the two extra trailing arguments (JS drops them), so Library's own single-track-pick behavior (always clears `queueSource`, no forced continuation) is completely unaffected.

**`jumpToQueueSource()`** — the breadcrumb's click target. Calls `setHomeDetailOrigin('now_playing')` (so the destination page's own back-chevron reads "‹ Now Playing") then `setView('home')` + `setHomeDetailItem(queueSource.item)` — the exact same path Home's own cards and Now Playing's clickable artist/album links already use. Because it's generic over `homeDetailItem`'s shape, it works automatically for any detail type, including Mix, with zero source-specific code.

**Narrow vs. full-width placement is deliberately asymmetric**, because the two layouts are built differently:
- **Narrow (Song tab)** — an ordinary flex child, `{queueSource?.label && <div>...}`, placed above the artwork row. It only consumes layout space when a label is actually present. This is safe specifically because it sits *above* the artwork — the artwork card's own drop shadow paints downward onto later siblings (see "Now Playing glass backdrop" below), so a conditionally-appearing element above it can never be shadowed the way the title block below it once was.
- **Full-width** — the back-button/lyrics-toggle row and the breadcrumb below it are absolutely positioned, siblings of the artwork+controls column rather than inside it, so a conditionally-appearing breadcrumb would shift them every time one appears or disappears. Instead the space is **unconditionally reserved**: `paddingTop` on the content row is a fixed `80` (was `56`, not conditional on `queueSource`). The breadcrumb itself renders `position: absolute; top: 50` regardless of whether a label is present; when absent it simply renders nothing, and the reserved padding is the (cheaper, ~24px) cost paid either way. The artwork column below needs no matching adjustment for this — it's `flex: 1` (see "Now Playing artwork sizing" above), so it just fills whatever height is left under `paddingTop`, automatically, rather than needing a hand-widened pixel budget the way the old `--np-scale` approach once did.

Both breadcrumb variants render `Playing from "` + (a `.player-meta-link` span, if `queueSource.item` exists, else plain text) + `"` — `fontSize: 11`(narrow)/`12`(full-width), `color: rgba(255,255,255,0.45)`. `.player-meta-link` is the same hover-to-white affordance used by the player-panel artist/album links elsewhere in Now Playing.

## Missing file handling

Files deleted from disk outside the app are handled at two points:

1. **Cold launch** — `library:load` serves cached index entries instantly (it does not touch the files); the background verification pass then stats every path and pushes removals for missing files via `library:updated`. No user action needed.

2. **Live session — audio `onError`** — The `<audio>` element has an `onError` handler. On any playback error, it calls `fs:checkPaths` for the current track's path. If the file is gone: removes the track from library via `removeTracks` (which auto-advances to the next track), shows a toast. If the file exists (codec/format error): skips to next without removing.

3. **Live session — window focus** — A `window.addEventListener('focus', ...)` handler in `App.jsx` fires 500ms after the app regains focus. It batch-checks all library paths via `fs:checkPaths`, removes any missing ones in a single `removeTracks` call, and shows a combined toast ("N tracks removed — files not found"). Uses `libraryRef` (not `library` state directly) to avoid stale closures without putting `library` in the effect's dep array.

**Toast system** — `toast` state (`{ msg, id }`) + `showToast` `useCallback` in `App.jsx`. `showToast` sets the toast then schedules `setTimeout` to clear it after 3.5s (keyed by `id` to avoid clearing a newer toast). Rendered as a `position: fixed` overlay centered above the player, `pointerEvents: none` — `bottom: NARROW_PILL_CLEARANCE` in narrow mode, `bottom: PLAYER_PILL_CLEARANCE` at full width (the same constants each `<TrackList>`'s own scroll clearance uses, see "Player pills" above, not separately hand-picked numbers).
