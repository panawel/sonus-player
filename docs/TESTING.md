# Testing, tooling and their history

Moved out of `CLAUDE.md` to keep that file short: the rules stay there in a line or two, the full detail, the coverage list and the real cases behind them live here. Read the relevant section before changing the smoke suite or chasing a flaky run.

## Dev server details

- `npm run dev` — starts Vite (`localhost:5173`) and launches Electron concurrently (via `concurrently` + `wait-on`). This is the normal development loop; the Electron window loads the Vite dev server, not `dist/`. **It keeps its own data, in `~/Library/Application Support/Sonus Dev`** (the built app uses `.../Sonus`): sharing one folder let whichever of the two quit last overwrite the other's window size and session. Its first launch copies the library, index, covers and session from `Sonus`; delete `Sonus Dev` to start it fresh from the built app's data again. A `--user-data-dir` on the command line still wins.
  - **Kill any previous dev server first** (`pkill -f "mp3Player/node_modules"` — scope the pattern to this project, a bare `pkill -f Electron` also kills VS Code and any other Electron app). `pkill -f` also matches **the shell running it** when its own command line contains the pattern (e.g. `pkill -f "vite --port 5173"` inside a longer command): the whole command dies with exit 144 and later steps silently never run; use `ps aux | grep <pattern> | grep -v grep | awk '{print $2}' | xargs kill` in multi-step commands — and even that kills its own shell when the pattern appears **anywhere else in the same command** (a `rm -rf /tmp/sonus-e2e` after a kill of `sonus-e2e` did exactly that, twice): run the kill as its own command. If Vite prints `Port 5173 is in use, trying another one…` it binds **5174**, while Electron still loads **5173** — so `wait-on` succeeds, the window opens against the *old* server, and you silently test stale code with no error anywhere.

## Commands (full notes)

The original, longer form of the command bullets `CLAUDE.md` now keeps short.

- `npm run build` — `vite build` (frontend → `dist/`) then `electron-builder`, producing a **universal** (Intel + Apple Silicon) `.dmg` and `.zip` in `release/`. ~257MB per artifact, ~525MB installed: both architecture slices of the Electron framework ship in one bundle. ~40s, but the *first* universal build downloads the x64 Electron dist (~100MB) and needs network. See `BUILD_INSTRUCTIONS.md` for the full packaging walkthrough (verification, cross-arch testing, file associations, moving to `/Applications`).
- `scripts/verify-bundle.sh [app] [--expect-universal|--expect-arch <arch>]` — structural checks on a packaged `.app` (defaults to `release/mac-universal/Sonus.app`). **The app path must come first when you pass a flag**: `verify-bundle.sh --expect-universal` reads the flag as the path and dies with `No app bundle at: --expect-universal`; write `verify-bundle.sh release/mac-universal/Sonus.app --expect-universal`. Exits 0/1. Asserts every Mach-O binary carries both slices, `LSMinimumSystemVersion`, all six file associations, all three Finder Service bundles, a single merged `app.asar`, and that the smoke fixture is present. **A partial `lipo` merge is the failure this exists for** — the app launches fine on the machine that built it and then dies on Intel in whichever helper process was missed.
- `npm run lint` — ESLint over the whole repo (flat config in `eslint.config.js`). **The clean baseline is `5 problems (0 errors, 5 warnings)`** — three `exhaustive-deps` in `App.jsx` and one in `HomeDetailView.jsx` whose dep arrays are deliberately incomplete (each marked "intentionally omits" in a comment right above it), plus TanStack Virtual's incompatible-library notice in `TrackList.jsx`. Don't try to "fix" those five; a **sixth** warning is the signal. (One further exhaustive-deps warning — a volume/mute sync effect — genuinely disappeared when the full-width player pill removed volume control entirely and deleted the now-dead effect along with it; that's a real drop in the baseline, not a fix you need to re-apply.)
- **Developing against the smoke suite: run only the section you touched.** `npx electron . --smoke --only=menus` (or `SONUS_SMOKE_ONLY=menus,adddialog`; sections: `tracklist, header, mini, menus, adddialog, split, strip, listrows, chillend, chillswitch, tagwrite, folder, writers, reindex, fileopen, save-playing, reopen, tageditor, bench, frames, mix, session`) runs just those, ~10s instead of ~3min. The names don't always say where a check lives: the title strip, the song's pill and the 380px narrow checks are in `mini` (not `header`, which is the tracklist's column header); the split and its frame-sampled motion are in `split`. Every check inside a chosen section is identical to the full suite; the others are not run. The result carries `partial: true` and a notice is printed: **a filtered pass is a development aid, never the gate**; run the full suite once before a build or release. A mistyped section name is reported as a failure (a filter matching nothing would otherwise read as success). Smoke windows also opt out of Chromium's background/occlusion throttling (`main.js`, smoke only) so a covered or idle window no longer produces random failures. Workflow that keeps it quick without skipping anything: unit tests + the relevant `--only` section while iterating, one full run at the end, in the background, never a rerun for the same edit.
- `ELECTRON_RUN_AS_NODE=1 node_modules/.bin/electron scripts/check-quit.cjs [path/to/Sonus.app]` — the **real quit test** on the built app (defaults to `release/mac-universal/Sonus.app`), which the smoke suite can't do: throwaway profiles; a visible window, a closed (hidden) one and the strip; one Quit each, sent like Cmd+Q to that one PID; checks the app exited and what it reopens as. ~1 minute. Run it after anything that touches quitting, window lifecycle or the session. It must run through Electron-as-Node (it needs `WebSocket`) and must not pass that variable on to Sonus (it would start as Node and every window check would read nothing).

## Unit test coverage

- `npm run test` — `vitest run`, all tests once. Tests sit beside their sources: `src/*.test.{js,jsx}` run under jsdom + React Testing Library, `electron/*.test.mjs` are pure Node against temp dirs — which is *why* `artwork.mjs`, `indexStore.mjs`, `launchFiles.mjs`, `finderServices.mjs`, `folderScan.mjs`, `pointerTracker.mjs`, `pointerMotion.mjs`, `appMenu.mjs`, `windowModes.mjs` and `session.mjs` are Electron-free modules.
- **Coverage is deliberately lopsided, and a green run means less than it looks.** The pure modules, the sort/selection hooks and `TrackRow` are covered well. The three biggest renderer files are not covered at all: `HomeView.jsx` (1500+ lines), `TagEditorWindow.jsx` (577) and `TrackList.jsx` have **no unit tests**, and `App.test.jsx` only asserts that 2600+ lines of `App.jsx` mount without throwing. `MiniPlayer.jsx` and the Chill-mode components (`ChillScene`, `ChillTurntable`, `ChillBeach`, `ChillScenePicker`) have no unit tests either; what *is* covered is their pure maths and hooks — `trackMatchesQuery`, `pointerTracker.mjs`, `pointerMotion.mjs`, `chillGeometry.js` / `chillScene.js` / `chillBeach.js` / `chillRoom.js` / `chillLyrics.js` / `chillScenes.js` / `chillTransition.js` (the scene-switching state machine) / `chillPreload.js` / `chillNotes.js` (which verses go on the room's papers) (framing, the quad→matrix3d solver, the swing, the typing clock, breathing, the poster and laptop calibration, the scene registry) and `useChillChrome` — plus `ChillPhoneScreen` and `ChillLivingPhoto`'s no-WebGL fallback in jsdom, and the title strip / Now Playing motion pieces (`bubbleMotion.js` — the spring solver, `Bubble.jsx`'s presence logic with a fake `animate()`, `useCrossfadeStack.js`, `coverCache.js`, `ArtCrossfade.jsx`) and `useAutoHideScrollbars.js`. Everything meaningful about those is exercised **only** by the smoke suite below. `npm run test` passing says nothing about the UI.

## Writing smoke checks

- **Prove every new check fails on the bug**: put the bug back temporarily, run the check, calibrate the threshold between the two (see `docs/PITFALLS.md`, "Write a regression check without proving it fails on the bug").
- **Synchronisation is condition-based where it gates an assertion.** The suite used to sync with fixed `await sleep(400)` calls, which encoded the speed of the Apple Silicon machine they were written on; running the x86_64 slice under Rosetta made four *different* assertions fail across four runs. Shifting, non-reproducible failures are the signature of a harness race, not a defect. Those points now poll for the real condition, so machine speed stops mattering. Four rules when adding more: a layout measured right after `mainWindow.setContentSize` lags the resize by a frame (a `ResizeObserver` → state → transform chain), and a *stale* layout can satisfy a condition by accident (a bigger stage still "covers" a smaller box) — so wait for **two identical consecutive samples** before judging geometry; the fixture is only **20 seconds** long, so any block that runs longer than that after playback starts must set `audio.loop = true` (and restore it) or the track ends underneath it, `play()` finds nothing to resume, and every later test that expects audible playback (the mini player's) fails as a cascade; assert that an animation actually *advances* (angle/`currentTime`), not just that its `playState` is `running`; and the condition must be **false before** the transition (waiting on `.track-row` to be non-zero is wrong — the Library's rows are already mounted, so the loop exits immediately and samples too early), and on timeout the last value must still be returned so the `check()` still runs and still fails. `SLOW` scales the remaining "settle" sleeps, auto-detecting Rosetta; override with `SONUS_SMOKE_SLOW=<n>` on genuinely slow native hardware.

## Driving the app outside the suite

- For one-off DOM inspection outside the smoke suite (e.g. verifying a narrow-width layout), a standalone script run via `electron <script>.mjs` can create a `BrowserWindow` at any size and drive it with `executeJavaScript` — same technique `smokeTest.mjs` uses, no dev toolchain needed beyond the running `vite` dev server. **Creating a second `BrowserWindow` in the same process after the first sometimes fails to load** (`ERR_FAILED`, reproducible on this machine) — run one check per `electron` invocation rather than reusing a process across multiple test windows. For a window that loads the running dev server (`http://localhost:5173/?test=1`) give it `preload: electron/preload.cjs`, `webSecurity: false` and `enableLargerThanScreen: true` (to test sizes above the display), seed `window.__sonusTest.setLibrary([...])` with a `test-fixture.mp3` copy, and double-click a `.track-row` to start real playback. Resizing the *same* window with `setContentSize` between captures works fine; `webContents.capturePage()` captures opaque in-page content (a photo, say) correctly even though it can't capture vibrancy. The main process's IPC handlers aren't registered in such a window, so `library:load` / `fs:readArtwork` errors on stderr are expected noise.
- **Driving the real app end to end (real `main.js`, real cursor)** — what the standalone-`BrowserWindow` technique above can't reach (anything the main process owns: pointer tracking, window chrome, IPC handlers). Start `npx vite`, then `npx electron . --remote-debugging-port=9333 --user-data-dir=/tmp/sonus-e2e` (a **throwaway profile**, so your real library and saved window state are untouched; there is no single-instance lock, so it runs beside a live `npm run dev`). To launch at a chosen size, pre-seed `/tmp/sonus-e2e/window-state.json` (`{"x":300,"y":200,"width":440,"height":300,"isMaximized":false,"isFullScreen":false,"displayBounds":{…}}` — only the x/y/width/height need to land on a display). Drive the page over CDP (`http://127.0.0.1:9333/json`); **run the driver with `ELECTRON_RUN_AS_NODE=1 npx electron script.cjs`**, because the system Node (v20) has no global `WebSocket` and `ws` isn't installed. Move the real cursor with `osascript -l JavaScript -e 'ObjC.import("CoreGraphics"); $.CGWarpMouseCursorPosition($.CGPointMake(x, y))'` (screen coordinates, no permissions needed). Things that look like they should work but don't: `window.resizeTo()` from the page doesn't resize an Electron window, `Browser.setWindowBounds` isn't available on the page target, and `screencapture` from inside a Claude Code session is denied ("could not create image from rect" — no Screen Recording permission), so native window chrome (traffic lights) can't be seen from here; ask the user to look. **Profiling rendering on the real app** (how the skip flicker was found; seed the throwaway profile with a copy of the real `library.json` to use real covers, read-only): from the CDP driver, `LayerTree.enable` + `LayerTree.layerPainted` events (filter by clip area to count *large* repaints) on the page target, and `Tracing.start`/`Tracing.end` with `transferMode: 'ReportEvents'` on the **browser** target (`/json/version`, then `Target.attachToTarget` with `flatten: true` to drive the page). `contentTracing` from an Electron main script hung here, and `capturePage` cannot see compositor-level glitches (tile patchwork, partial frames): a user's screen recording + `ffmpeg` frame extraction is the evidence for those. Kill it with `pkill -f "user-data-dir=/tmp/sonus-e2e"` and delete the profile.
- **To run the suite against a *development* React build** — `NODE_ENV=development npx vite build --mode development && npx electron . --smoke`. The normal suite runs production React, which never double-invokes StrictMode updaters, so a whole class of dev-only bugs (see the "side effect inside a `setState(updater)`" row below) passes it while breaking under `npm run dev`. This is the only way to exercise that path with real IPC. `--mode development` **alone is not enough** — Vite still emits production React (bundle stays ~402KB); the `NODE_ENV` env var is what flips it (bundle ~639KB — check that number, it's the only visible confirmation). Run a plain `npx vite build` afterwards so `dist/` is production again.

## Rosetta runs and flaky failures

- **`arch -x86_64 <binary> --smoke` failing with `Bad CPU type in executable` doesn't necessarily mean the build isn't universal** — it's also exactly what happens when Rosetta itself isn't installed on the host Mac, which a macOS upgrade can silently reset (hit for real right after an upgrade to macOS 27). Don't assume the build is broken and start re-lipo'ing things; check first with a trivial system binary the build had no hand in: `arch -x86_64 /usr/bin/true` fails identically either way, so the real discriminator is `lipo -info <binary>` (confirms both slices are genuinely present) plus `ps aux | grep oahd` / `pkgutil --pkgs | grep -i rosetta` (confirms whether Rosetta is actually installed). If it's missing, `softwareupdate --install-rosetta --agree-to-license` is the fix — a standard, reversible Apple component install, not a system/security setting change.
- **The x86_64 smoke under Rosetta flakes roughly one run in three**, on a shifting assertion ("library command bar", "instant load", the frame-time probe, the Mix block's `waitFor` checks) — the harness-race signature described under `npm run test` above, not a defect; it doesn't always fail just one assertion either — a heavily-loaded run can take out a cluster of unrelated ones at once (real case: `mix: Details page shows the MIX kicker` through the breadcrumb check, four in one run). Protocol: rerun **once**, and capture the *full* failure text that time (don't `cut` it) so a genuine second failure is diagnosable. Two failures in a row on the *same* assertion(s) is real. **A second run failing on a *different* assertion than the first is not yet a clean bill of health either** — that's still the harness-race signature, just a different sample of it — keep rerunning until one pass has zero failures; only that counts as confirmation. Never publish on a single green rerun without having seen what the first failure said. It takes **7-10 minutes** translated (measured at 1.7.0; the suite has grown), so run it in the background and don't poll. **Check for these causes before calling a Rosetta failure a flake** — each one produced a *recurring*, not random, cluster at 1.7.0, and each was a harness assumption, not an app bug: (1) **the 20-second fixture track ended** underneath a long block (everything after fails with "playing false" / a paused record / a progress bar that wrapped), so loop it from the moment playback starts; (2) a check **sampled a transition's start, not its end** (opacity reaches 1 before the idle flag clears; the scene attribute flips before its disc mounts; the Details page appears a beat before the search panel closes): wait for the settled state; (3) a **timing assumption measured from the wrong start** (lightning: the scene's first flash was over before the polling loop began, and the next is up to 26s away, so wait for the event, polling in real time, not on a `SLOW`-scaled sleep that can step over a 150ms peak); (4) a **fixed delay after heavy work** (the 20k-track bench leaves a slow machine busy for a while: wait for the `<audio>` element, retry `play()`, and settle frame sampling before measuring). The final 1.7.0 build passed both slices with zero failures after those fixes. **1.8.0 added three more of the same kind**: (5) a check that **counts samples** of something fast or timed (in-between widths of a spring, stopped samples at a verse break): the count falls with the frame rate and with `SLOW`-scaled polls, so assert real elapsed time or the bug's own signature (0) instead; (6) **polling a brief peak over IPC** steps over it (lightning read 0.49 against 0.5): sample inside the page on `requestAnimationFrame`; (7) a page opening **stalls the main thread right through a short animation**, so its overshoot is never sampled: accept the running spring easing as evidence when the sampler demonstrably stalled.
- **Intermittent smoke failures and multi-second frame stalls on this Mac, cause unconfirmed.** Seen across several runs: a single Now Playing frame taking 12s (once 484s — an ~8 minute run instead of ~50s), and runs where the mini-player section never appeared within its wait and everything after it failed. Every one passed on a plain rerun, repeatedly (five clean ~49s runs in a row at one point), and nothing in the code explained them. The smoke window is *visible* on screen, so the leading suspicion is the window being covered or the display idle (Chromium/macOS throttling an occluded window) — not proven, and `main.js` has no `backgroundThrottling`/`disable-backgrounding-occluded-windows` guard. **Stronger evidence since:** a run stuck for 11+ minutes while `ioreg -c IOHIDSystem | awk '/HIDIdleTime/'` showed the user idle for ~30 minutes (display almost certainly asleep); killed and rerun under `caffeinate -di npx electron . --smoke` (keeps the display awake for just that command), it passed in ~50s twice in a row. Still not proven the cause, but when the user is away, **run smoke as `caffeinate -di npx electron . --smoke`** — it costs nothing. If it recurs anyway: check `ps aux | grep -i electron` first (the item below), look at the metrics' `frameTimeMs.max` (a huge value = a stall, not a defect), and rerun before debugging. Also remember that `pkill -f "mp3Player/node_modules"` — the documented step before a smoke run — stops the user's own `npm run dev` window too; restart it afterwards.
- **The Chill idle-fade smoke check (`bar, tabs, search, add and exit all fade out together…`) failed intermittently, then three runs in a row — it was a REAL bug, not a flake.** `useChillChrome` remembered "the pointer is resting on the chrome" from the last `mousemove`'s target; that went stale whenever the pointer left without an event to say so (the smoke window resizing away from a parked cursor over the bar — the cursor's *position* decided whether a run failed, which is why it came and went; a user tabbing away after resting on the bar), and held the chrome up forever. Found only by logging what woke it (a trusted `mousemove` on the seek bar, then nothing). The fix asks the browser (`:hover`) when the timer fires. Lessons: don't remember pointer-over state, ask at decision time; a synthetic DOM `mousemove` can't test hover — use `webContents.sendInputEvent`; and don't explain an intermittent failure away ("the mouse", "a stall") without evidence — I blamed the mouse and then a stall, and both guesses ended up in this file before the log refuted them. (Real renderer stalls do exist — see the next entry; a 36s `frameTimeMs.nowPlaying.max` is how to recognise one.) **It has failed intermittently again since** (once on a packaged arm64 run at 1.8.0, nobody at the mouse, the OS cursor nowhere near the chrome; then six clean runs), cause unknown. The check now reports wakes, the element under the pointer and open panels in its failure text: read that before explaining it.
- **Running more than one Electron process at once (a `--smoke` run alongside another `--smoke` run, or alongside a live `npm run dev` window) makes `save-while-playing` fail spuriously**, cascading into `20k: scroll window actually moved` and a `frame-time probe` reading zero captured frames — all three at once, on *either* architecture, not the shifting-single-assertion Rosetta pattern above. Real audio playback and `requestAnimationFrame` both appear to get starved when something else is fighting for the same GPU/compositor. Confirmed by running the *same* build solo immediately after: clean pass, every time. Before trusting a `--smoke` failure (especially `save-while-playing`), check `ps aux | grep -i electron` and kill any other instance, then rerun alone.

## README screenshots

- A plain Playwright/CDP screenshot of this app will render mostly blank/white — it can't capture macOS's vibrancy/transparency compositing. This is a known tooling limitation, not a visual regression; don't diff against headless screenshots as a correctness check. To verify visual changes: run `npm run dev`, then use `screencapture -x /tmp/sonus.png` (native macOS screenshot, which correctly captures vibrancy compositing). For pixel-level verification, use Python PIL (`from PIL import Image; img = Image.open('/tmp/sonus.png').convert('RGB'); img.getpixel((x, y))`). Retina displays produce 2× physical pixels, so logical coordinates must be doubled.
- **The 1.9 README assets** (`docs/assets/*.jpg`) were exported by hand from the user's captures, not by the script below: downscaled to 1600px wide (downscale-only), flattened onto black, JPEG q88 with `subsampling=0`; the hero's track list had a title with the developer's first name, blurred (Gaussian, the name's box only). The script below still writes the old PNG names and its `MAPPING` is stale.
- `python3 scripts/prepare-screenshots.py` — turns raw captures in `screenshoots/` (gitignored) into the README assets in `docs/assets/`. Resizing is **downscale-only** — the phone-portrait captures (`narrow-*.png`) are natively under the 1600px target and are left at native size rather than blurred upward. Two non-obvious jobs beyond that: it repaints the Tag Editor's File field, which showed a real absolute path containing the developer's macOS username; and it flattens RGBA onto opaque black, because GitHub renders README images over a light *or* dark page depending on the viewer's theme and any transparency would show through inconsistently. Captures must come from native `screencapture` — see "Working in this repo" for why headless screenshots of this app are useless.
- **The 1.7 README assets were exported by hand, not by this script**: 13 PNGs + `chill-mode.gif` came pre-captured (retina, ~3456px), were downscaled to 1600px wide and flattened onto black with Pillow, and two spots showing a track title that contains the developer's first name were blurred (Home's bottom-row album card; the phone-width Details page). Their names differ from this script's `MAPPING` (`details.png`, `narrow-details.png`, `now-playing-lyrics.png`, `mini-mode.png`, `chill-mode.gif`; `artist*.png` and `now-playing.png` were removed), so rerunning it would recreate the removed files: update `MAPPING` first. The new captures black out the Tag Editor's File field entirely rather than painting a generic path.
- **The File-field redaction relies on the field being captured as a transparent region** (macOS occasionally rasterizes an editable text field that way) — `transparent_bbox()` finds it via alpha. Screenshots supplied pre-named and pre-organized (e.g. dropped straight into a folder matching the `docs/assets/` output names, bypassing `screenshoots/` and the `MAPPING` dict entirely) have come through fully opaque instead, alpha check finds nothing, and the field's real text — a real path, username included — is genuinely visible pixels. In that case the fix is manual: crop tightly around the field to find its pixel bounds, sample its fill color from a flat area away from any glyphs, `ImageDraw.rectangle` over just the interior (inset a few px so the field's own rounded border survives untouched), then draw replacement text sized to actually fit the box (measure with `textbbox`, shrink the string or the font until it's narrower than the interior — don't guess).

## Asset scripts (full notes)

- `python3 scripts/make-app-icon.py` — rebuilds `build/icon.png` (1024 master, also the dev Dock icon) and `build/icon.icns` (packaged) from `build/icon-art.png`, cutting the artwork to the exact squircle macOS needs to NOT put the icon on a grey plate (see "Known accepted issues" — the plate entry, now resolved). Needs only Pillow + `iconutil`. `build/icon-art.png` is the current "Sunset record" art (a vinyl and tonearm on a gold-to-magenta gradient), drawn once with Pillow at 3x supersampling; **that generator is not in the repo**, only its output, so a redesign means producing a new opaque 824x824 PNG (any tool) and rerunning this script.
- `python3 scripts/fit-chill-room-posters.py [--overlay DIR] [--adopt id,...]` — measures the study room's poster quads **and the two lyrics papers' (`notes`)** against the photo's real edges (and each print's blur) and writes `quad` / `fit` into `src/chillRoomPosters.json`; prints that don't pass get no artwork. Needs only Pillow; run it BEFORE `make-chill-room-mask.py` (the glare map is restricted to the fitted quads). `--overlay` writes red-seed / green-fit / amber-rejected crops to look at; `--self-test` asserts the outer-edge check still flags the old bad New York top edge (a fit sitting on lettering ~10px inside the print's real edge passes every other test — only that check catches it). Sides are listed top, right, bottom, left: when marking one `"trust"` after a flagged outer edge, count carefully (I trusted `bottom` when the flagged side was `left`).
- `python3 scripts/make-chill-room-mask.py [--preview out.png]` — rebuilds the study room's masks (and, for the lyrics papers, measures their real `paper` colour from the photo: they are dim and warm, never white) (`room-mask.png`: window glass / string lights / her back) from the polygons in the script **and refreshes `light` — the room's own lighting around each print — in `src/chillRoomPosters.json`** (the 24 poster quads themselves are edited by hand); run from the repo root, needs only Pillow. `--preview` tints the photo with the masks and outlines the posters.
- `python3 scripts/make-chill-beach-mask.py [--preview out.png]` — rebuilds `src/assets/chill/beach-mask.png` (palm/sea/shore masks) and `beach-body.png` (the hammock + man + phone, for the swing) for the hammock scene's animated photo, from `beach.jpg`; run from the repo root, needs only Pillow. `--preview` writes the photo tinted with the masks (red palms, cyan sea, yellow shore, magenta body), which is how you check them by eye.
