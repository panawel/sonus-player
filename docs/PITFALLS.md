# Things that fail silently — full entries

The complete version of `CLAUDE.md`'s table, with the real case behind each row, and the full "known accepted issues". `CLAUDE.md` keeps each rule in a line; read the entry here before touching that area.

Each of these looks fine in `npm run dev` (or by eye) and breaks somewhere you won't notice. Read the linked section before touching that area.

| Don't | Why |
| --- | --- |
| Hand-write `-webkit-backdrop-filter` | Kills the blur in **packaged builds only**. See [`backdrop-filter`: never hand-write the `-webkit-` prefix](../CLAUDE.md#backdrop-filter-never-hand-write-the--webkit--prefix) in `CLAUDE.md`. |
| Put the tracklist column header back inside a scroll container | Rows pass behind it, forcing an opaque fill that visibly darkens on scroll. [Details](ARCHITECTURE.md#the-column-header-lives-outside-the-scroll-container) |
| Animate the column header's *height* | `TrackList` measures `scrollMargin` in a layout effect that never re-runs on scroll — windowing and `scrollToIndex` silently desync. [Details](ARCHITECTURE.md#tracklist-engine-tracklistjsx--trackrowjsx--tracklistheaderjsx--hooks) |
| Point `scrollElRef` at anything but the real scrolling ancestor | Virtualization silently stops — every row mounts, no error. [Details](ARCHITECTURE.md#tracklist-engine-tracklistjsx--trackrowjsx--tracklistheaderjsx--hooks) |
| Read the metadata store without `await ensureStoreLoaded()` | Every path looks unknown → whole library served as placeholders + a full spurious reindex. [Details](ARCHITECTURE.md#launch-behavior-what-library-the-app-starts-with) |
| Detect the pointer over a `-webkit-app-region: drag` element with page mouse events (`mouseenter`, `mousemove`, React `onMouseEnter`) | Electron hands drag areas to the OS, so the page **never receives the pointer there** — only over the no-drag controls (buttons, inputs, `.clickable`). The mini player's hide-the-chrome-until-hover first did exactly this and only worked over its buttons; synthetic input (`webContents.sendInputEvent`, dispatched events) bypasses the drag layer, so every automated test passed. The pointer is now tracked from the main process (`electron/pointerTracker.mjs`, OS cursor vs window bounds). If a new feature needs hover over a draggable surface, do the same. [Details](ARCHITECTURE.md#mini-player-very-short-windows) |
| Hide the app under the mini player with `visibility: hidden` or `display: none` | `visibility` is overridden by descendants that set their own (`.scrollable` does), so the Library shows straight through the mini card; `display: none` collapses the scroll containers and silently loses every scroll position. It's `inert` + `opacity: 0`. [Details](ARCHITECTURE.md#mini-player-very-short-windows) |
| Conditionally render `HomeView` instead of `display: none` | Re-decodes every artwork image on each visit; the freeze returns. [Details](ARCHITECTURE.md#home-view-srchomeviewjsx-srchomedetailviewjsx) |
| Remove `nativeTheme.themeSource = 'dark'` or any one vibrancy flag | Glassmorphism depends on the window flags **and** the CSS **and** this line together. [Details](ARCHITECTURE.md#vibrancy-and-forced-dark-mode) |
| Drop `corsEnabled` from the `sonus-thumb` scheme | Renderer `fetch()` of thumbnails is refused outright; `<img>` still works, so it looks fine. [Details](ARCHITECTURE.md#metadata-index-thumbnails-play-stats-electronindexstoremjs--mainjs) |
| Save scroll position in an effect cleanup | `display: none` collapses `scrollHeight` first, so the saved value is always 0. [Details](ARCHITECTURE.md#scroll-position-preservation-across-views-appjsx) |
| Rely on `setCurrentTrack` alone to (re)start playback | `<audio src>` comes from the track's path, so re-selecting the **already-loaded** track produces an identical src — React changes no DOM, `autoPlay` never re-fires, and the element stays paused mid-track. `playTrack` restarts it explicitly; keep that branch. |
| Set `isPlaying` optimistically before audio starts | The button then claims "playing" over silence, turning any playback failure into a "stuck" app. `onPlay`/`onPause` are the only source of truth. |
| Use `BrowserWindow.center()`, or resize a window without repositioning it | `setContentSize` pins the top-left corner, so a window that grows lands off-centre; and Electron's `center()` was measured ~40px off the work-area centre. [Details](ARCHITECTURE.md#tag-editor--a-separate-window-not-a-view) |
| Reintroduce base64 artwork into track objects | The whole index/thumbnail architecture exists to keep it out of renderer heap. |
| Upgrade Electron without checking `LSMinimumSystemVersion` | Electron's macOS floor climbs over releases, and raising it **permanently drops the oldest supported Mac** — see [The macOS support floor](../CLAUDE.md#the-macos-support-floor-and-why-electron-is-pinned) below. Nothing warns you; the build succeeds and the app simply refuses to launch there. |
| Ship a universal build without running `scripts/verify-bundle.sh` | A partial `lipo` merge leaves one helper arm64-only. The app launches on Intel and then dies in that process. Invisible on the machine that built it. |
| Move Inter back to a CDN `@import`, or break the bundled woff2 paths | The UI silently renders in `-apple-system` — no error, no console warning, just subtly wrong typography everywhere, and permanently so on an offline Mac. Guarded by a `FontFace.status` assertion; see below. |
| Test font loading with `document.fonts.check()` | It returns **true for a family that does not exist**, because the text is still renderable through the fallback chain. Verified against `__SonusNoSuchFont__`. Use `FontFace.status === 'loaded'` instead — `check()` makes the assertion pass unconditionally. |
| Give an element inside `.glass-panel` (or any `backdrop-filter` surface) a z-index to stack it above a true sibling | `backdrop-filter` creates its own stacking context, so that z-index only competes with the panel's *other* children — it can never out-rank something outside the panel, no matter how high. The element has to actually be a sibling of what it needs to beat, not just carry a bigger number. Second real case: the search panel lived inside `.glass-panel`, so Chill mode's full-window layer (a sibling, z 30) covered it completely — the search button "did nothing" while its click handler ran fine (hit tests on every button said clickable, which is why it took a hit test *on the panel* to see it). It now renders at the root, and its CSS `top` is `92px` (the 42px title strip + the 50px it used to sit below the card, since a `backdrop-filter` ancestor is also the containing block for `position: fixed` descendants). First real case: the since-removed narrow-mode sidebar drawer once covered the search box/hamburger this way — confirmed live via `document.elementFromPoint()`, the covered element wasn't just visually dimmed, it was genuinely unclickable. [Details](ARCHITECTURE.md#narrow-layout-phone-portrait-widths) |
| Dedupe against current library membership *before* deciding what a "Play Next" action should queue | Regression that shipped and went unnoticed: Finder Services' "Play Next in Sonus" (`queueTracksFromService`) and the drag-and-drop confirm modal's Play Next (`resolvePendingTracks`) both used to filter out already-in-the-library tracks before touching `forcedNextQueueRef` — the ref that actually drives what plays next (`playNext()` reads only that, not row position). A track you Play-Next'd that happened to already be in your library silently did nothing. Fix: dedupe only decides which rows get newly *inserted*; every selected track, new or not, still reaches `forcedNextQueueRef`. `add-to-queue` is unaffected — for that action, an already-present track really is a no-op. [Details](ARCHITECTURE.md#finder-services-integration-add-to-queue--play-next) |
| Trust `getComputedStyle` + `document.elementFromPoint()` to prove text is rendering the color it declares | Both can say "fine" while the pixels are wrong. Real case: narrow Now Playing's title rendered ~186/255 gray with `color: rgb(255,255,255)` and a hit-test returning the text itself — the artwork card's `zIndex: 1` drop shadow (24px downward offset) was painting *over* the text, and **box-shadows paint over later siblings but are never hit-testable**, so `elementFromPoint` cannot reveal one. Forcing the text onto its own compositing layer changed nothing either (that doesn't alter z-order). The fix was `position: relative; zIndex: 2` on the text block; the diagnosis only came from `webContents.capturePage()` + PIL, sampling actual pixels against a known reference. When a color looks wrong but the CSS says it's right, go straight to pixels. [Details](ARCHITECTURE.md#now-playing-glass-backdrop--contrast-guarantee) |
| Put a side effect inside a `setState(updater)` function | `src/main.jsx` wraps the app in `StrictMode`, which **calls updater functions twice** in dev — never in the packaged build. Anything order-dependent inside one breaks only under `npm run dev`, exactly where everyone looks. Real case: the tag-saved handler reloaded `<audio>` inside `setCurrentTrack(ct => …)`; the first call's `audio.load()` synchronously reset the element to 0/paused, so the second call captured "resume at 0, wasn't playing" and the song stopped at the start after every Save — while the smoke suite (built app) passed. Do the effect in the handler body, read state through the mirror refs (`currentTrackRef` etc.), and keep updaters pure. The save-while-playing smoke case guards the production path; the dev-only half is guarded only by keeping updaters pure. [Details](ARCHITECTURE.md#tag-editor--a-separate-window-not-a-view) |
| Add a `-webkit-app-region: drag` element and assume z-index decides who wins over the buttons | **Electron builds the draggable area by walking the page in DOCUMENT ORDER**: a later `drag` region is *unioned over* earlier ones, a later `no-drag` is *subtracted* from them. z-index plays no part. Chill mode's `.chill-drag-strip` (needed because its full-window `no-drag` layer would otherwise carve the whole strip out and make the window immovable) was first rendered *after* the title-bar buttons, re-claimed their area as draggable, and **none of them could be clicked** — while every test passed, because `.click()` and CDP/`sendInputEvent` bypass the OS drag layer entirely (a real click needs Accessibility permission, which this session doesn't have). Keep the drag band *before* the buttons in the document (it's rendered before them in `App.jsx`); the back arrow is now the centred pill's first slot, so it needs no ordering of its own. And never put `no-drag` on a layer that covers the title strip — the glass card now runs under it (the Now Playing overlay's whole-box `no-drag` once made the window immovable; only its content wrapper below the strip is `no-drag`). Detail pages put a `drag` band at the top of their own page (the scroller is `no-drag`), which is why the strip's pills come after the card in `App.jsx`; the smoke suite asserts the order and `no-drag`. The same trap applies to anything floating over a drag area: the shared track menu (`.track-dropdown`, rendered at the root and opened from the pill, Now Playing, Chill mode and the mini player) is explicitly `no-drag`, because over the mini card (a drag area) its items would otherwise show but never take a click. The page also never sees the pointer over drag areas, so anything that must wake on pointer movement up there needs the main process (`pointerMotion.mjs`). [Details](ARCHITECTURE.md#chill-mode-the-turntable) |
| Give a menu item an accelerator that is also a text-editing key (Space, ⌘←/→, ⌘A...) | A menu accelerator is handled natively and wins over the focused field, so it silently breaks typing in Search and the Tag Editor (and never reaches the page as a keydown). Play/Pause in the Controls menu therefore has none (Space stays the renderer's handler) and Next/Previous are ⌥⌘←/→. Also check the View role first: ⇧⌘R is Force Reload. The smoke suite walks the whole menu and fails on a duplicate accelerator. [Details](ARCHITECTURE.md#file-and-controls-menus) |
| Add or move content in the mini player without checking the 180px minimum | The window can be 180px tall and the content needs ~124px of the ~128px left after padding, so anything added either overflows or squeezes the traffic-light clearance (the artwork once sat ~5px below them, against 22px of margin on its left). The top padding, artwork size and seek gap are CSS custom properties (`--mini-pad-top`, `--mini-art`, `--mini-seek-gap`) with an `@media (max-height: 215px)` override in `index.css`; the smoke suite asserts the artwork's top and that nothing crosses the bottom edge at 380x180 and 380x205. The traffic lights are native and can't be seen from tests — the 22px figure came from a user screenshot. [Details](ARCHITECTURE.md#mini-player-very-short-windows) |
| Trust a `-webkit-app-region` area you cannot drag | The add-songs dialog's first version made its title band `drag` over a no-drag backdrop; every smoke check (computed region, document order) passed and the user still could not drag the window. `sendInputEvent` bypasses the OS drag layer, so a native region can only be asserted, never exercised. Where a drag must be *provable*, make it page-driven (`window:drag`, main follows the OS cursor; the smoke suite warps the real cursor) and test the window's position. Also swallow the click after such a drag: the window lags the pointer, so the release can hit a click-to-cancel backdrop. [Details](ARCHITECTURE.md#add-songs-dialog-addtracksdialogjsx) |
| Pass an open-file batch to `parseFilePaths` without `expandOpenedPaths`, or "rename a Service" by renaming its `.workflow` | A Finder Service can hand over a **folder** (the Services accept `public.folder`); parsed as if it were a song it fails silently, so both consumers of the batch (`flushOpenFiles`, `resolveInitialLibrary`) expand folders first, in natural file-name order (a directory listing isn't sorted on APFS). And a Service's menu title is `NSMenuItem.default` in its `Info.plist`, **not** the bundle's file name: renaming the file would install a second copy beside the old one (the installer never removes what it didn't track); change the title and bump `SERVICES_VERSION`. ## Known accepted issues (don't "fix" opportunistically)

- `webSecurity: false` in the `BrowserWindow` config is required for `file://` audio/art loading to work against the `http://localhost:5173` dev origin. Don't flip this without implementing a custom protocol handler as a replacement.
- `npm audit` reports `shell-quote` (transitive via `concurrently`) and `undici` (transitive via `electron-builder`'s `@electron/rebuild`/`node-gyp`, and via `jsdom`) advisories — both dev-only tooling, never shipped in the built app. Known, accepted risk; don't force-downgrade `concurrently` or otherwise "fix" these opportunistically.
- ~~Album art stored as full-resolution base64 in every track object~~ — **resolved** by the metadata-index/thumbnail architecture (tracks carry only a `sonus-thumb://` URL; full-res is on-demand for NP/Tag Editor). Don't reintroduce base64 into library track objects.
- Orphaned thumbnail files (tracks removed from the library, or art format changes leaving an old-extension file) are not garbage-collected — they're a few KB each in `userData/thumbs/`. Accepted; a cleanup sweep is a possible future follow-up, not a bug.
- Inter ships as `@fontsource/inter` (a devDependency — Vite inlines the CSS and emits the woff2 as hashed assets at build time, so nothing is needed at runtime). All **seven** subsets are bundled for the five weights, not just latin: the previous Google Fonts endpoint served them all via `unicode-range`, and bundling latin alone would silently drop Cyrillic and Greek track titles to the system font. Cost is ~520KB of woff2. `@fontsource` also references a legacy `.woff` per face, so ~680KB of never-loaded fallbacks ship too — Chromium always picks woff2. Accepted: ~0.14% of a ~500MB bundle, and stripping it would mean hand-maintaining 35 `@font-face` blocks or a fragile post-build rewrite.
- The packaged `app.asar` ships the ~320KB generated fixture MP3 and the `*.test.mjs` files (~14MB of its 25MB). **Deliberate, not an oversight** — it is exactly what lets the packaged app run its own `--smoke` suite on a target machine with no dev toolchain installed, which is how the Intel iMac gets machine-checked rather than eyeballed. A `files` exclude would save 14MB out of a 494MB bundle and cost on-device acceptance testing. Don't strip it without replacing that capability.
- The universal build is **unsigned and un-notarized** (no Apple Developer account). On Ventura the right-click → Open bypass still works, so it costs one extra click the first time on a given Mac. Note this bypass was removed in macOS 15 Sequoia, so a modern Mac needs System Settings → Privacy & Security → "Open Anyway" instead. `codesign --verify` fails strictly on the ad-hoc signature (`code has no resources but signature indicates they must be present`) — that is normal for electron-builder's unsigned output and matches the known-good baseline, which is why `verify-bundle.sh` reports it as info rather than asserting it.
- The `react-hooks/refs`, `react-hooks/set-state-in-effect`, and `react-hooks/immutability` ESLint rules are disabled in `eslint.config.js` — they're React-Compiler diagnostics, this project has no React Compiler, and the codebase's documented render-time mirror-ref idiom (`viewRef.current = view` etc.) is deliberate. Don't "fix" the idiom to re-enable them.
- ~~The packaged app's Dock/Finder icon sits on a light-grey plate~~ — **resolved**, and the earlier "accepted, needs an Xcode asset catalog" diagnosis was wrong. On macOS 26/27 the system decides from the icon's **alpha outline alone** whether to draw it as a modern icon or shrink it onto a grey plate: with Sonus's colours and another app's outline it is not plated; with Sonus's outline and another app's shadow it is. Size (824/1024 vs larger), a shadow, a rim, the Info.plist, the linked SDK and the `.icns` chunk layout all made no difference. A plain rounded square (circular corner arcs, radius ~190, the usual "squircle" recipe) is rejected even at the right size; a **superellipse |x|^5 + |y|^5 = 1**, 824px centred in the 1024 canvas, is accepted. `scripts/make-app-icon.py` builds `build/icon.png` + `build/icon.icns` from the opaque 824x824 art in `build/icon-art.png` — edit the art there, never the outputs, and keep the mask curve. How this was found, and how to re-check it without seeing the Dock: render the icon through macOS's own icon service (`NSWorkspace.iconForFile` on an ABSOLUTE path — a relative one silently returns a generic document icon — drawn into a bitmap via `osascript -l JavaScript`) and look at the PNG; a bundle with just an `Info.plist`, a `Resources/icon.icns` and a dummy executable is enough to test an icon variant in seconds, and the installed apps in `/Applications` are free comparison cases. Dock/Finder cache the old icon: after installing a new build, `killall Dock` (and `killall Finder`).
